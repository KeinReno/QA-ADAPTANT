## РЕШЕНИЕ: REJECT

Исправление QWEN-F1 на SHA 41043ad **не принимается**.

Основание (критерий заказчика): «Если хотя бы один из R5–R8 воспроизводит ложный trusted
PASS в исходной A2 — классифицируй дефект по фактическому воздействию и выдай REJECT».
Воспроизведены **три** независимых пути к ложному доверенному PASS в исходной A2:

1. **R5** — процесс того же Windows SID изготавливает валидный DPAPI-конверт закрепления
   для корня жертвы со своими keyId, **не извлекая приватные ключи жертвы**; подмена
   публичных файлов + изготовленного pin → полный доверенный PASS в хранилище жертвы.
2. **R8** — штатная процедура `resealTrustRootPin` после подмены `owner.pub` принимает
   секреты атакующего: сравнение ключа с `owner.pub` из того же подменённого корня
   самореферентно → перезакрепление чужих ключей → полный доверенный PASS.
3. **R7 (= N10в базовой матрицы)** — публичный `startTrusted` с указателем `trustRoot` на
   полностью новый корень атакующего (валидный pin «из коробки» от `createTrustRoot`) →
   полный доверенный PASS в хранилище жертвы; корень жертвы не изменяется.

Дополнительно **R6** подтвердил обход кэша `verifiedPins` по метаданным (mtimeMs:size без
хеширования содержимого): в процессе с прогретым кэшем подменённый корень принимается и
выполняется мутация; полный PASS этим вектором остановлен холодным кэшем дочерних
процессов (зафиксировано честно, отдельная слабость P3).

Исправление закрыло только первоначальный демонстрационный сценарий: исходный R1 и
файловую подмену без изготовления закрепления (N04–N06, N11 — fail-closed
`TRUST_ROOT_KEY_SUBSTITUTION`). Дизайн-документ исправления сузил исходную A2
(«не исполняет код от имени пользователя») — сужение **не принято**, модель угроз ради
ACCEPT не изменялась.

## Состав проверки

1. **Основная матрица без изменения атакующей логики**: исходный R1 (без правок) +
   N01–N12 + P01 на SHA 41043ad. Итог: R1 отклонён; N01–N09, N11, N12 — NO_TRUSTED_PASS;
   **N10 — ложный trusted PASS (сохраняется)**; P01 — legitPass, идемпотентный reconcile,
   повторной мутации нет.
2. **Новые проверки R5–R8** (DPAPI Same-SID, кэш PIN, конфигурация, перезакрепление) —
   см. `WP08-QWEN-F1-RETEST.md` §4.

4. **F2/F3 после изменений**: F2 — disposition подтверждён кодом (криптография не менялась,
   независимость fingerprint не заявляется); F3 — отложено, заголовок в доверенном POST

## Условия повторной ре-приёмки

1. Внешний якорь доверия (отдельная учётная запись/сервисный SID, TPM/HSM или внешнее
   хранилище ожидаемых keyId), недоступный процессам того же SID и записи файлов A2.
2. Закрепление идентичности разрешённого trustRoot владельцем вне корня; отказ публичного
   API принимать произвольный корень с валидным самозакреплением.
3. `resealTrustRootPin` со сверкой против внешнего ожидаемого keyId.
4. Кэш закреплений с хешированием содержимого либо его отсутствие.
5. Исходная A2 не сужается; остаточные риски принимаются владельцем явно, отдельным решением.
6. R-D матрица: инструмент и сценарии опубликованы в дереве продукта, воспроизводимы из
   опубликованного SHA.

Повторная проверка будет выполнена по тем же сценариям R1, N01–N12, P01, R5–R8 без
изменения атакующей логики.
