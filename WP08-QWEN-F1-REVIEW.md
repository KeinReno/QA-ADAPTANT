## Критерии приёмки исправления (что будет проверяться)

Исправление должно делать подмену публичных ключей trust root **обнаруживаемой и fail-closed в рамках A2**
(противник пишет любые файлы runDir и trust root, кроме приватных ключей; запускает процессы того же SID;
без инъекции/отладки/DPAPI-извлечения). Допустимые механизмы (один или комбинация):

1. **Внешнее закрепление keyId** owner/anchor вне перезаписываемого противником trust root: доверенный канал
   передачи (fork IPC от процесса, создавшего корень), отдельный SID/каталог с ACL, либо подпись `ready.json`
   ключом, чья публичная часть закреплена внешне. Самопроверка keyId по файлу внутри того же корня
   (текущее поведение `loadTrustRoot`, identity.mjs:87-98) исправлением НЕ считается.
2. **Обнаружение подмены на всём пути к PASS:** `loadTrustRoot`/preflight/подписант/наблюдатель должны
   отказывать (типизированный код, fail-closed), а не продолжать с подменёнными ключами.
3. **Легитимный путь не сломан:** корень, созданный штатным keygen, проходит; легитимный прогон даёт PASS;
   отзыв/перевыпуск ключей штатно работает.
4. **Модель угроз обновлена явно:** остаток «подмена корня до старта» (WP-00 04-THREAT-MODEL.md:18) либо
   закрыт механизмом, либо остаётся принятым — но тогда перечень остатков A1–A3 (WP08-REMEDIATION-ARCHITECTURE.md §3)
   обязан явно его перечислять, и для Dev/ЦИЗ требуется отдельное решение владельца (отдельный SID /
   внешнее закрепление). Документация без механизма — не исправление.
5. **Контракты:** изменения через `docs/changes`, замороженные пути 0.1 не затронуты; расширения не молча.

## Протокол проверки (будет выполнен по предъявлении ревизии)

Расширенный негативный набор по WORKPACK QWEN-SECURITY-GATE §4 подготовлен в `repro/neg/`
(12 атак N01–N12 + положительный контроль P01 + агрегатор `run-all.mjs`): замена только
`owner.pub` / только `anchor.pub` / только `ready.json`; согласованная замена всех трёх;
подмена до загрузки; между загрузкой и стартом; во время Recovery; подложный approval от чужого
owner; поддельный Anchor от чужого signer; подмена конфигурации ожидаемых ключей (аргументы API,
env, указатель trustRoot); несанкционированная ротация; повреждение/отсутствие закрепления.
Каждая атака фиксирует достигнутую границу, фактический verdict, состояние trusted observer и
количество бизнес-мутаций. Исходные R1–R4 сохранены как базовые доказательства и не переписываются;
набор переносим между ревизиями (относительные импорты, SHA из git). Базовый прогон набора на
SHA `1a510a5` — `repro/logs/neg-baseline/`.

   `ready.json`, точки входа Control/подписанта/наблюдателя; карта «где именно подмена теперь отвергается».
3. Перенос `repro/` в check-worktree (скрипты самодостаточны, относительные импорты `../packages/...`,
   только %TEMP% и локальный стенд 127.0.0.1). При изменении API — минимальная адаптация скрипта,
   зафиксированная в журнале; смысл атаки R1 не менять.
4. **Негативный прогон R1 против исправления** (исходный скрипт без изменения атакующей логики):
   ожидается fail-closed — `rootTakeover` обнаружен, подложный прогон НЕ достигает
   `observeTrusted {trusted:true, passed:true, verdict:PASS}`; `falseTrustedPass=false`. Журнал сохранить.
4a. **Негативный набор N01–N12 против исправления** (`node repro/neg/run-all.mjs`): ни одна атака

5. **Позитивный контроль:** легитимный мир (штатный keygen) — principal верифицируется, легитимный
   прогон PASS; R2/R3/R4 при затронутых поверхностях — повторить.
6. Полный gate `npm test` на SHA исправления (ожидание: 0 fail; число тестов может вырасти — зафиксировать).
7. Проверка п.4 критериев: обновлены ли WP-00/A1–A3 и docs/changes; не затронут ли Stable 0.1.
8. Вердикт **ACCEPT / REJECT / BLOCKED** с доказательствами (журналы, файлы-строки, SHA).
   Исправление не принимаю единолично как исполнитель — только независимое ревью; продуктовый код не правлю.

## Что НЕ будет принято как исправление

- Косметика: подпись `ready.json` тем же ключом, чья публичная часть лежит в том же перезаписываемом корне
  (атакующий перегенерирует всё связкой, как в R1).
- ACL «текущий пользователь» на trust root — не отделяет того же SID (R-04/R-06, подтверждено аудитом).
- Только документация/переформулировка остатка без механизма обнаружения — допустимо лишь как явное
  решение владельца о принятии риска, но тогда статус F1 остаётся «принятый остаток», не «исправлено»,
  и Dev/ЦИЗ-приёмка требует отдельного решения.
- Отказ только в одном месте (например, только в keygen) при обходе через прямую запись файлов в корень.
