# WP08-V2-QWEN-THREAT-ANALYSIS — модель угроз и атакующие сценарии против TAS

Пакет: `arch/wp08-trust-foundation-v2`, SHA f99573322a1be7955926b82c92253c559d6c0b33.
Реализации нет; все оценки ниже — против **проектной модели**, не против исполненного кода.
Классификация: `ЗАКРЫТО-ПРОЕКТом` (механизм обоснован, нужны реализация+тест),
`ТРЕБУЕТ-РЕАЛИЗАЦИИ` (механизм не специфицирован до конца), `ТРЕБУЕТ-РЕШЕНИЯ-ВЛАДЕЛЬЦА`,
`НЕ-ЗАКРЫТО` (пробел в архитектуре, обязательное изменение до реализации).
PASS ни одному сценарию не ставится: ничего не исполнялось.

## 1. Этап C — модель угроз

Исходная A2 сохранена без сужения (BOUNDARIES-V2 §1 явно отвергает сужение 41043ad):
запись файлов runDir/trustRoot (кроме приватных ключей), свои процессы того же Windows SID,
публичные локальные каналы, HTTP; без отладки/инъекции в доверенные процессы и без
извлечения приватных ключей через DPAPI. A1/A3 сохранены. Это соответствует требованию
заказчика и подтверждается текстом пакета.

Новые предпосылки (BOUNDARIES-V2 §3) и их обеспечимость на целевых Windows:

| Предпосылка | Обеспечимость |
|---|---|
| ACL ProgramData для SID службы | Обеспечима штатными ACL; требует корректной установки (S1) и проверки отсутствия user-writable путей, включая junction/symlink (историческая N11/junction) |
| UAC/elevated нельзя получить без согласия админа | Верно для не-админ пользователя; secure desktop защищает согласие. Для owner=админ — деградация (см. §3) |
| A2 не админ и не отлаживает TAS | Это и есть граница; при owner=админ предпосылка ложна → условие развёртывания M09 |
| Наименьшие привилегии службы; ключ анкера DPAPI LocalMachine + права службы | DPAPI LocalMachine сам по себе НЕ граница (любой локальный процесс распечатывает); граница = ACL файла ключа (только SID службы) + контекст службы. Требуется явная фиксация M07; SID службы — выделенная виртуальная учётка, не LocalSystem |
| Реестр: запись только TAS, чтение через IPC | Обеспечима ACL; монотонность версий и подписи записей — M06 |

## 2. Этап B — атакующие сценарии против TAS (T01–T11 по заданию)

### T01. Grant по поддельному approval
TAS сверяет подпись approval с enrolled ownerKeyId; A2 не извлекает owner-ключ →
подделка подписи невозможна. **Однако** легитимный approval — публичный документ в
A2-читаемом trustRoot; потребление в 0.2 хранится файлом в trustRoot (approval.mjs:89),
привязка runId — по первому потребителю (approval.mjs:269). V2 не специфицирует хранение
потребления в TAS. Атакующий читает непотреблённый approval и первым запрашивает grant
со своим runId (те же operation/fixture/environment — публичны) → TAS принимает подлинную
подпись → grant выдан атакующему; легитимный прогон теряет approval.
Классификация: подделка подписи — ЗАКРЫТО-ПРОЕКТом; **replay-гонка потребления — НЕ-ЗАКРЫТО (M02)**.

### T02. Grant по чужому runId
Grant привязан к runId/approvalId; approval привязывает operation/inputs/fixture/environment.
TAS должна сама сверять bundle-хеши с approval и фиксировать пару approvalId→runId
атомарно в защищённом состоянии. Без M02 — T01. Классификация: ТРЕБУЕТ-РЕАЛИЗАЦИИ (M02).

### T03. Подмена evidenceHead
evidenceHead вычисляется из файлов runDir (A2-writable). Grant «привязан к evidence head»,
но момент фиксации и источник head не специфицированы; аттестации независимых чтений в
пакете нет. Атакующий изготавливает согласованные evidence-файлы → head сходится →
TAS подписывает заявление о фактах, которых не было.
Классификация: **НЕ-ЗАКРЫТО (M01)** — центральный пробел.

### T04. Поддельное происхождение Verification Worker
Worker запускается Control (пользовательский SID). Атакующий поднимает процесс того же
SID с тем же кодом. Единственное отличие по пакету — PID/creationTime pinning, явно
«не граница доверия». Криптографической аутентификации Worker (эфемерный ключ в памяти,
приватный канал, созданный TAS, регистрация при spawn) нет.
Классификация: **НЕ-ЗАКРЫТО (M01)**: TAS должна сама создавать Worker/канал и принимать
аттестацию только по нему.

### T05. Использование настоящего grant другим процессом того же SID
Grant — bearer-токен в пользовательском IPC. Если grant попадает в runDir/файлы/аргументы
процессов — A2 его читает и использует. Пакет не запрещает запись grant в user-writable
места и не привязывает grant к каналу, созданному TAS. PID-pinning не граница.
Классификация: ТРЕБУЕТ-РЕАЛИЗАЦИИ → **НЕ-ЗАКРЫТО без M04** (grant только в памяти
доверенных процессов и в TAS, привязка к сессии канала TAS; перехват без инъекции —
вне A2, но запись grant на диск делает атаку внутренней для A2).

### T06. Повторное использование grant
Одноразовость + TTL заявлены. Потребление grant должно фиксироваться в защищённом
состоянии TAS (не в файлах runDir). Классификация: ЗАКРЫТО-ПРОЕКТом при условии M02;
тест N14 обязателен.

### T07. Повторный запрос подписи
Одноразовый grant → второй anchor-sign отказ. Состояние подписи — в TAS.
Классификация: ЗАКРЫТО-ПРОЕКТом (M02), тест обязателен.

### T08. Race между cancel, verification и anchor
Пакет не специфицирует сериализацию жизненного цикла grant в TAS. Cancel должен
атомарно отзывать grant до подписи; иначе окно cancel→sign даёт анкер отменённому прогону.
Классификация: ТРЕБУЕТ-РЕАЛИЗАЦИИ (M02: транзакционная сериализация в TAS), race-тест обязателен.

### T09. Подпись без фактических независимых чтений
То же, что T03/T04: без аттестации readSetSha256 и byte-identity candidate TAS подписывает
любые согласованные файлы. Классификация: **НЕ-ЗАКРЫТО (M01)**.

### T10. Анкер через публичный IPC
Read-only глаголы отделены от anchor-*; anchor требует grant. Но при T01/T05 публичный
IPC становится оракулом подписи. Дополнительно: канал не аутентифицирует сервер (T12).
Классификация: ТРЕБУЕТ-РЕАЛИЗАЦИИ (M01/M03/M04): anchor-sign только по каналу
аттестованного Worker + grant + проверка evidence.

### T11. Восстановление с устаревшим grant
Recovery через TAS заявлен; TTL grant и проверка registryVersion должны отвергать
устаревшие grant; recovery не повторяет мутацию. Классификация: ЗАКРЫТО-ПРОЕКТом
(M02), тест обязателен (N07/recovery + устаревший grant).

## 3. Новые сценарии, направленные непосредственно на TAS (T12–T20)

### T12 (N15). Поддельный TAS: named pipe squatting
Процесс того же SID создаёт канал с именем TAS раньше службы / после её остановки и
отвечает клиентам как TAS. Аутентификации сервера канала в пакете нет.
Классификация: **НЕ-ЗАКРЫТО (M03)**: клиент проверяет SID процесса-владельца канала
(GetNamedPipeServerProcessId → токен == SID службы) и подпись ответов ключом TAS,
закреплённым в устанавливаемом продукте (вне user-writable путей).

### T13 (N19). Владелец = локальный администратор
Same-SID атакующий получает права админа: запись в registry (ACL «Admins»), изменение
конфигурации службы (бинарь → код от SID службы), чтение DPAPI LocalMachine, отладка.
Граница TAS полностью деградирует. Пакет признаёт это (BOUNDARIES §3–4).
Классификация: **ТРЕБУЕТ-РЕШЕНИЯ-ВЛАДЕЛЬЦА + обязательное условие развёртывания (M09)**:
не-админ учётная запись владельца, либо TPM/HSM, либо явное принятие остатка.
UAC сам по себе не защита от процесса уже-админа.

### T14 (N17). Enrollment из подменённого корня
`enroll --root <путь>` читает owner.pub/anchor.pub из A2-writable каталога. Без внешней
сверки fingerprint владелец регистрирует ключи атакующего. Пакет требует офлайн-подтверждение.
Классификация: ЗАКРЫТО-ПРОЕКТом при жёстком исполнении M05 (подтверждение обязательно,
не пропускаемо, не подделываемо процессом того же SID; повторный enroll отказ;
adminSignature отдельной роли). Тест обязателен.

### T15 (N18). Откат/подмена Registry и восстановление из backup
Атакующий A2 (не-админ) не может писать в registry (ACL). Откат версии/удаление —
отказ fail-closed. Требуется монотонность registryVersion + high-water mark + подпись
владельца на каждой записи и на backup. Админ-откат — вне A2 (T13).
Классификация: ЗАКРЫТО-ПРОЕКТом (M06), тесты обязательны.

### T16 (N20). Исторические анкеры до v2
Ключ анкера 0.2 жил в пользовательском пространстве (DPAPI CurrentUser) — его подлинность
постфактум недоказуема (R5-эпоха). «Чтение старых артефактов поддерживается» не должно
означать доверенный PASS для legacy-прогонов. Классификация: **ТРЕБУЕТ-РЕШЕНИЯ-ВЛАДЕЛЬЦА
+ M08**: legacy-статус без доверенного PASS, либо переаттестация владельцем fingerprint
исторических ключей; автопринятие запрещено.

### T17. Подмена файлов по enrolled-пути (R1/N04–N06 на v2)
Атакующий подменяет owner.pub/anchor.pub по enrolled-пути. TAS сверяет подписи с
**enrolled ownerKeyId/anchorKeyId из реестра**, а не с утверждениями файлов → отказ.
Классификация: ЗАКРЫТО-ПРОЕКТом (механизм реестра), тесты R1/N04–N06 обязательны.
Важно: TAS должна разрешать путь из реестра физически (junction/symlink-проверка).

### T18. Выбор trustRootId клиентом
Клиент передаёт произвольный trustRootId → нет записи → TRUST_ROOT_NOT_ENROLLED.
trustRootId — непрозрачный идентификатор реестра, не путь. Несколько enrolled-корней —
явный выбор из реестра. Классификация: ЗАКРЫТО-ПРОЕКТом (R7'/N10в), тест обязателен.

### T19. Fake TAS-провайдер в приёмке
Harness-fake для unit/CI не должен выбираться через env/config в приёмочных прогонах
(A2 пишет конфиг). Классификация: ТРЕБУЕТ-РЕАЛИЗАЦИИ (M11): fake только тестовый,
приёмка — против реальной службы.

### T20. TAS как оракул верификации
Read-only verify-* возвращает результат проверки документов атакующего. Утечка —
бит валидности, не ключи; подделка подписи всё равно требует owner-ключ. Прямой обход
не даёт; комбинировать с T01 для подбора не требуется (подпись не подобрать).
Классификация: ЗАКРЫТО-ПРОЕКТом (при M01/M02), низкий приоритет.

## 5. Ответ на главный вопрос приёмки

По текущему тексту пакета: **ДА** — произвольный процесс пользовательского SID может
получить ложный trusted PASS, не изменяя реестр и не извлекая ключи (цепочка A:
replay-гонка approval → grant → fabricated evidence → anchor; цепочка B: fake pipe).
После внесения M01–M04 (аттестация Worker + защищённое состояние потребления/grant +
аутентификация канала + запрет grant в user-writable) ответ должен стать «НЕТ»;
это подлежит проверке исполненными сценариями на v2-SHA, а не декларацией.
