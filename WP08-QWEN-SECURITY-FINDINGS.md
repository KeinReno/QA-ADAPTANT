Аудитор: Qoder / Qwen4-Max-Preview, WP-08 INDEPENDENT CORE SECURITY AUDIT.
Ревизия: `1a510a5d5929534d400dc965f58c78cf468bc270`. Ветка `audit/wp08-qwen-independent-core`, worktree `qwen-core-audit`.
Модель: A1–A3 (утверждена владельцем, WP08-REMEDIATION-ARCHITECTURE.md §10) + доверенные базы WP-00.
Классификация проекта: P0 — ложный PASS/вторая мутация/второй verdict; P1 — обход разрешения или утечка секрета; P2 — ограничение с эксплуатационным следствием; P3 — наблюдение.

## QWEN-F1 — подмена публичных ключей корня доверия даёт ложный доверенный PASS (E2E воспроизведено)

- **Severity:** P2 (принимаемый остаточный риск WP-00; пробел формулировки A1–A3). НЕ новый P0 против утверждённой модели: WP-00 04-THREAT-MODEL.md:18 явно принимает подмену корня до старта; Luna уже отмечала это как P3 «граница модели». Для Dev/ЦИЗ — недопустимо (P0-эквивалент при переносе без отдельного SID/внешнего пиннинга).
- **Файлы/строки:** packages/trust/identity.mjs:79-98 (readPublic/loadTrustRoot: ready.json не подписан, keyId сверяется только с самим файлом); identity.mjs:162-184 (createTrustRoot, ACL текущего пользователя); docs/wp-00/04-THREAT-MODEL.md:18,65; docs/harness/WP08-REMEDIATION-ARCHITECTURE.md:33-46 (A2 разрешает запись в trust root; остаток перечисляет только инъекцию/DPAPI).
- **Условия эксплуатации:** противник в рамках A2 — запись файлов в trust root (кроме приватных ключей), свои процессы того же Windows SID, HTTP. НЕ требует извлечения DPAPI, инъекции, прав отладки. Подмена выполняется ДО старта прогона (после загрузки ключей в память подмена не действует — ключи загружаются один раз).
- **Воспроизведение:** `node repro/r1-trustroot-substitution.mjs` (только %TEMP% и локальный стенд). Шаги: легитимный корень жертвы → атакующий создаёт СВОЙ корень (свои ключи, своя DPAPI-обёртка) → копирует owner.pub/anchor.pub/ready.json в trust root жертвы → подписывает свои principal/environment-record/approval → запускает startTrusted со своим стендом и своим anchorKeyPath.
- **Ожидаемо (по модели):** обнаружение подмены не обещается (WP-00:18); защита — права на файл ключа.
- **Фактически:** `rootTakeover=true`; документы жертвы отвергнуты (`APPROVAL_SIGNATURE_INVALID`); `forgedRun.verdict=PASS`; `observeTrusted: trusted=true, passed=true, verdict=PASS, anchorId=anchor-3e8f4475-…`; стенд жертвы не мутировал (`victimStandMutations=0`), мутация ушла на стенд атакующего (`rogueStandMutations=1`). Exit 0.
- **Корневая причина:** три файла публичных ключей — единственная точка целостности всей цепочки; ready.json не подписан и не привязан к чему-либо вне trust root; ACL текущего пользователя не защищает от того же SID (что и есть предпосылка A2).
- **Замечание о модели:** A2 явно разрешает запись в trust root, но перечень остаточных рисков A1–A3 (§3) перечисляет только инъекцию/отладку/DPAPI/запуск доверенных бинарников. Подмена публичных ключей возможна БЕЗ DPAPI-извлечения и в перечень не попала. WP-00:65 (DPAPI доступен тому же SID) и A2 (DPAPI-извлечение вне модели) также расходятся. Требуется явное решение владельца: либо перечислить подмену корня в остатках A1–A3, либо ввести внешний пиннинг keyId.
- **Рекомендация (не исправлялось аудитором):** (1) явно перечислить компрометацию корня до старта в остаточных рисках A1–A3; (2) для Dev/ЦИЗ — отдельный Windows SID для Verification/подписанта и пиннинг keyId вне trust root (конфиг поставки/внешнее хранилище); (3) рассмотреть подпись ready.json ключом owner с внешним пиннингом — обнаружение, а не предотвращение.

## QWEN-F2 — проверки envBefore/envAfter доверенного Verification тавтологичны; fingerprint среды не покрыт подписью

- **Severity:** P3 (мёртвая проверка; вводит в заблуждение о полноте контроля среды). Ложного PASS в рамках A2 не даёт: идентичность среды подтверждается подписанной аттестацией (environmentId/generation/standKeyId/pid/portOwnerPid), а не fingerprint.
- **Файлы/строки:** apps/verification/trusted-worker.mjs:194-198 (environmentRead синтезируется из context.environmentId и manifest.environment.fingerprint), :67 и :134-135 (сравнение fingerprint манифеста с самим собой); комментарий :183-184 документирует намеренность; adapters/local/server.mjs (stand-response не включает fingerprint).
- **Условия эксплуатации:** не атака, а дефект assurance: среда, изменившая fingerprint без смены поколения/ключа/процесса, не детектируется доверенным Verification. На локальном стенде это fault `changedEnvironment`.
- **Воспроизведение:** `node repro/r2-fingerprint-tautology.mjs`. Полный доверенный прогон со стендом `fault:'changedEnvironment'`; инструментация http.createServer только в процессе теста.
- **Ожидаемо:** проверка среды должна либо реально читать /environment, либо быть удалена/задокументирована как неприменимая.
- **Фактически:** `verdict=PASS` при `standFingerprintAfter=…-changed` ≠ fingerprint манифеста; `environmentReadsAfterPost=0` (продуктовых GET /environment после POST нет); `tautologyConfirmed=true`. Exit 0.
- **Корневая причина:** при переносе Verification на аттестованный канал (R-B) реальный environmentRead заменён синтезом из манифеста, но проверки envBefore/envAfter оставлены и создают видимость контроля.
- **Рекомендация:** удалить тавтологичные сравнения либо покрыть fingerprint подписью stand-response/аттестации и читать его реально; привести fault-семантику changedEnvironment к единой для legacy и trusted путей.

## QWEN-F3 — доверенный POST не отправляет x-qa-run-id: одноразовость мутации на стенде не активна на доверенном пути

- **Severity:** P3 (defense-in-depth). В рамках A2 Bearer недоступен противнику (память процессов/IPC), поэтому самостоятельного вектора ложного PASS нет; одноразовость обеспечена Control (consumeDispatch + единственный Worker + единственный POST).
- **Файлы/строки:** apps/browser/trusted-worker.mjs:88-107 (postMutation: только authorization, idempotency-key, x-qa-stand-challenge); adapters/local/server.mjs:152-161,203 (привязка к runId и one-shot только при x-qa-run-id).
- **Условия эксплуатации:** обладатель Bearer (вне A2) может выполнять повторные POST одним токеном, пока стенд жив; стенд не ограничит мутацию одним runId.
- **Воспроизведение:** `node repro/r3-one-shot-inactive.mjs`.
- **Ожидаемо:** доверенный путь использует все доступные защиты стенда.
- **Фактически:** без x-qa-run-id два POST одним токеном → 201/201, `mutationCount=2`; с x-qa-run-id второй → 403 `token_revoked`, `mutationCount=1`; в исходнике postMutation заголовок отсутствует (`workerSendsRunIdHeader=false`). Exit 0.
- **Корневая причина:** run-binding стенда сделан opt-in ради совместимости с замороженным Worker 0.1 (отчёт R-B §1.1); доверенный Worker его не включает.
- **Рекомендация:** добавить `x-qa-run-id: job.runId` в postMutation доверенного Worker (аддитивно, стенд уже поддерживает; поведение 0.1 не меняется).

## QWEN-F4 — legacy named-pipe подписант: регистрация ключа любым соединением того же SID, sign без lease; теоретический front-running регистрации

- **Severity:** P3 (тестовая поверхность; продуктовые доверенные входы signerPipe отвергают). В продуктовой fork-топологии канал приватный (A3), регистрация чужому процессу недоступна.
- **Файлы/строки:** packages/trust/anchor-signer.mjs:518-568 (startAnchorSigner, pipe без сужения ACL), :463-466 (register-verification-key разрешён только inProcess), :352 (lease обязателен только !inProcess), :155-167 (регистрация first-wins: повтор с другим ключом/pid/nonce отвергается), :171-187 (WMI: родитель=controlPid, образ, живость); apps/control/trusted.mjs:770-790 (assertSignerConfigured/signerFor отвергают signerPipe).
- **Условия эксплуатации:** кто-то явно запустил startAnchorSigner (тесты/внешний вызов). Противник того же SID подключается к pipe. Регистрация first-wins: если противник зарегистрирует СВОЙ ключ+nonce с pid РЕАЛЬНОГО Verification Worker раньше Control, WMI-проверка пройдёт (реальный процесс жив, родитель верный, образ верный), и подписант примет аттестацию, подписанную ключом противника. Окно — между стартом Worker и регистрацией Control; требует знания runId (runDir читаем) и pid (WMI доступен того же SID).
- **Воспроизведение:** `node repro/r4-pipe-signer-lease.mjs` (базовые свойства): регистрация чужого ключа произвольным подключением принята (`foreignKeyRegistration.accepted=true`); sign без lease не отклоняется по lease (`leaseNotRequiredInPipeMode=true`, отказ уже на привязке runDir). Front-running в полной мере не воспроизводился (тестовая поверхность, вне продуктового потока) — зафиксирован как теоретический/UNVERIFIABLE-в-продукте.
- **Ожидаемо:** legacy-режим не должен ослаблять инварианты, если когда-либо будет использован вне тестов.
- **Фактически:** lease в pipe-режиме не требуется; регистрация доступна любому соединению того же SID; единственная защита происхождения — WMI (defense-in-depth).
- **Корневая причина:** режим совместимости сохранён для существующих тестов (отчёт R-A §5.3); приватность канала в нём не обеспечивается.
- **Рекомендация:** пометить startAnchorSigner как test-only (или удалить после перевода тестов на anchorKeyPath); не использовать pipe-режим в продуктовых сценариях; при сохранении — требовать lease и в inProcess.

## QWEN-F5 — WMI-идентичность процесса: гранулярность и окно повторного использования PID

- **Severity:** P3 (defense-in-depth, не единственная привязка — так и заявлено R-A §5.2).
- **Файлы/строки:** packages/trust/anchor-signer.mjs:48-78 (queryProcess: CreationDate строкой, ParentProcessId, ExecutablePath, commandLineSha256), :171-187 (проверка суффикса командной строки `apps\verification\trusted-worker.mjs`, node.exe), :372 (при наличии receipt повторная WMI-проверка пропускается — она выполнена при подготовке receipt).
- **Условия эксплуатации:** теоретическое окно PID-reuse между запросом WMI и использованием; суффикс командной строки допускает другой каталог с тем же именем файла (но родитель обязан быть Control, что противник без инъекции не подделает). CreationDate в строковом формате WMI имеет ограниченную гранулярность.
- **Воспроизведение:** не воспроизводилось (требует управления планировщиком PID/инъекции — вне A2). Source-анализ: проверка родителя (process.ppid подписанта = Control) криптографически не усиливаема в локальной 0.2; session nonce + регистрация по приватному IPC — основная привязка, WMI — дополнительная.
- **Ожидаемо/фактически:** соответствует заявленному дизайну; криптографическая привязка обеспечена nonce+ключом, WMI лишь повышает планку.
- **Рекомендация:** для Dev/ЦИЗ — отдельный SID и защищённый IPC вместо WMI; в локальной 0.2 оставить как есть, документируя гранулярность.

## QWEN-F6 — cancelTrusted не проверяет роль: любой активный principal с совпадающим SID может отменить прогон

- **Severity:** P3 (отказ в обслуживании в безопасную сторону; ложного PASS/мутации не создаёт).
- **Файлы/строки:** apps/control/trusted.mjs:848-857 (principalFact + SID, без role-проверки; комментарий P2-02).
- **Условия эксплуатации:** любой процесс того же SID с валидной карточкой principal (роли operator/runner/agent и т.п.) может вызвать cancelTrusted для чужого runId.
- **Воспроизведение:** source-анализ; поведение согласуется с тестами P2-02 (отмена без approval). Отмена блокирует PASS (cancel.request), т.е. эффект — только срыв прогона.
- **Ожидаемо:** роль для отмены может требоваться политикой владельца.
- **Фактически:** роль не проверяется; отмена доступна любому аутентифицированному principal того же SID.
- **Рекомендация:** решить владельцу, нужна ли роль (например operator/owner) для отмены; задокументировать текущее поведение как намеренное.

## QWEN-F7 — expectedKeyId в verifyWithTrustedWorker само-referential

- **Severity:** P3/informational (компенсировано).
- **Файлы/строки:** apps/control/trusted.mjs:214-240 (RESULT: аттестация проверяется ключом из того же сообщения `expectedKeyId: publicKey.keyId`).
- **Условия эксплуатации:** противник, способный подменить IPC-сообщение RESULT (вне A3 — канал приватный, создан Control), мог бы прислать свой ключ+аттестацию. Компенсация: session nonce известен только Control и Worker (IPC), подписант требует регистрации ключа по своему приватному каналу и совпадения nonce; WMI-происхождение.
- **Воспроизведение:** source-анализ; в рамках A1–A3 недостижимо.
- **Рекомендация:** не требуется; при желании — сверять keyId с зарегистрированным у подписанта до приёма RESULT (дополнительный round-trip).
