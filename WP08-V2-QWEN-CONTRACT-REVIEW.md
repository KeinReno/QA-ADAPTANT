# WP08-V2-QWEN-CONTRACT-REVIEW — контракты и совместимость Trust Foundation v2

Пакет: f99573322a1be7955926b82c92253c559d6c0b33. Фактический API сверен по 41043ad.
Реализации нет; оценка — проектная.

## 1. База архитектурной ветки (несоответствие)

Ветка `arch/wp08-trust-foundation-v2` основана на `59d82d4` — общем предке с линиями
1a510a5 и 41043ad (merge-base проверен). Дерево ветки **не содержит текущий 0.2-код**
(apps/control, packages/trust в актуальном состоянии, тесты 0.2). Относительно 41043ad
diff показывает −20602 строки — это отсутствие 0.2, а не удаление.

Последствие: пакет описывает изменения поверх API, которого в своей ветке не имеет.
До реализации обязателен ребейз/перенос пакета на текущую продуктовую линию (M10);
контрактные дельты должны сверяться с фактическим 41043ad (что и сделано в этом ревью).
Само по себе это не дефект архитектуры, но блокер начала реализации в текущей ветке.

## 2. Публичные Trust API (V2-CONTRACT-CHANGES §1)

| Изменение | Оценка |
|---|---|
| Удаление `trustRoot`/`secretsDir`/`anchorKeyPath` из публичных вызовов; `trustRootId?` | Правильно закрывает R7/N10в. Требование: trustRootId — непрозрачный идентификатор реестра, НЕ путь; путь разрешает TAS из реестра с физической проверкой (junction/symlink). Опциональность допустима только при единственном enrolled-корне; при нескольких — явный выбор |
| Удаление `loadTrustRoot` из публичного экспорта | Правильно: источник истины — TAS. Внутренние вызовы TAS читают enrolled root и сверяют keyId с реестром |
| Удаление `resealTrustRootPin` | Правильно закрывает R8. Ротация — только elevated CLI + внешний ожидаемый keyId (M05/M06) |
| `createTrustRoot` остаётся для тестов/bootstrap | Допустимо при явном правиле: созданный корень НЕ доверенный до enrolled; автопринятие запрещено (M08). Тестовый harness не должен enrolled-ить корень без владельца |
| Поведение без TAS/enrolled → `TRUST_ROOT_NOT_ENROLLED` | Fail-closed — правильно; тихое принятие старого корня запрещено |

Пробелы контрактов (обязательные дополнения):
- **Verification Grant v1** не содержит полей привязки к аттестованному Worker/каналу
  (verificationKeyId, attestationSha256, sessionId канала TAS). Без них grant — bearer-токен
  для любого процесса (T05). M01/M04.
- **Anchor Receipt extension** (`trustRegistryVersion`, `anchorKeyId`, 0.2.2) — аддитивно,
  корректно. Требуется также ссылка на аттестацию (verificationAttestationSha256) —
  иначе анкер не доказывает независимые чтения (T03/T09). M01.
- **IPC-протокол TAS v1**: коды ошибок перечислены; отсутствует аутентификация сервера
  канала клиентом и защита от pipe squatting (T12). M03.
- **Потребление approval/grant**: контракт не фиксирует, что состояние потребления живёт
  в защищённом состоянии TAS, а не в файлах trustRoot/runDir. В 0.2 потребление — файл
  в trustRoot (approval.mjs:89) — A2-writable. M02.

## 3. Взаимодействие с ADAPTANT 0.3

Feature-ветка 0.3 не меняется; интеграция через стабильные публичные контракты
(bundle, approval, anchor, evidence) и аддитивные поля. Оценка: корректно при условии,
что 0.3 не вызывает удалённые экспорты (`loadTrustRoot`, `resealTrustRootPin`) и не
передаёт пути корня. Требуется проверка фактических вызовов 0.3 на этапе S3 (M10) —
в пакете заявлено, но не показано. Схемы 0.1 не переписываются — подтверждено текстом
пакета; фактическая неизменность проверяется gate `schemas` на реализации.

## 4. Исторические подписанные анкеры

Пакет: «исторические PASS проверяются по registryVersion, действовавшей на момент выпуска»;
«чтение старых артефактов поддерживается». Проблема: анкеры до v2 подписаны ключом,
жившим в пользовательском пространстве (DPAPI CurrentUser, 0.2). Подлинность этого ключа
постфактум недоказуема — в эпоху 41043ad он мог быть подменён (R5/R8). Наличие файла
анкера не делает исторический PASS достоверным.

Требование (M08): legacy-анкеры получают статус «неподтверждённое происхождение ключа»;
доверенный PASS для них НЕ выдаётся автоматически; допустима переаттестация владельцем
(офлайн-подтверждение fingerprint исторического anchorKeyId с внесением в реестр как
legacy-записи с явной пометкой). Решение владельца обязательно.

## 5. Версионирование Registry, rollback, backup

- Append-only журнал версий с подписями владельца/админа — правильный механизм.
- Требуется (M06): монотонный registryVersion; TAS отвергает записи/состояния с версией
  ниже high-water mark; high-water mark хранится в защищённом состоянии TAS (не в файле,
  доступном A2); каждая запись подписана владельцем; восстановление из backup — только
  с подписью владельца и версией не ниже high-water mark; удаление/повреждение реестра —
  fail-closed (`TAS_REGISTRY_UNAVAILABLE`).
- Откат к старой версии реестра пользователем невозможен (ACL + монотонность).
  Админ-откат — вне A2, условие развёртывания M09.
- «Запрет автоматического принятия старого Trust Root»: подтверждён fail-closed без
  enrolled-записи; legacy trust-pin.json игнорируется (MIGRATION §2.4) — правильно.

## 6. Stable 0.1

Пакет заявляет неизменность Stable 0.1 (отдельная ветка/тег). Дерево архитектурной ветки
фактически является 0.1-эпохой (база 59d82d4) — это не затрагивает тег Stable 0.1, но
подчёркивает необходимость M10. На реализации: gate `schemas` + тесты 0.1 зелёные,
форматы ключей/approval/anchor/evidence 0.1 не переписываются (аддитивные 0.2.2 поля).

## 7. Тестовый harness-провайдер TAS

MIGRATION §3: in-memory fake за тем же контрактом для unit/CI; «fake не должен
использоваться в приёмочных прогонах». Требуется жёсткое разделение (M11): fake недоступен
в production-коде/приёмке, не выбирается через env/config (A2-writable), приёмка — только
против реальной службы. Иначе приёмка может быть обманута подменой провайдера.

## 8. Итог по контрактам

Направление контрактных изменений корректно и совместимо с 0.1/0.3 при аддитивности.
Обязательные дополнения до реализации: M01 (аттестация в grant/receipt), M02 (защищённое
состояние потребления), M03 (аутентификация канала), M04 (запрет grant в user-writable),
M06 (монотонность/backup), M08 (legacy-анкеры), M10 (ребейз + проверка вызовов 0.3),
M11 (разделение fake/real).
