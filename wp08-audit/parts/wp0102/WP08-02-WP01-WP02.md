## 2. WP-01 Identity

### 2.1 `packages/trust/windows-sid.mjs` — доверенный SID вызывающего

- Ответственность: получить SID текущего Windows-токена и сравнить с карточкой Principal.
- Контракт: `isValidSid` (форма `S-1-…-…`), `currentUserSid()` (только win32, иначе `CALLER_UNAUTHENTICATED`), `assertCallerSid(principal, sid)`.
- Входы/выходы: вход — токен процесса ОС; выход — строка SID / код отказа.
- Граница доверия (windows-sid.mjs:13-27): PowerShell `[Security.Principal.WindowsIdentity]::GetCurrent().User.Value`, резерв — `whoami /user`; оба читают токен процесса, а не аргументы. SID из JSON/окружения не участвует.
- Обработка ошибок: пустой/невалидный результат → `CALLER_UNAUTHENTICATED` (fail-closed, windows-sid.mjs:26).
- Скрытые side effects: запуск `powershell.exe` и `whoami.exe`; оба ищутся по PATH (см. OBS-WP01-05).
- Соответствие WP-00: `docs/wp-00/02-TRUST-ARCHITECTURE.md:152` — «SID, присланный аргументом функции, игнорируется»; на доверенном входе (`apps/control/trusted.mjs:264-276`) SID всегда берётся из `currentUserSid()`.
- Проверено: независимый тест `wp0102-identity.test.mjs` — совпадение с независимым `whoami /user`, устойчивость к подмене `USERNAME/USERDOMAIN/SID/QA_SID/WINDOWS_SID/windowsSid` в дочернем процессе; карточка с чужим SID отвергается; у runner без SID — `PRINCIPAL_UNKNOWN`.
- Дефектов не найдено. Наблюдение OBS-WP01-05 (PATH).

### 2.2 `packages/trust/identity.mjs` — ключи, подпись, trust root

- Ответственность: генерация Ed25519-ключей, DPAPI-обёртка, domain separation, подпись/проверка документов, загрузка/создание trust root.
- Контракт:
  - домены owner: `approval, revocation, principal, environment-record`; anchor: `anchor-statement` (identity.mjs:9-10,33-37);
  - `signTrustedDocument` сверяет `keyId` с приватным ключом (identity.mjs:56-58), `verifyTrustedDocument` выбирает ключ по домену и сверяет `keyId`/`signatureAlgorithm`/`signature` (identity.mjs:62-71);
  - `assertPrincipal` — статус/роли/несовместимости/SID (identity.mjs:39-51);
  - `loadTrustRoot` — `owner.pub`, `anchor.pub`, `ready.json` с совпадающими keyId (identity.mjs:87-98);
  - `createTrustRoot` — физическое разрешение путей, запрет repo/вложенности/runDir, ключи через `wx`, `ready.json` последним, откат созданных файлов при ошибке (identity.mjs:126-184).
- Граница доверия: приватные ключи — только в `secrets`, DPAPI CurrentUser + ACL; Control получает только public-ключи; якорный подписант — отдельный процесс по named pipe (identity.mjs:100-116,158-193; `docs/wp-00/02-TRUST-ARCHITECTURE.md:40,73`).
- Обработка ошибок: коды `TRUST_STORE_UNAVAILABLE`, `APPROVAL_SIGNATURE_INVALID`, `CALLER_UNAUTHENTICATED`, `ROLE_DENIED`, `CONTRACT_INVALID`; fail-closed.
- Скрытые side effects: DPAPI/PowerShell процессы; ACL-ужесточение каталога секретов; `ready.json` — последняя точка «корень готов».
- Соответствие WP-00: частичная инициализация не даёт годного корня (`docs/wp-00/03-CONTRACT-PROPOSALS.md:90`; `docs/wp-00/05-IMPLEMENTATION-ROADMAP.md:66`).
- Проверено (01-identity-tests.log, 9/9, EXITCODE 0): `ready.json` отсутствует/частичный/с подменённым keyId → отказ; повторная инициализация поверх частичного корня отвергается и не затирает байты; `fault:'after-owner'` откатывает созданные файлы; частичный корень не чинится автоматически.
- Наблюдения: OBS-WP01-01 (ACL trust root), OBS-WP01-02 (нет целостностной привязки trust root), OBS-WP01-04 (sign не связывает домен с назначением ключа; границу держат verify/commit).

## 3. WP-02 Approval

### 3.1 Контракт и реализация (`packages/trust/approval.mjs`)

- Ответственность: закрепление подписанного approval, отзыв, единственный расход dispatch, проверка состояния, привязки к замороженным входам.
- Закрепление (approval.mjs:164-178,235-248): CREATE_NEW (`wx`) + `fsync` + повторное чтение; существующее имя не перезаписывается, совпадение по `digest` идемпотентно; иное содержимое → `CONTRACT_INVALID`.
- Расход (approval.mjs:301-364): guard-lock на `approvalId` (`guards/<id>.lock`, spin ≤5 с), проверка approval/отзыва/срока/привязок, затем CREATE_NEW `consumption/<id>.json`, `fsync`, повторное чтение, сверка `bodySha256/runId/inputsHash`, три повторные проверки отзыва (до создания, после создания, после записи). ACK (`ack:true`) только при полном совпадении. Повтор имени: полный файл с тем же runId → `ack:false/APPROVAL_CONSUMED`; другой runId → `APPROVAL_REPLAY`; неполный → `CONSUMPTION_INCOMPLETE`.
- Отзыв (approval.mjs:279-299): подпись owner, `wx` в `revocations/<id>.json`, тот же guard; второй отзыв не перезаписывает файл.
- Состояния (approval.mjs:147-154): `incomplete → consumed → revoked → not-yet-valid → expired → issued`; для уже израсходованного approval отзыв/просрочка не отменяют ACK, но и не дают второй.
- Часы: для dispatch — только часы процесса (`trustedNow`, approval.mjs:156-162); `now` из запроса не принимается.
- Привязки (approval.mjs:123-133): operation id/version/`digest(operation)`, inputs, scenarioContentSha256, fixtureId, environmentId+generation, effects, resource.
- Граница доверия: проверка канонического документа с ключом домена owner; вызывающий обязан передать аутентифицированный SID; `trust`-объект — in-process (подтверждение F-04, `docs/harness/WP-06-REPORT.md:66`).
- Скрытые side effects: guard-lock, файлы approvals/consumption/revocations, DPAPI не используется; `request.fault` — тестовые хуки в продуктивном модуле (OBS-WP02-01).
- Обработка ошибок: все отказы кодами; брошенные системные ошибки заворачиваются в `CONSUMPTION_INCOMPLETE/TRUST_STORE_UNAVAILABLE` (fail-closed).

## 4. Интеграция с Control (проверено чтением кода)

- `apps/control/trusted.mjs:264-276`: `startTrusted` сам загружает trust root (`loadTrustRoot`) и читает SID (`currentUserSid()`); `sid`/trust из аргументов не берутся.
