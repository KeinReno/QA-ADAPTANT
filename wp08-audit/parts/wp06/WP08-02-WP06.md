## 1. Итог

Доверенный маршрут **Identity → Approval → Environment → Policy → PEP → Consumption → Intent → ACK → POST → Verification → Candidate → Anchor → Verdict**
в коде присутствует и в целом упорядочен правильно. Ключевые негативные инварианты («нет POST до ALLOW», «нет секрета
до ALLOW», «нет PASS без анкера», «нет второго POST», «нет второго terminal verdict», «нет бизнес-мутации через
observe/reconcile», «нет обхода Trusted через start/adopt», «произвольный SID не аутентификация») **подтверждены**
статически и независимыми запусками.

Однако найдены дефекты публикации и восстановления:

* **F-WP06-01 (P1)** — аварийное окно «анкер записан, terminal-choice/verdict ещё нет» (V-07) не восстанавливается:
  `reconcileTrusted` падает `CANDIDATE_CONFLICT`, валидный анкерованный PASS-candidate остаётся недостижим для автоматического
  восстановления, terminal-verdict не пишется. Это прямое нарушение критерия матрицы V-07 и правила «потеря уже подтверждённого
  коммита — REJECT пакета».
* **F-WP06-02 (P2)** — при ошибке `trust.publish()` внутри свежего прогона `run()` ловит её в общем `catch` и через
  `persistVerdict` пишет терминальный verdict **напрямую, без terminal-choice**, теряя реальный результат Verification.
  Нарушает инвариант 07-ARCHITECTURE «в evidence нет verdict, пока нет `terminal-choice.json`».
* **F-WP06-03 (P3)** — доверенные терминальные отказы (BLOCKED на T-A, CANCELED до intent) публикуются старым путём
  0.1, без terminal-choice; `observeTrusted` на них возвращает `inconsistent/INTEGRITY_ERROR`, то есть доверенный
  интерфейс чтения не умеет представить легитимный отказ.
* **F-WP06-04 (P3)** — ошибки публикации в `reconcile()/reconcileTrusted()` не нормализуются в terminal-состояние:
  вызывающий получает внутренние коды `CANDIDATE_CONFLICT`, `TERMINAL_CHOICE_INCOMPLETE`, `ANCHOR_CONFLICT`;
  при конкурентных reconcile оба процесса завершаются отказом.

Ложного PASS, второго POST и второго terminal verdict получить не удалось ни статически, ни в трёх независимых
сценариях атак/аварий. Обнаруженные дефекты — fail-closed, но нарушают контракт восстановления и публикации.

### F-WP06-01 — P1: восстановление после «анкер записан, verdict ещё нет» (V-07) не работает, анкерованный PASS теряется

* **SHA:** 07c21c4
* **Файлы/строки:** `apps/control/trusted.mjs:190–214` (publish), `apps/control/run.mjs:546–566` (reconcile → verifyAndPersist),
  `apps/control/run.mjs:443–466`, `packages/trust/anchor.mjs:251–284` (publishCandidate), `packages/trust/anchor.mjs:298–311`.
* **Нарушенный инвариант/критерий.** Матрица V-07: «Анкер уже записан, процесс падает до verdict → восстановление:
  дописывается ровно один verdict, совпадающий с candidate»; 02-TRUST-ARCHITECTURE.md:213 «Выбор anchor есть, verdict
  в evidence нет → дописать ровно тело выбранного candidate; бюджет заново не разыгрывать»; правило WP-08 «потеря уже
  подтверждённого коммита — REJECT».
* **Сценарий.** Доверенный прогон доходит до публикации, anchor-signer записывает `anchor-statement` в trust root,
  процесс Control гибнет до `terminal-choice.json`/verdict (краш в окне получения подписи). На диске:
  durable `runDir/trust/candidate.json` = PASS, файл анкера, `terminal-choice.json` НЕТ, verdict НЕТ.
  Восстановление: `reconcileTrusted` (или `startTrusted`) → `reconcile` → `verifyAndPersist` заново запускает
  Verification с `browserUncertain: true` (run.mjs:443–455, 565) → новый verdict INCONCLUSIVE/WORKER_LOST →
  `trust.publish` читает choice (нет) → `publishCandidate(INCONCLUSIVE)` → durable candidate уже PASS →
  `CANDIDATE_CONFLICT`.
* **Ожидаемо/фактически.** Ожидаемо: выбранный/годный candidate публикуется ровно одним verdict (PASS), бюджет не
  разыгрывается заново, POST=0 новых. Фактически: `reconcileTrusted` **отвергает** с `CANDIDATE_CONFLICT`,
  verdict не пишется; состояние остаётся `candidate-ready` (`PUBLICATION_PENDING`), автоматическое восстановление
  невозможно ни через `startTrusted`, ни через `reconcileTrusted`; повторные попытки воспроизводят ту же ошибку.
  Для контраста: вручную собранный `terminal-choice=anchor` (сценарий V-11 ниже) публикует PASS корректно —
  дефект именно в отсутствии автовосстановления состояния `candidate-ready`.
* **Доказательство.** `wp08-audit/evidence/wp06/publication.log`: строки V-07-подготовка (exitCode 42; durable
  PASS-candidate + anchorId; verdicts=0), FAIL «V-07 (критерий матрицы): дописан ровно один verdict…»,
  INFO F-WP06-01 (`CANDIDATE_CONFLICT`), POST=1 не вырос. Запуск: `wp08-audit/tests/wp06-publication.mjs`,
  EXITCODE:1 (единственный провал — этот критерий).
* **Минимальное направление фикса.** `publish()` не должен писать новый candidate, если durable candidate уже есть:
  при choice=null и существующем candidate — переиспользовать candidate и его (возможно, уже подписанный) анкер,
  запросить подпись заново только в бюджете; `reconcile` не должен пересчитывать Verification для состояния
  `candidate-ready`; `CANDIDATE_CONFLICT` при существующем годном candidate не должен быть фатальным.
  Дополнительно — регрессионный тест «crash между anchor и choice».

### F-WP06-02 — P2: ошибка `trust.publish()` в `run()` catch пишет terminal verdict напрямую, без terminal-choice

* **SHA:** 07c21c4
* **Файлы/строки:** `apps/control/run.mjs:384–396` (catch → `persistVerdict`), `apps/control/run.mjs:603–610`,
  `apps/control/trusted.mjs:190–237` (publish бросает TERMINAL_CHOICE_INCOMPLETE/CANDIDATE_CONFLICT/…).
* **Нарушенный инвариант.** 07-ARCHITECTURE-DECISIONS.md:77 «в evidence нет verdict, пока нет `terminal-choice.json`»;
  02-TRUST-ARCHITECTURE.md:191–196 (состояние terminal = единственный verdict, равный выбранному candidate);
  V-12 «имя выбора занято и не заменено» (соблюдено), но терминальный исход не должен обходить choice.
* **Сценарий.** Свежий доверенный прогон; до момента публикации в `runDir/trust/terminal-choice.json` появляется
  неполное тело (авария/внешний писатель). `publish()` → `readTerminalChoice` бросает TERMINAL_CHOICE_INCOMPLETE →
  `run()` `catch` → `persistVerdict` пишет INCONCLUSIVE/WORKER_LOST (а не реальный результат Verification и не
  choice-исход). Аналогично любая ошибка publish (CANDIDATE_CONFLICT/ANCHOR_*) в этом окне ведёт к прямой записи verdict.
* **Ожидаемо/фактически.** Ожидаемо: PASS не публикуется, публикация блокируется, состояние остаётся
  `candidate-ready/anchor-held` без terminal-verdict до явного разрешения (как V-12). Фактически: PASS не
  публикуется (хорошо), но терминальный INCONCLUSIVE/WORKER_LOST **записан без choice**, реальный верифицированный
  результат отброшен, `observeTrusted` → inconsistent/INTEGRITY_ERROR; причина скрыта (`reasonCode=WORKER_LOST`).
* **Доказательство.** `wp08-audit/evidence/wp06/publication.log`: блок INJ (итог INCONCLUSIVE/WORKER_LOST,
  choice не перезаписан, «терминальный verdict дописан напрямую, без валидного выбора исхода»). V-12-сценарий:
  `reconcileTrusted` в этом же состоянии, наоборот, отвергает TERMINAL_CHOICE_INCOMPLETE и verdict НЕ пишет —
  поведение двух входов расходится.
* **Минимальное направление фикса.** Для прогонов с `trust` не вызывать `persistVerdict` из `run()` catch:
  либо пробрасывать ошибку публикации как `PUBLICATION_PENDING/INTEGRITY_ERROR` без записи verdict, либо закрывать
  только через `trust.publish` (после проверки choice/candidate/анкера).

### F-WP06-03 — P3: доверенные отказы публикуются старым путём 0.1 (verdict без terminal-choice); observeTrusted их не представляет

## 9. Статические наблюдения (INFO, не дефекты уровня пакета)

1. **F-04-подобный in-process мост.** `assertOldEntryOptions` (run.mjs:19–23) не отвергает `options.trust`; старые
   функции принимают внутренний контекст trust. Внешний CLI (apps/control/cli.mjs) его не передаёт; это граница
   R-04 (тот же SID/процесс), заявлена в WP-06-REPORT F-04. Для внешнего входа обхода нет.
2. **Тестовый hook в доверенном входе.** `startTrusted`/конфиг передают `fault` в `run`; fault
   `tamperSnapshotBeforeBrowser` (run.mjs:256–259) изменяет замороженный снимок после PDP. Это тестовая инъекция,
   доступная только программному вызывающему; в продуктивном CLI отсутствует. Рекомендация: не пробрасывать `fault`
   через доверенный публичный вход в релизе.
3. **Fixture binding до preflight.** `claimFixture` (run.mjs:232) выполняется до `trust.preflight` (235–241):
   отказанный доверенный старт всё же занимает привязку fixture для своего runId. Освобождение возможно
   (`canReleaseFixture`, 139–144: без mutation-evidence привязка переносится в quarantine), поэтому отказанный
   прогон не блокирует чужие навсегда; тем не менее это side effect до ALLOW.
4. **cancelTrusted** (trusted.mjs:299–306) проверяет только карточку субъекта и SID, не связывает отмену с
   approval/runId/issuer. В границах одного Windows-пользователя (R-04) это DoS-возможность, не эскалация прав.
5. **Секрет стенда.** Bearer не пишется в runDir (проверяется `rt-01` поставки); в моих прогонах секрет жил только
   в env Browser/Verification. Утечек в evidence не обнаружено.
6. **Документация.** WP-06-REPORT.md:26 «9/9» и список T-01…T-09 не соответствуют фактическим 13 тестам
   (`tests/trust-integration.test.mjs`); это дефект отчётности (P3), фактические тесты зелёные.
