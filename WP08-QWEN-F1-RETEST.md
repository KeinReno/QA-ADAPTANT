# WP08-QWEN-F1-RETEST — независимая повторная проверка исправления QWEN-F1

- Продукт: KAIDEN QA ADAPTANT 0.2, ветка исправления `fix/wp08-trust-root-hardening`.
- Проверяемый SHA: **41043ad50eb80948c0aa146ab18748998b5bce05**.
- Базовый SHA аудита: `1a510a5d5929534d400dc965f58c78cf468bc270`.
- Проверка выполнена в отдельном check-worktree `qwen-f1-check` (detached HEAD 41043ad),
  продуктовые файлы не изменялись (деревья `packages`/`apps`/`adapters` совпадают с HEAD;
  единственное изменение `package-lock.json` от `npm install` возвращено к исходному состоянию).
- Атакующая логика исходных R1 и N01–N12/P01 не изменялась. Все прогоны — только `%TEMP%`
  и локальный стенд 127.0.0.1; настоящий Dev/ЦИЗ не подключался.
- Роль: финальный независимый проверяющий, не соавтор исправления.

## Решение: REJECT

Исправление закрывает первоначальный демонстрационный сценарий R1 (подмена трёх публичных
файлов без изготовления закрепления), но **не устраняет QWEN-F1 по существу**: в исходной
модели A2 воспроизводятся три независимых пути к ложному доверенному PASS (R5, R7, R8).
Критерий заказчика: «Если хотя бы один из R5–R8 воспроизводит ложный trusted PASS в исходной
A2 — REJECT». Выполнен с запасом: три из четырёх.

## 1. Исходная модель A2 (не переопределяется)

`docs/harness/WP08-REMEDIATION-ARCHITECTURE.md:36` (ревизия 41043ad, текст не изменён исправлением):

> **A2.** Противник в локальной 0.2 может: писать любые файлы в runDir и trust root (кроме
> приватных ключей), поднимать свои процессы того же Windows SID, подключаться к публичным
> локальным каналам, делать HTTP-запросы. Противник **не** имеет прав отладки/инъекции в
> доверенные процессы и не извлекает ключи через DPAPI.

Дизайн-документ исправления `TRUST-ROOT-HARDENING-DESIGN.md` §2 подменяет модель:
«не исполняет код от имени пользователя». Это сужение **не принимается**: исходная A2 явно
включает собственные процессы того же SID. Заказчик прямо запретил принимать эту замену.
Все проверки R5–R8 классифицированы относительно исходной A2.

Ключевое разграничение: **создание нового DPAPI-конверта для собственных данных** процессом
того же SID — не «извлечение ключей через DPAPI» и остаётся внутри A2. Раскрытие чужой
DPAPI-обёртки — исключено исходной A2 (зонд R8-B классифицирован отдельно как вне модели).

## 2. Механизм исправления (source-ревью)

`packages/trust/identity.mjs` (41043ad):

- `createTrustRoot` дополнительно пишет `trust-pin.json`: тело {schemaVersion 0.2.1, domain
  `trust-root-pin`, trustRootPathHash, ownerKeyId, anchorKeyId}, запечатанное
  `protectSync` (DPAPI CurrentUser) от `canonical(body)`.
- `loadTrustRoot` после проверки `ready.json` вызывает `verifyTrustPin`: распечатывает конверт,
  сверяет pathHash и keyId; отказы `TRUST_ROOT_UNPINNED` / `TRUST_ROOT_PIN_INVALID` /
  `TRUST_ROOT_KEY_SUBSTITUTION`.
- Кэш `verifiedPins` (Map в модуле): ключ — sha256 пути корня, сигнатура —
  `mtimeMs:size` четырёх файлов **без хеширования содержимого**.
- `resealTrustRootPin({trustRoot, secretsDir})`: читает `owner.pub` **из того же корня**,
  раскрывает `secretsDir/owner.key`, требует совпадения keyId, перезакрепляет.
- `dpapi.mjs`: добавлены `protectSync`/`unprotectSync` (PowerShell, DPAPI CurrentUser).

Структурные слабости (подтверждены воспроизведением ниже):

1. DPAPI CurrentUser не разделяет процессы одного Windows SID: любой процесс пользователя
   может изготовить валидный конверт. Источник истины — профиль ОС, доступный атакующему
   на запись новых данных, а не только чтение чужих ключей.
2. Закрепление самореферентно: корень подтверждает сам себя; ожидаемые keyId не закреплены
   нигде вне корня. `resealTrustRootPin` сравнивает две стороны, обе подконтрольны атакующему
   после подмены `owner.pub`.
3. Идентичность разрешённого `trustRoot` нигде не закреплена: публичный API принимает любой
   каталог с валидным самозакреплением, включая только что созданный корень атакующего.
4. Кэш доверия к метаданным (`mtimeMs:size`) обходится восстановлением mtime (utimes) —
   файловая операция в пределах A2.

## 4. Новые проверки R5–R8

### R5 — DPAPI CurrentUser под тем же SID: изготовление закрепления (ВНУТРИ A2)

Сценарий `repro/reacceptance/r5-dpapi-sid-pin-forge.mjs`:

1. Легитимный мир жертвы; корень атакующего с собственными ключами (своя DPAPI-обёртка).
2. Дочерний процесс того же SID (подтверждено: SID родителя и ребёнка совпадают) изготавливает
   `trust-pin.json` для **пути корня жертвы** с keyId атакующего: `canonical(body)` →
   `protectSync` (продуктовый DPAPI). Приватные ключи жертвы не читаются и не извлекаются.
3. A2-запись: подмена трёх публичных файлов + изготовленного закрепления.
4. `loadTrustRoot` принимает корень (`FORGED_PIN_ACCEPTED`), полный доверенный прогон
   ключами атакующего в хранилище жертвы.

Результат: **ложный trusted PASS** (observer: trusted=true, passed=true, verdict=PASS,
anchor опубликован; мутация на стенде атакующего 1, на стенде жертвы 0).
Классификация: создание нового конверта своим процессом того же SID — внутри исходной A2.
Закрепление не является границей против исходной A2. Журнал: `reacceptance-suite.json` → R5.

### R6 — кэш закреплений: подмена с восстановлением mtimeMs и размеров (ВНУТРИ A2)

Сценарий `repro/reacceptance/r6-pin-cache-mtime.mjs`:

1. Корень жертвы загружен (кэш прогрет); mtime нормализован до целых секунд
   (utimes на Windows теряет субмикросекундную точность исходных значений — первая попытка
   восстановления исходных mtime дала расхождение ~0.7 мкс и кэш-промах; нормализация
   устраняет артефакт точности, атакующая логика та же).
2. Подмена трёх публичных файлов (размеры совпадают по построению), восстановление тех же
   целых секунд mtime; `metadataRestored=true`.
3. Повторная загрузка в том же процессе: **кэш-промах не происходит** — `loadTrustRoot`
   возвращает ключи атакующего (`PIN_CACHE_BYPASS_METADATA`).
4. Контроль: отдельный процесс с холодным кэшем отвергает тот же корень
   (`TRUST_ROOT_KEY_SUBSTITUTION`).
5. Полный прогон в процессе с прогретым кэшем: мутация на стенде атакующего выполнена (1),
   но дочерние процессы (worker/signer) начинают с холодным кэшем и отвергают корень —
   анкер не опубликован, verdict INCONCLUSIVE (`EVIDENCE_MISSING`), observer trusted=true,
   passed=false.

Результат: обход `verifyTrustPin` по метаданным **воспроизведён** в процессе с прогретым
кэшем; полный ложный trusted PASS этим вектором не достигнут (честная фиксация: холодный
кэш дочерних процессов останавливает цепочку). Дефект кэша — самостоятельная слабость
(P3): сигнатура доверия без хеширования содержимого + мутация под подменённым корнем.
Журнал: `r6-pin-cache-mtime.rerun.json`.

### R7 — конфигурация: полностью новый корень атакующего (ВНУТРИ A2)

Сценарий `repro/reacceptance/r7-config-new-root.mjs`:

1. Корень жертвы не изменяется (рекурсивный снимок файлов до/после совпадает,
   `victimRootUntouched=true`).
2. Публичный `startTrusted` получает `trustRoot`, указывающий на корень атакующего,
   созданный штатным `createTrustRoot` (валидное DPAPI-закрепление «из коробки»).
3. Полный доверенный прогон ключами атакующего; результат публикуется в хранилище жертвы.

Результат: **ложный trusted PASS** (observer: trusted=true, passed=true, PASS, anchor
опубликован; мутация на стенде атакующего 1, жертвы 0). Это тот же вектор, что N10в
базовой матрицы; исправление его не затрагивает.

Ответ на вопрос ре-приёмки: идентичность разрешённого `trustRoot` должна быть закреплена
**вне корня и вне досягаемости атакующего** — конфигурация владельца/политика запуска
(allowlist путей и ожидаемых keyId), закреплённая внешним якорем (отдельная учётная запись
сервиса, TPM/HSM или эквивалент). Самозакрепление каждого корня этого не заменяет.
Журнал: `r7-config-new-root.rerun.json`.

### R8 — несанкционированное перезакрепление resealTrustRootPin (ВНУТРИ A2, часть A)

Сценарий `repro/reacceptance/r8-reseal-sid.mjs`:

- Часть A (чистая A2: запись файлов + свой процесс): подмена трёх публичных файлов, затем
  штатная процедура `resealTrustRootPin({trustRoot: корень жертвы, secretsDir: секреты атакующего})`.
  Процедура читает `owner.pub` **из подменённого корня** и сравнивает с ключом из переданного
  `secretsDir` — обе стороны сравнения подконтрольны атакующему. Результат:
  **перезакрепление принято** (`RESEAL_ACCEPTED_ATTACKER_SECRETS`), `loadTrustRoot` принимает
  ключи атакующего, полный доверенный прогон даёт **ложный trusted PASS** (observer:
  trusted=true, passed=true, PASS; мутация атакующего 1, жертвы 0). Извлечение ключей жертвы
  не требуется. «Санкционированная ротация» принимает чужие ключи.
- Часть B (зонд возможности, ВНЕ исходной A2): процесс того же SID раскрывает DPAPI-обёртку
  `owner.key` жертвы (`unwrapped=true`, выведен только keyId) и перезакрепляет неповреждённый
  корень. Исходная A2 явно исключает извлечение ключей через DPAPI, поэтому это не новое
  нарушение A2, а демонстрация: «владение owner.key» опирается ровно на то же допущение
  DPAPI, без отдельной границы. Материал ключа не выводился и не сохранялся.

Журнал: `reacceptance-suite.json` → R8.

## 5. Классификация по фактическому воздействию

  изготовление ложного доверенного PASS в локальной 0.2 в пределах исходной A2, теперь тремя

  мутация под подменённым корнем; полный PASS остановлен холодным кэшем дочерних процессов.

## 9. Требования к приемлемому исправлению (рекомендации, не реализация)

1. Внешний якорь доверия: отдельная учётная запись/сервисный SID для Verification и
   anchor-signer, либо TPM/HSM, либо внешнее хранилище ожидаемых keyId — вне досягаемости
   процессов того же SID и записи файлов A2.
2. Идентичность разрешённого trustRoot (путь + ожидаемые ownerKeyId/anchorKeyId) должна
   закрепляться владельцем вне корня; публичный API не должен принимать произвольный корень
   с валидным самозакреплением.
3. `resealTrustRootPin` обязан сверяться с внешним ожидаемым keyId, а не с `owner.pub` из
   того же (потенциально подменённого) корня.
4. Кэш закреплений должен хешировать содержимое файлов (или отсутствовать); метаданные
   mtime/size не являются границей доверия.
5. Модель угроз не сужать: остаточный риск «код того же SID» должен быть закрыт внешним
   якорем либо явно принят владельцем как отдельное решение, а не подменён в дизайн-документе.
