## РЕШЕНИЕ: REVISION REQUIRED

Архитектура перспективна и принципиально правильнее DPAPI-pin: вынос источника доверия
в службу с отдельным SID и защищённый реестр корректно закрывают R5/R7/R8/R6 и N10в
**проектным механизмом**. Однако в опубликованном виде архитектура **не отвечает
утвердительно на главный вопрос приёмки**:

> Может ли произвольный процесс пользовательского SID получить ложный trusted PASS,
> обманув TAS, даже если он не может изменить её защищённый реестр и приватные ключи?

**По текущему тексту — ДА, может** (цепочка A ниже). Поэтому ARCHITECTURE ACCEPT
не выдаётся. Фундаментального обхода, несовместимого с исходной A2, нет: пробелы
закрываются конкретными проектными механизмами (M01–M08 в REQUIRED-CHANGES), часть
из которых уже была спроектирована в WP08-REMEDIATION-ARCHITECTURE (verification-attestation,
приватный канал доверенного родителя). Это REVISION REQUIRED, а не ARCHITECTURE REJECT.

## Цепочка A — ложный trusted PASS без записи в реестр и без извлечения ключей (в пределах A2)

1. Approval — **публичный подписанный документ**, хранящийся в trustRoot (A2-читаемый).
   В 0.2 потребление approval фиксируется файлом в trustRoot
   (`packages/trust/approval.mjs:89`, `storeFile(trustRoot, 'consumption', approvalId)`),
   привязка к runId — по первому потребителю (`approval.mjs:269`, `APPROVAL_REPLAY`).
   V2-документы **не указывают**, где хранится потребление в TAS.
2. Атакующий (процесс того же SID) читает легитимный ещё не потреблённый approval и
   первым отправляет TAS `verify-approval` со своим runId и тем же operation/fixture/
   environment (все значения публичны и привязаны в approval). Подпись владельца
   подлинная — TAS её принимает. Гонка потребления: первый запрос выигрывает.
3. TAS выдаёт `verificationGrant` (runId/approvalId/evidenceHead/TTL). Происхождение
   Verification Worker удостоверяется только «pinning по PID/creationTime … как
   дополнительный сигнал, **не как граница доверия**» (ARCHITECTURE §4). Криптографической
   аутентификации Worker в пакете нет; аттестация независимых чтений не упоминается.
4. Атакующий пишет в свой runDir согласованные файлы evidence (A2: запись любых файлов
   runDir) и просит `anchor-sign`. TAS сверяет grant + evidenceHead, вычисленный из
   **файлов атакующего**, и подписывает statement своим ключом анкера. Факт реальных
   независимых чтений не проверяется — TAS становится сервисом подписи заявлений клиента.
5. `observeTrusted` через TAS читает runDir атакующего, проверяет анкер ключом TAS и
   enrolled ownerKeyId — всё сходится → **ложный trusted PASS**. Реестр не изменён,
   приватные ключи не извлечены, отладка/инъекция не использованы.

Побочный эффект шага 2: легитимный прогон теряет approval (DoS + перехват авторизованной
мутации). Даже при атомарном потреблении в TAS атакующий может выиграть гонку.

## Цепочка B — поддельный TAS (named pipe squatting, в пределах A2)

Клиенты подключаются к именованному каналу TAS. Процесс того же SID может создать канал
с тем же именем раньше службы (или после её остановки) и отвечать на `verify-*`/`anchor-*`
как «TAS». В пакете **нет аутентификации сервера канала клиентом**. Без проверки SID
процесса-владельца канала и подписи ответов ключом TAS, закреплённым в устанавливаемом
продукте, поддельный канал выдаёт grant и «анкеры» → ложный trusted PASS. Закрывается M03.

## Этап A — проверка доверенной границы TAS (9 пунктов)

| # | Проверка | Оценка проекта |
|---|---|---|
| 1 | Выделенный Windows SID службы | Механизм корректен: пользовательский процесс не может имперсонировать SID службы. Требуется явно: отдельная виртуальная учётная запись (NT SERVICE\KAIDEN-TAS) или выделенный пользователь, **не LocalSystem**. Реализация + тест |
| 2 | ACL Registry и ключевого материала | Применимы, но схема «SYSTEM+Admins+TAS» даёт администраторам запись. Для границы против A2 (не-админ) достаточно SYSTEM+TAS; админ-деградация — обязательное условие развёртывания (M09). ACL на ключ анкера = только SID службы (M07) |
| 3 | Writable-пути из пользовательского SID | Registry/ключи в ProgramData с закрытым ACL — вне записи A2 (не-админ). Каталог установки продукта не user-writable. runDir/trustRoot остаются writable: TAS не должна принимать их содержимое как истину о фактах исполнения — **это и есть пробел M01/M02** |
| 4 | DPAPI LocalMachine | **Не граница**: любой локальный процесс может распечатать LocalMachine-конверт. Защита = ACL на файл ключа (только SID службы) + контекст службы; DPAPI LocalMachine — лишь defense-in-depth. В пакете указано «+ права службы», но требуется явная фиксация (M07) |
| 5 | Локальные административные права пользователя | Граница **не обеспечивается**: same-SID атакующий = админ → запись в registry (ACL Admins), конфигурация службы, DPAPI LocalMachine, отладка. Пакет честно признаёт деградацию (§3 BOUNDARIES). Обязательное условие развёртывания: не-админ учётная запись владельца, либо TPM/HSM, либо явное принятие остатка владельцем (M09) |
| 6 | Первоначальный enrollment | Проект правильно требует внешнюю сверку fingerprint владельцем (офлайн). Требуется жёстко: enrollment никогда не принимает ключи из файлов как истину без подтверждения; повторный enroll отвергается; подтверждение не подделываемое процессом того же SID (secure desktop UAC; при owner=админ — см. п.5). M05 |
| 7 | Обновление и откат Registry | Append-only + подписи владельца/админа спроектированы. Требуется: монотонный registryVersion, отказ отката к старой версии, high-water mark, восстановление из backup только с подписью владельца и проверкой версии. M06 |
| 8 | Выбор чужого Trust Root через публичные API | Закрыто проектом: `trustRoot`/`secretsDir`/`anchorKeyPath` удаляются, только enrolled `trustRootId`; новый корень без записи → `TRUST_ROOT_NOT_ENROLLED`. Требует реализации и теста (R7'/N10в) |
| 9 | Разграничение TAS/Control/Verification/пользователь | Частично: «ни одно значение из пользовательского процесса не становится доверенной истиной о ключах» — верно для ключей, но **не выполнено для фактов исполнения** (evidenceHead из runDir). Происхождение Worker не аутентифицировано. M01/M04 |

**Перенос дефекта:** исходный дефект (источник доверия в зоне записи A2) НЕ перенесён
в новый файл конфигурации для идентичности ключей — реестр защищён ACL и недоступен A2.
Но он **частично перенесён в поток фактов исполнения**: evidenceHead/grant опираются на
данные пользовательского каталога без аттестации. Это исправимо в рамках архитектуры (M01).

## Почему не ACCEPT и не REJECT

- Не ACCEPT: главный вопрос имеет положительный ответ для атакующего (цепочки A и B);
  известные блокеры (R5/R7/R8) закрыты проектом, но появились новые блокеры уровня
  «TAS как сервис подписи произвольных заявлений» — до их закрытия реализацию начинать
  нельзя в текущем виде.
- Не REJECT: направление (отдельный SID + защищённый реестр + enrollment владельцем)
  совместимо с исходной A2 и устраняет первопричину F1; пробелы закрываются конкретными
  механизмами, уже известными по WP08-REMEDIATION-ARCHITECTURE (аттестация, приватный
  канал доверенного родителя, проверка паритета). Фундаментального несовместимого обхода нет.

## Условия перехода к ARCHITECTURE ACCEPT

Внести в пакет M01–M08 (обязательные до реализации), M09 (решение владельца + условие
развёртывания), M10 (ребейз на текущую линию продукта), M11–M12 (до приёмки реализации).
Повторная архитектурная приёмка — по обновлённому SHA пакета; сценарии T01–T20
(THREAT-ANALYSIS) должны быть закрыты проектным механизмом с явной трассировкой.
