## Блокеры до начала реализации

### M01. Происхождение Verification и аттестация фактов (центральный пробел)
Требование: TAS не подписывает заявления, происхождение которых не установлено.
- TAS сама создаёт Verification Worker (или приватный канал, созданный TAS, с регистрацией
  эфемерного ключа аттестации при spawn); Worker не держит долгоживущих ключей.
- Worker выполняет независимые чтения и подписывает аттестацию:
  {runId, manifestSha256, candidateSha256, readSetSha256 (evidenceId+artifact.sha256+kind),
  verificationKeyId, pid, startedAt, nonce}.
- Anchor-sign принимается только по каналу аттестованного Worker; TAS сверяет
  byte-identity candidate, readSetSha256 с durable evidence и полный паритет проверок
  (assertEvidenceRefs, assertTerminalEvidence, validateVerdictCoverage — аналог
  AUD-P0-01 из WP08-REMEDIATION-ARCHITECTURE).
- Grant/Receipt расширяются: verificationKeyId, verificationAttestationSha256, sessionId.
Критерий: сценарии T03/T04/T09/T10 (fabricated evidence, поддельный Worker, подпись без
чтений, анкер через публичный IPC) невозможны в проектной модели; трассировка в матрице.
Закрывает: T03, T04, T09, T10, T20; главный вопрос приёмки.

### M02. Защищённое состояние потребления approval/grant и жизненный цикл
Требование: потребление approval и grant живёт только в защищённом состоянии TAS
(не в файлах trustRoot/runDir, которые пишет A2).
- Атомарная фиксация пары approvalId→runId при первой выдаче grant; повторный запрос
  с другим runId → APPROVAL_REPLAY; гонка первого потребителя документирована и
  ограничена: grant выдаётся только в контексте исполнения, созданного TAS (с M01),
  что лишает перехватчика возможности изготовить аттестованные факты.
- Grant одноразовый, TTL, отзыв при cancel атомарно до подписи; сериализация
  cancel/verification/anchor в TAS.
Критерий: T01 (replay-гонка), T02, T06, T07, T08, T11 закрыты проектом; race-тесты
обязательны на реализации.

### M03. Аутентификация сервера IPC (защита от поддельного TAS)
Требование: клиент удостоверяется, что говорит с реальной TAS.
- Проверка SID процесса-владельца канала (GetNamedPipeServerProcessId → токен == SID
  службы KAIDEN-TAS).
- Ответы TAS подписаны ключом службы; публичный ключ закреплён в устанавливаемом
  продукте (каталог установки, не user-writable), не в runDir/trustRoot/config пользователя.
Критерий: T12/N15 (pipe squatting) невозможен; тест с поддельным каналом обязателен.

### M04. Grant не покидает доверенную зону
Требование: grant не записывается в user-writable места (runDir, trustRoot, файлы,
аргументы/окружение пользовательских процессов); передаётся только по каналу, созданному
TAS, и хранится в памяти доверенных процессов и TAS. PID/creationTime — вспомогательный
сигнал, не граница.
Критерий: T05 (перехват grant процессом того же SID без инъекции) невозможен; тест обязателен.

### M05. Enrollment и ротация: внешняя сверка, неподделываемое подтверждение
Требование: enroll/rotate никогда не принимают ключи из файлов как истину без
подтверждения владельца; подтверждение fingerprint — офлайн-карточка/внешний канал,
не подделываемый процессом того же SID; повторный enroll отказ; adminSignature —
отдельная административная роль; ротация сверяется с внешним ожидаемым keyId.
Критерий: T14/N17 закрыт; тест «enroll из подменённого каталога без подтверждения → отказ».

### M06. Registry: ACL, монотонность, backup
Требование: ACL на запись = SYSTEM + SID службы (Admins — не писатели; админ-деградация
фиксируется M09); append-only; монотонный registryVersion + high-water mark в защищённом
состоянии; подпись владельца на каждой записи; восстановление из backup только с подписью
владельца и версией не ниже high-water mark; повреждение/удаление → fail-closed.
SID службы — выделенная виртуальная учётная запись (NT SERVICE\KAIDEN-TAS) или отдельный
пользователь, не LocalSystem.
Критерий: T15/N18 закрыт; тесты rollback/backup/удаления обязательны.

### M07. DPAPI LocalMachine — не граница
Требование: явная фиксация в пакете: любой локальный процесс может распечатать
LocalMachine-конверт; защита ключа анкера = ACL файла (только SID службы) + контекст
службы; DPAPI LocalMachine — defense-in-depth. Ключевой материал недоступен пользовательскому
SID на чтение/запись.
Критерий: текст пакета исправлен; тест доступа к ключу из пользовательского процесса → отказ.

### M08. Исторические анкеры и запрет автопринятия
Требование: legacy-анкеры (до v2) не дают доверенный PASS автоматически; статус
«неподтверждённое происхождение ключа»; переаттестация — только явным решением владельца
с офлайн-подтверждением fingerprint исторического anchorKeyId. Старый trust-pin.json
игнорируется; созданный createTrustRoot корень не доверенный до enrolled.
Критерий: T16/N20 закрыт; тест «legacy-анкер без переаттестации → не доверенный PASS».

## Решение владельца + условие развёртывания

### M09. Конфигурация «владелец = локальный администратор»
Граница TAS не обеспечивается против same-SID атакующего с правами админа (запись в
registry при ACL Admins, конфигурация службы, DPAPI LocalMachine, отладка). UAC не защита
от уже-админа. Обязательное условие развёртывания (одно из):
(a) владелец приложения работает под не-админ учётной записью;
(b) TPM/HSM-вариант хранения ключа анкера и реестра;
(c) явное письменное принятие остаточного риска владельцем для конкретной среды.
Без выполнения (a)/(b)/(c) приёмка v2 на среде owner=админ не выдаётся.
Критерий: решение владельца зафиксировано; пакет содержит условие как обязательное.
Закрывает: T13/N19 (как условие, не как механизм).
