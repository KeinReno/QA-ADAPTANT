## 2. Перехват первого `prepare-run`: приводит ли к несанкционированной мутации

### 2.1. Что зафиксировано в v2.1

- approval связывает operation/inputs/fixture/environment/manifest-хеши (контракт 0.2),
  но **не содержит runId** (проверено по `packages/trust/approval.mjs`, поля 0.2).
- bind approvalId→runId выполняется первым `prepare-run`; grant — только TAS-исполнению.
- анкер подписывается только после attestation; POST выполняет Worker, созданный TAS.

### 2.2. Что даёт перехват

1. **Содержание мутации не подменяется:** operation/inputs/fixture/environment привязаны
   к подписи владельца; TAS отвергает несовпадение. Изменить бизнес-содержание операции
   перехватчик не может.
2. **Но перехватчик выбирает runId и момент исполнения.** TAS создаст Worker и выполнит
   POST с разрешённым (owner-signed) содержимым. Мутация формально авторизована
   подписью, однако:
   - исполнение инициируется не владельцем, а сторонним процессом;
   - легитимный прогон теряет approval (DoS);
   - владелец теряет контроль момента (TOCTOU-подобный разрыв между «одобрено» и «выполнено сейчас»).
3. **Ложного PASS нет:** анкер и вердикт достанутся только TAS-исполнению; перехватчик
   не получает подписи и не может выдать чужой PASS.

### 2.3. Вывод

Перехват подготовительного шага **не создаёт несанкционированную бизнес-мутацию по
содержанию**, но создаёт **несанкционированное исполнение авторизованной операции**
(и DoS владельцу). Для строгой модели этого недостаточно: исполнение должно быть
связано с намерением владельца на конкретный прогон.

### 2.4. Безопасное исправление (предложение, до реализации)

**G1 — runIntent (owner-bound run binding).** Ввести owner-подписанный документ
`runIntent` {approvalId, runId, manifestSha256, nonce, notBefore, expiresAt}, выдаваемый
при старте прогона (подпись owner-ключом, недоступным A2). `prepare-run` принимается
только при валидном runIntent, совпадающем с approval и manifest; повторный runId
отвергается. Тогда:

- перехватчик без runIntent получает отказ;
- копирование валидного runIntent даёт только запуск того же прогона (раньше/повторно),
  но не новую мутацию, и упирается в реестр runId/одноразовость;
- bind остаётся атомарным в TAS.

**G2 — authorize-post checkpoint.** Перед фактическим POST Worker обязан получить у TAS
атомарное разрешение `authorize-post(grantId, evidenceHead)`; cancel/revoke, истёкший TTL
или расхождение evidence дают отказ до отправки. Это закрывает окно «cancel после spawn,
но до POST» и гарантирует, что отменённый прогон не отправит мутацию.

Оба пункта — изменения контрактов (approval/runIntent) и state machine; они **не входят**
в проверяемый SHA 07adb5f. Предлагается включить G1/G2 в следующую ревизию пакета
(или отдельным change-документом) после заключения Qwen, не меняя текущий SHA.

## 3. TAS evidence внутри пользовательского runDir

### 3.1. Риски текущей формулировки v2.1

В v2.1 сказано: evidence доверенного прогона пишется в `runDir/trusted/` с ACL службы.
runDir — пользовательский (A2-writable) путь. Риски:

1. **Junction/symlink до создания.** Пользователь заранее создаёт `runDir/trusted` как
   junction на свой каталог; TAS «создаёт каталог», но пишет в редирект. ACL применяется
   к цели, а не к ожидаемому пути.
2. **TOCTOU.** Проверка «путь не содержит reparse points» и последующая запись — разные
   операции; каталог можно подменить между ними.
3. **Подмена родительского пути.** runDir может быть junction/символической ссылкой
   (историческая N11/junction): физический путь уходит в user-writable зону.
4. **Переименование/удаление после создания.** Пользователь переименовывает каталог,
   создаёт новый на его месте — TAS продолжает писать по старому дескриптору или теряет
   данные; удаление → DoS/fail-closed.
5. **Наследование ACL.** Создание внутри родителя с наследуемыми правами может дать
   пользователю запись, даже если на корне выставлен ACL (если наследование не отключено).
6. **Hardlink-атаки на файлы** внутри каталога службы (если у пользователя есть запись
   в каталог-цель junction).

### 3.2. Предлагаемое решение (G3)

**Источник истины — вне пользовательского дерева.** TAS хранит evidence и цепочку
в собственном сторе `ProgramData\KAIDEN\TAS\state\runs\<sha256(runId)>\`
(ACL: SYSTEM + SID службы; пользователю нет доступа). В runDir публикуется только
**проекция для чтения** (копии/hashes/указатели), которая не является доказательством
для TAS.

Если по контракту evidence обязателен в runDir — дополнительно:

- TAS **не принимает runDir от клиента** для доверенных артефактов: создаёт свой
  каталог под фиксированным TAS-путём, runId — хеш, не пользовательский путь;
- при работе с пользовательским путём: открывать каждый компонент с
  `FILE_FLAG_OPEN_REPARSE_POINT`, проверять `FILE_ATTRIBUTE_REPARSE_POINT`, сравнивать
  итоговый handle-path с ожидаемым (`GetFinalPathNameByHandle`), создавать каталог
  эксклюзивно (`CREATE_NEW`), отключать наследование ACL, запрещать delete/rename
  (deny ACE), повторно проверять identity handle перед записью;
- любые расхождения → fail-closed, без записи.

Это архитектурный пробел v2.1; фиксируется как **G3** и предлагается к включению
в следующую ревизию (текущий SHA не меняется).

## 4. Установка TAS: разделение пользовательского и административного SID

Предусловия (M09/D1): рабочая учётная запись — не-администратор; административная
граница — отдельная учётная запись администратора; UAC secure desktop.

1. **Учётные записи.** Создать виртуальную учётную запись службы `NT SERVICE\KAIDEN-TAS`
   (не LocalSystem); служба запускается под ней. Администратор установки — отдельный SID.
2. **Каталоги.**
   - `C:\Program Files\KAIDEN\TAS\` — бинарь/конфиг: Administrators+SYSTEM запись,
     Users чтение/выполнение; SID службы чтение/выполнение.
   - `C:\ProgramData\KAIDEN\TAS\` — Registry/state/ключ: SYSTEM + SID службы запись;
     Administrators — **не писатели** (D1/M06); Users — нет доступа.
   - Проверка отсутствия junction/symlink по всем компонентам путей установки.
3. **Служба.** Регистрация с `sc create` (или MSI), автозапуск, recovery-политика
   (рестарт с backoff), без интерактивного рабочего стола.
4. **Ключ TAS.** Генерируется службой при первом старте в своём контексте; приватная часть —
   файл с ACL только SID службы (DPAPI LM — defense-in-depth); публичная — экспорт
   fingerprint в admin-консоль и в подписанный артефакт установки (D7).
5. **Закрепление в клиенте.** Публичный ключ TAS (и его хеш) входит в подписанный пакет
   продукта/клиента; клиент читает из install dir (read-only для пользователя), не из
   user-конфигурации. Никаких env/config-override.
6. **Проверка.** `status` через IPC с mutual auth; при несоответствии SID/подписи клиент
   отказывает (fail-closed). Smoke-тест: поддельный канал → отказ.
7. **Обновление/удаление.** Только под администратором; обновление сохраняет Registry
   (HWM), удаление требует явного решения (иначе state остаётся, служба не удаляет
   доказательства автоматически).

## 5. Первичное закрепление и ротация ключа TAS без доверия к пользовательским файлам

### 5.1. Bootstrap

1. Установочный пакет подписан ключом релиза; клиент проверяет подпись пакета при
   установке (supply-chain).
2. Публичный ключ TAS + fingerprint включаются в подписанный пакет (install dir,
   не user-writable). Клиент доверяет **вшитому/установочному** ключу, а не файлу,
   который может заменить A2.
3. При первом старте служба экспортирует fingerprint в admin-консоль; администратор
   сверяет его с записью в подписанном пакете (офлайн/независимый канал).

### 5.2. Ротация

1. Новая ключевая пара генерируется службой; публичный ключ подписывается **старым**
   ключом TAS (chain: `rotationAttestation` {oldKeyId, newKeyId, version, createdAt}).
2. Клиенты принимают новую пару только при: подписи старым закреплённым ключом,
   монотонном `keyVersion`, совпадении version-политики. Обновление закрепления —
   атомарно, в install dir (admin), с сохранением старого ключа для проверки уже
   выданных артефактов (историческая проверка).
3. Rollback ключа запрещён: `keyVersion` не уменьшается (аналог HWM); при попытке —
   fail-closed, требуется явное решение владельца с офлайн-подтверждением.
4. Компрометация ключа: внеплановая ротация только через offline-подтверждение владельцем
   и отдельный recovery-epoch; старые артефакты переходят в `LEGACY_UNVERIFIED`.

## 6. Безопасное восстановление Registry после повреждения (без отката ниже HWM)

1. **HWM хранится независимо:** в заголовке Registry и в отдельном защищённом файле
   (ACL службы), плюс событие в append-only журнале. Расхождение → fail-closed.
2. **Восстановление из backup:** принимается только backup с подписью владельца и
   версией V ≥ HWM. V < HWM → отказ (`REGISTRY_ROLLBACK`), даже если backup «выглядит
   целым».
3. **Целостность:** проверяется цепочка версий (каждая запись ссылается на предыдущую,
   подписи владельца/админа), непрерывность версий; разрыв → fail-closed.
4. **Epoch при невосстановимой потере:** owner-подписанный `recoveryDecision`
   {lostUpToVersion, newEpoch, reason, nonce}; HWM переводится в новый epoch со значением
   больше потерянного; всё, что ниже, помечается `legacy-unverified` (никакого
   ретроактивного доверия). Это **не** откат: новые решения не могут ссылаться на
   потерянные версии как на доверенные.
5. **Журнал восстановления** append-only; администратор не может «переписать» историю —
   только добавить решение.
6. **Тесты:** restore V<HWM → отказ; restore V=HWM → ok; разрыв цепочки → отказ;
   решение владельца → новый epoch, legacy-статусы; повторное восстановление идемпотентно.
