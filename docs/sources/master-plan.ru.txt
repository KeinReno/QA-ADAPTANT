Для каждого кандидата определить одно решение:

REWRITE — реализовать заново по подтверждённому контракту.
REJECT — не переносить.
Зафиксировать причины, лицензии сторонних зависимостей, необходимые тесты и стоимость интеграции.
Код без подтверждённой работоспособности нельзя считать готовым компонентом.
Старые проекты остаются неизменными.

4. АРХИТЕКТУРА ЦИЗ — ОБЯЗАТЕЛЬНЫЙ КОНТЕКСТ
Тестируемая система ЦИЗ состоит из трёх крупных кодовых баз:
task_manager_front
React SPA.
Включает маршруты, модальные окна, Redux, сохранённое состояние, HTTP-клиенты, Socket.IO и tracking пользовательской активности.
tasks_manager
Основной FastAPI backend.
Содержит множество роутеров, бизнес-сущности, транзакции, задачи, задания, сотрудников, клиентов, справочники, биллинг и взаимодействия с другими сервисами.
micro_services
Не один сервис, а несколько независимо работающих компонентов.
По исследованию Кими, в этом репозитории находятся gateway, auth, WebSocket, push, activity, files, warehouse, AI, транскрибация, Redis/KeyDB, отдельные БД и инфраструктурные компоненты.
4.1. Gateway
Предполагаемая по исходникам цепочка:
Browser → nginx → HAProxy → Frontend / Backend / Services
Маршрутизация зависит от префикса.
Например:
- /backend/auth/* → auth service.
- Прочие /backend/* → основной backend.
- /socket.io/ → WebSocket.
- /activity/ → activity service.
- Другие сервисные префиксы → соответствующие сервисы.
Gateway может изменять внешний путь при передаче внутреннему сервису.
QA должен понимать разницу между публичным маршрутом и фактической точкой обработки.
4.2. Авторизация
По анализу исходников:
- Frontend выполняет login через gateway.
- Auth service создаёт токены.
- Auth service обращается к основному backend за дополнительными пользовательскими данными.
- Backend обращается к auth service для проверки токенов.
Получение access token само по себе не доказывает полной загрузки пользовательского контекста.
4.3. Неатомарные операции
Одна операция пользователя может запускать несколько технических действий.
Например, создание задачи, сохранение исполнителей, добавление комментария, биллинг и рассылка событий не обязательно завершаются одной атомарной транзакцией.
Следовательно:
HTTP 200 не означает, что все бизнес-эффекты завершились успешно.
4.4. Асинхронность
В ЦИЗ присутствуют фоновые обработчики и read-model.
Данные могут быть сохранены, но ещё не отображаться в определённых пользовательских представлениях.
Использовать ограниченные ожидания и независимые проверки.
Не считать отсутствие мгновенного WebSocket-события доказательством отсутствия записи.
4.5. Корреляция
В ЦИЗ используется X-Ciz-Id для HTTP-запросов.
QA ADAPTANT должен использовать собственный runId для всего теста.
Связывание:
runId → stepId → HTTP Request → X-Ciz-Id → Response → Business Entity
Далее независимое чтение подтверждает принадлежность объекта.
Не создавать фиктивную причинную связь по одной временной близости событий.
4.6. Важное различие предметных сущностей
В ЦИЗ задача и задание не должны автоматически считаться одной сущностью.
Ранее исследовался endpoint создания задачи:
POST /backend/tasks/create_new_task/
Но в обязательном испытательном сценарии используется операция создания задания, обозначенная как create-action.
Это разные бизнес-процессы.
Не смешивать:
- ID родительской задачи.
- ID созданного задания.
- ID справочного типа работ.
- ID конкретной выполненной работы.
- ID складской позиции.
Фактические маршруты create-action, поля ответа и модели данных установить по исходникам и Dev.
4.7. Степень достоверности
Весь приведённый раздел основан на исследовании Кими.
Кими изучал исходники, но не подтвердил соответствие локальных копий текущему Dev.
Astra должна рассматривать эти сведения как сильную исходную гипотезу.
Необходима отдельная сверка фактического runtime.

5. ЦЕЛЕВАЯ МОДУЛЬНАЯ АРХИТЕКТУРА
На старте предусмотреть следующие исполняемые компоненты.
5.1. Control Plane
Отвечает за:
- Создание и запуск прогонов.
- Расписание и очереди.
- Назначение исполнителей.
- Управление состояниями.
- Остановку и отмену.
- Соблюдение лимитов.
- Проверку версий сценариев.
- Формирование RunManifest.
- Защиту от конфликтующих прогонов.
Не выполняет браузерные действия.
5.2. Browser Worker
Изолированный процесс исполнения.
Использует Playwright.
Поддерживает:
- Реальный браузер.
- Несколько независимых контекстов.
- Браузерные действия.
- Наблюдение состояния.
- DOM и accessibility-информацию.
- Сетевые события.
- Скриншоты и трассы.
- Тайм-ауты.
- Ограниченные повторы.
- Безопасное прекращение работы.
Не выносит бизнес-вердикт.
5.3. Verification Worker
Независимый процесс.
Получает утверждённый Operation Contract и проверяемые факты.
Использует независимые read-only источники данных, где они доступны.
Обязательно самостоятельно проверяет происхождение доказательств и принадлежность созданных сущностей текущему прогону.
Не доверяет простому утверждению Browser Worker, что «всё выполнено».
Не изменяет проверяемые бизнес-данные.
5.4. Intelligence Worker
Изолированный процесс анализа.
Отвечает за:
- Исследование трёх репозиториев.
- Семантическую карту интерфейса.
- Анализ маршрутов.
- Сопоставление frontend и backend.
- Установление связей с микросервисами.
- Обнаружение изменений.
- Анализ требований пользователя.
- Поиск устаревших действий.
- Предложение новых сценариев.
Не изменяет утверждённый Acceptance Run.
В первом минимальном ядре может отсутствовать, но для полного релиза обязателен.
5.5. Workbench
Отдельный интерфейс.
Не управляет внутренним жизненным циклом браузера напрямую.
Работает через публичный API Control Plane и поток событий.
Закрытие Workbench не должно останавливать исполнение.
5.6. Библиотечные пакеты
Отдельно от исполняемых процессов:
- Scenario Registry.
- Scenario Compiler / Validator.
- Execution Planner.
- Operation Contracts.
- Evidence Store.
- CIZ Adapter.
- Fixture Management.
- Provider Adapters.
- Shared Schemas.
Запрещены несанкционированные импорты внутренних реализаций чужих модулей.
Все публичные интерфейсы документируются.
Не создавать отдельный сервер для каждого пакета.

6. ШЕСТЬ ОБЯЗАТЕЛЬНЫХ КОНТРАКТОВ
Astra должна спроектировать и согласовать с Luna шесть машинно проверяемых контрактов до параллельной разработки.
6.1. OPERATION-CONTRACT
Описывает бизнес-операцию:
- Условия начала.
- Роли и права.
- Входные данные.
- Обязательные результаты.
- Условные результаты.
- Асинхронные эффекты.
- Правила ожидания.
- Источники подтверждения.
- Критерии успеха.
ИИ не может самостоятельно превращать неподтверждённое предположение в обязательное бизнес-требование.
6.2. SCENARIO-SCHEMA
Описывает способ выполнения операции:
- Идентификатор и версию.
- Узлы.
- Переходы.
- Входные параметры.
- Действия.
- Условия.
- Проверки.
- Допустимые ожидания.
- Безопасные стратегии повторов.
Утверждённый сценарий неизменяем во время Acceptance Run.
6.3. RUN-PROTOCOL
Описывает:
- Создание запуска.
- Назначение исполнителя.
- Запуск.
- События.
- Остановку.
- Ошибки.
- Прерывания.
- Восстановление.
- Завершение.
Каждая команда должна иметь понятное состояние и правила повторного применения.
6.4. EVIDENCE-SCHEMA
Фиксирует происхождение доказательств.
Недостаточно хранить только task_id или action_id.
Необходимо сохранять проверяемую цепочку от уникального fixture до запроса, ответа и независимого чтения.
Исходные артефакты должны быть доступны Verification Worker.
Защищать журнал от незаметного изменения; использовать контрольные суммы и привязку артефактов к конкретной версии запуска.
6.5. VERDICT-POLICY
Только четыре итоговых вердикта:
- PASS.
- FAIL.
- BLOCKED.
- INCONCLUSIVE.
Диагностические причины хранятся отдельно.
Например:
ENVIRONMENT_CHANGED
ELEMENT_AMBIGUOUS
BUSINESS_INVARIANT_VIOLATED
EVIDENCE_MISSING
REQUIREMENT_MISMATCH
RESULT_UNCONFIRMED
AUTH_UNAVAILABLE
Перечень reasonCode должен быть типизированным и версионированным.
6.6. FIXTURE-CONTRACT
Описывает:
- Тестовые учётные записи.
- Разрешённые роли.
- Исходные данные.
- Уникальный fixtureId.
- Принадлежность объектов.
- Изоляцию.
- Политику очистки.
- Разрешённые мутации.
- Правила обращения с неопределёнными результатами.
Запрещается автоматически удалять объект, принадлежность которого не доказана.
Неизвестный результат мутации не разрешает повторить её без независимой проверки.
Сведения об окружении фиксируются в RunManifest.

7. ДВА НЕЗАВИСИМЫХ РЕЖИМА
7.1. ACCEPTANCE RUN
Официальная проверка.
Правила:
- Только утверждённый сценарий.
- Фиксированная версия.
- Детерминированное исполнение.
- Никакого редактирования сценария ИИ во время проверки.
- Никакого автоматического изменения ожидаемого результата.
- Никакого произвольного выбора похожих элементов.
Если действие невозможно безопасно выполнить, прогон останавливается с обоснованным статусом.
7.2. ADAPTIVE EXPLORATION
Режим исследования и создания тестов.
В нём разрешены:
- Анализ текста пользователя.
- Исправление опечаток в рабочем представлении.
- Сопоставление пользовательских терминов с текущим UI.
- Исследование DOM.
- Анализ исходников.
- Поиск изменённых элементов.
- Построение бизнес-операций.
- Генерация сценариев.
- Предложения по исправлению устаревших инструкций.
Результатом становится новая версия сценария в статусе DRAFT.
Она не превращается автоматически в утверждённый тест.
Между исследованием и официальным прогоном должен существовать явный шаг утверждения.

8. CIZ INTELLIGENCE И SEMANTIC ATLAS
Это центральный компонент полной версии.
Основная проблема предыдущих QA: система находила элемент по внешнему сходству, но не понимала его назначение.
В ЦИЗ много одинаковых надписей и одинаково выглядящих кнопок.
Кнопка «Добавить» может выполнять разные функции в зависимости от экрана, модального окна, строки таблицы или активного бизнес-процесса.
8.1. Семантическая идентичность
Каждый элемент должен сопоставляться с устойчивой функциональной идентичностью.
Например:
ciz.work-types.create
ciz.actions.completed-work.add
ciz.warehouse.position.add
Идентификаторы условные; реальные значения определить при исследовании.
Хранить:
- Экран.
- Маршрут.
- Модальное окно.
- Контейнер.
- Бизнес-операцию.
- Тип элемента.
- Доступное имя.
- Исходный компонент.
- Обработчик.
- API-связь.
- Условия доступности.
- Подтверждённый способ поиска.
8.2. Иконки, созданные кодом
Поддерживать:
- SVG.
- React-компоненты.
- CSS-иконки.
- Псевдоэлементы.
- Шрифтовые иконки.
- Динамические элементы.
- Кастомные интерактивные компоненты.
Не предполагать, что визуальная иконка обязательно является тегом img.
При необходимости сопоставлять визуальный элемент с DOM и исходниками.
8.3. Запрет неоднозначного выбора
Не использовать .first() и .nth() только для обхода неоднозначности.
Индекс элемента допустим, если его позиционное назначение доказано контрактом.
Перед действием проверять нужный контейнер, контекст, бизнес-объект и уникальность.
Если цель не установлена достоверно — остановить действие.
8.4. Происхождение знаний
Для каждого утверждения сохранять:
- Источник.
- Файл и ревизию.
- Runtime-наблюдение.
- Время последнего подтверждения.
- Степень достоверности.
- Статус утверждения.
- Применимость к текущему Dev.
Разделять:
SOURCE_DISCOVERED
RUNTIME_OBSERVED
BEHAVIOR_VERIFIED
HUMAN_APPROVED
Нельзя считать эти состояния эквивалентными.
8.5. Инкрементальное обновление
Не переиндексировать три репозитория перед каждым тестом.
Отслеживать изменения исходников, маршрутов, компонентов и контрактов.
Обновлять только затронутые области знаний.
При несовпадении исходников и Dev показывать неопределённость.

9. ОБЯЗАТЕЛЬНЫЙ ИСПЫТАТЕЛЬНЫЙ СЦЕНАРИЙ
9.1. Назначение сценария
Это главный интеграционный экзамен QA ADAPTANT.
Сценарий проверяет одновременно:
- Понимание естественного языка.
- Работа с опечатками.
- Обнаружение устаревших инструкций.
- Исследование контекстных меню.
- Наведение на вложенные меню.
- Работа с модальными окнами.
- Различение одинаковых кнопок.
- Создание справочных сущностей.
- Создание задания.
- Корреляция HTTP-запросов.
- Запоминание идентификаторов.
- Изменение выполненных работ.
- Работу со складом.
- Закрытие задания.
- Проверку результата в родительской задаче.
- Проверку бизнес-эффектов.
Исходный текст должен храниться без изменений.
Орфографические и лексические ошибки являются частью испытания.
9.2. Оригинальный текст задания владельца
1. Заходим в справочники «Типы выполненных работ», через контекстное меню в шапке сайта.
2. Нажимаем добавить тип работы.
3. В открывшейся мочалке выбираем отдел «Техники (ТП)» и в названии типа выполненных работ вбиваем текст «списание роутера».
4. В этой же модалке нажимаем «Добавить».
5. Ищем в списке созданный тип выполненных работ и нажимаем по нему.
6. Появляется контекстное окно и нам нужно в нем выбрать «списание роутера».
7. В открывшейся модалке, выбираем в «категория» — значение «общие», и прописываем в «Выполненные работы» — значение «списание роутера2». Указываем, что «Есть привяза к складу» и нажимаем добавить.
8. Закрываем модалу справочников.
9. В таблице задач, нажимаем на айди любой задачи(запоминаем айди задачи) и в контекстном меню наводим мышь на «Создать задание», в открывшемся подменю — наводим на отдел «Техники (ТП)» и откроется еще одно подменю, где мы должны выбрать «Забрать роутер», после чего откроется еще подменю, в котором надо выбрать любой адрес клиента, кроме «офис» или «узел».
10. Откроется модалка с сеткой выбора выездного исполнителя, где мы должны нажать на любую кнопку «выбрать».
11. Откроется модалка регистрации нового задания с заполненными полями. В ней нажимаем «Создать задание». Уйдет POST запрос на бекенд(create-action), который в ответе отдаст айди нового задания — его мы должны запомнить.
12. Запомненный, на предыдущем шаге, айди мы должны найти в таблице или через серверные фильтры и нажимаем на найденный наш айди.
13. В открывшейся модалке задания нажимаем на кнопку «изменить» в строке таблицы «Выполненные работы».
14. В ней выбрать отдел «Техники (ТП)», после чего найти открывшееся типы выполненных работ и нажать на «Списание роутера» — после чего внизу откроется строка с созданным нами ранее «Списание роутера2» — находим там кнопку «+».
15. После нажатия на «+», мы должны увидеть выбранную работу в правой части модалки.
16. После чего нажимаем «сохранить» — откроется модалка выбора оборудования с «склада» с названием «Позиции склада».
17. В этой модалке(Позиции склада) выбираем первую попавшуюся строку с текстом внутри «роутер» и добавляем его(запоминаем название роутера), путем нажатия в этой строке на «+». После чего нажимаем на кнопку «Добавить».
18. У нас остается модалка задания — в ней ищем «Платность» и выбираем в нем «Платно», а так же в ней ищем «Состояние» и в нем выбираем «Выполнено».
19. Откроется модалка «Закрытие задания» и в поле ввода «Затрачено часов» выбираем «2», после чего нажимаем на «Закрыть задание».
20. Закрываем модалку задания.
21. В таблице ищем айди, запомненный на этапе 9 и открываем эту задачу, путем нажатия на айди задачи и выборе «Просмотр» в контекстной меню.
22. В этой мочалке задачи ищем новое задание(не выполненное) на отдел «Менеджеры» и чуть ниже него мы должны увидеть комментарий задания с запомненным роутером и затраченными часами в виде (затрачено часов: 2).
23. Если все удалось — сценарий пройден.

10. НАМЕРЕННЫЕ ДЕФЕКТЫ И СЛОЖНОСТИ СЦЕНАРИЯ
Владелец заранее сообщил, что пункт 7 содержит заведомо устаревшее требование.
В соответствующем месте ЦИЗ больше нет поля «Категория».
Это не ошибка тестовика. Это проверка его способности распознать устаревшую инструкцию.
10.1. Требуемая реакция
QA ADAPTANT должен:
1. Сохранить исходный пункт 7.
2. Найти соответствующую операцию в ЦИЗ.
3. Проверить текущую структуру модального окна.
4. Сопоставить её с доступными исходниками.
5. Обнаружить отсутствие поля «Категория».
6. Установить, что требование не соответствует текущей реализации, если это подтверждается.
7. Сформировать конкретное диагностическое замечание.
8. Предложить актуальный вариант шага.
9. Сохранить новую версию сценария как DRAFT.
10. Запросить утверждение изменённой версии.
Пример правильной диагностики:
«В исходном пункте 7 указано поле "Категория" со значением "Общие". В текущем интерфейсе соответствующее поле не обнаружено. Проверка исходников указывает на изменение формы. Предлагается исключить этот выбор из шага, сохранив остальные действия. Требуется подтверждение изменения сценария».
Если исходники и Dev противоречат друг другу, система должна показать это расхождение, а не утверждать, что поле окончательно удалено.
10.2. Запрещённая реакция
Нельзя:
- Искать несуществующее поле бесконечно.
- Нажимать похожее поле.
- Самостоятельно менять бизнес-ожидания.
- Игнорировать отсутствующий шаг без уведомления.
- Объявлять исходный сценарий успешно выполненным после незаметной коррекции.
10.3. Исправление языка
Слова «мочалка», «модала», «айди», «привяза» и другие разговорные или ошибочные выражения должны интерпретироваться по контексту.
Однако исправление языка не означает автоматическое изменение бизнес-смысла.
Сохранять одновременно:
- Оригинальный текст.
- Нормализованную интерпретацию.
- Обнаруженные неоднозначности.
- Подтверждённые соответствия.
- Предложенные исправления.
10.4. Другие потенциально устаревшие пункты
Не считать остальные 22 шага гарантированно актуальными.
Особенно проверить:
- Существование нужного справочника.
- Реальную структуру вложенных меню.
- Доступность отдела «Техники (ТП)».
- Наличие операции «Забрать роутер».
- Названия складских полей.
- Доступность действия «Платно».
- Переход в состояние «Выполнено».
- Логику создания задания менеджерам после закрытия.
- Фактический формат комментария в родительской задаче.
Не удалять эти требования без установления их текущего статуса.

11. КОМПИЛЯЦИЯ СЦЕНАРИЯ В БИЗНЕС-ОПЕРАЦИИ
Исходные 23 пункта нельзя напрямую превращать в 23 браузерных клика.
Компилятор должен выделить независимые бизнес-операции.
OP-A — Подготовка справочника
Исходные шаги 1–7.
Создать тип выполненных работ «списание роутера» и связанную запись «списание роутера2» с привязкой к складу, учитывая подтверждённую актуальную структуру формы.
Проверить сохранение созданных объектов.
OP-B — Создание задания
Шаги 8–12.
Выбрать допустимую родительскую задачу, открыть контекстное меню, выбрать отдел, тип задания, адрес и исполнителя.
Создать задание через актуальный endpoint create-action и сохранить подтверждённый идентификатор созданного объекта.
Не путать ID задания и ID родительской задачи.
OP-C — Добавление выполненной работы
Шаги 13–16.
Открыть созданное задание, найти нужный раздел, добавить конкретную справочную работу и подтвердить сохранение выбора.
OP-D — Работа со складом
Шаг 17.
Выбрать допустимую тестовую складскую позицию, соответствующую роутеру.
Зафиксировать её идентификатор и наименование.
Проверить правильность связи с заданием.
OP-E — Завершение задания
Шаги 18–20.
Установить требуемую платность и статус.
Указать два затраченных часа.
Подтвердить фактическое завершение задания по серверным данным.
OP-F — Проверка родительской задачи
Шаги 21–23.
Повторно открыть родительскую задачу.
Установить наличие ожидаемого последующего задания менеджерам и комментария с наименованием выбранного роутера и двумя затраченными часами.
Проверить причинную связь с исходным заданием.
Если ожидаемый эффект отсутствует, установить, является ли это нарушением утверждённого контракта, допустимой задержкой или неопределённостью.
11.1. Обязательные переменные сценария
Как минимум:
- fixtureId
- parentTaskId
- createdActionId
- departmentId
- executorId
- customerAddressId
- workTypeId
- completedWorkId
- warehouseItemId
- warehouseItemName
- hoursSpent = 2
- paymentMode
- completionStatus
Фактические названия и типы полей определить по ЦИЗ.
Каждая переменная должна иметь источник происхождения и уровень подтверждения.
11.2. Динамические значения
Фразы «любая задача», «любой адрес», «любой исполнитель» и «первый попавшийся роутер» не разрешают произвольный выбор опасных данных.
Нужна детерминированная политика отбора:
- Объект принадлежит тестовому контуру либо разрешён для тестирования.
- У пользователя достаточно прав.
- Выбор соответствует заданным ограничениям.
- Объект доступен в текущем Dev.
- Возможные побочные эффекты разрешены.
- Выбранный идентификатор записывается до выполнения мутации.
Если подходящего объекта нет — BLOCKED с конкретной причиной.

12. ИСПЫТАНИЕ ДОЛЖНО ДОКАЗЫВАТЬ БИЗНЕС-РЕЗУЛЬТАТ
Нельзя ограничиваться тем, что браузер прошёл все экраны.
12.1. Проверка справочника
Подтвердить:
- Создан правильный тип.
- Сохранено нужное название.
- Сохранена принадлежность отделу.
- Создана связанная запись выполненной работы.
- Сохранён признак складской привязки.
12.2. Проверка задания
Подтвердить:
- Запрос создания действительно отправлен.
- Ответ содержит идентификатор созданного задания.
- Объект принадлежит текущему fixture.
- Правильная родительская задача.
- Правильный отдел.
- Правильный исполнитель.
- Правильный адрес.
- Данные сохранены после независимого чтения.
12.3. Проверка выполненных работ
Подтвердить связь созданной записи справочника с нужным заданием.
12.4. Проверка склада
Подтвердить связь выбранной складской позиции с заданием.
Не считать показ позиции на экране доказательством сохранения.
12.5. Проверка завершения
Подтвердить:
- Требуемую платность.
- Требуемое состояние.
- Значение затраченного времени.
- Фактическое сохранение изменений.
12.6. Проверка родительской задачи
Подтвердить:
- Правильную родительскую задачу.
- Требуемый последующий эффект для менеджеров.
- Правильный комментарий.
- Совпадение наименования роутера.
- Значение затраченного времени — 2.
При необходимости использовать независимую авторизованную сессию соответствующего пользователя.

13. ЛОКАЛЬНЫЙ СТЕНД ОТКАЗОВ
Перед выполнением опасных тестов на Dev необходимо создать минимальный контролируемый стенд.
Он должен уметь воспроизводить следующие ситуации:
1. Ответ на создание объекта потерян после сохранения.
2. Основной объект создан, комментарий не сохранён.
3. Read-model обновилась с задержкой.
4. Назначен неправильный исполнитель.
5. В интерфейсе несколько одноимённых элементов.
6. Browser Worker аварийно завершился после мутации.
7. Канал доказательств недоступен.
8. Сценарий заменён другой версией при повторном запуске.
9. Dev изменился во время выполнения.
10. Проверяющий получил неподтверждённый идентификатор.
11. Операция завершилась частично.
12. Очистка получила объект с недоказанной принадлежностью.
Не обязательно поднимать копию всей ЦИЗ.
Стенд должен минимально и воспроизводимо реализовывать необходимые API-эффекты, браузерные состояния и сбои.
Успех на стенде подтверждает свойства QA ADAPTANT, но не является приёмкой настоящей ЦИЗ.

14. УЧЁТНЫЕ ЗАПИСИ, АДРЕСА И БЕЗОПАСНОСТЬ
В материалах QA-v2 уже существуют сведения о тестовых аккаунтах, адресах и окружении.
Astra должна их обнаружить и инвентаризировать.
Не требовать от владельца повторного ввода данных, которые уже доступны и действительны.
При этом:
- Не копировать секреты в промпты моделей.
- Не показывать токены в логах.
- Не коммитить .env.
- Не переносить старые авторизованные сессии без проверки.
- Хранить учётные данные отдельно от сценариев.
- Предусмотреть masking в HTTP-доказательствах.
Обязательно различать авторизованного автора задачи, исполнителя и при необходимости менеджера.
Проверки разных пользователей выполнять в изолированных BrowserContext.
14.1. Особая осторожность со складом
В испытании присутствуют списание оборудования, платность и завершение задания.
Это потенциально значимые бизнес-мутации.
Нельзя произвольно выполнять такие действия с реальными клиентскими или складскими данными.
Первый реальный прогон разрешается только после подтверждения безопасного тестового окружения, допустимых аккаунтов, адресов и складских позиций.
Для опасных действий необходима явно разрешённая тестовая область.
Автоматическую очистку на первом Dev-прогоне можно отключить.
Все созданные объекты должны оставаться зарегистрированными с возможностью последующей контролируемой очистки.

18. СТРАТЕГИЯ СКОРОСТИ И ЭКОНОМИИ
Основной принцип:
Один раз исследовать → подтвердить → сохранить → многократно исполнять без модели.
ИИ разрешён:
- При проектировании новых сценариев.
- При исследовании неизвестных интерфейсов.
- При анализе изменений.
- При поиске причины неоднозначности.
- При подготовке новой версии сценария.
ИИ не требуется для каждого клика, заполнения поля или обычной бизнес-проверки.
Необходимо измерять:
- Количество вызовов модели на один сценарий.
- Число повторных исследований.
- Время подготовки теста.
- Время повторного исполнения.
- Долю заблокированных прогонов.
- Долю неподтверждённых результатов.
- Причины остановок.
- Использование CPU и памяти.
Не вводить произвольные показатели производительности как уже гарантированные.
Сначала измерить базовые значения, затем установить целевые пороги.

GPT Luna 6 обязательно участвует в инженерной проверке и приёмке.
Приоритет не в количестве созданных модулей, а в достоверно работающей системе, которой можно доверять.
Начинай с аудита исходных материалов и формирования архитектурных контрактов. После утверждения технических границ переходи к реализации и поэтапной приёмке.
Конечная цель: QA ADAPTANT — быстрый, экономичный, модульный, наблюдаемый и доказательно надёжный тестировщик распределённых бизнес-приложений.





Три условия, на которых я особенно настаиваю
Первое — не сокращать итоговую цель до одного простого теста. Кими правильно предложил начать с узкого сценария создания задачи с исполнителем. Но это только проверка ядра 0.1. Полностью работоспособный ADAPTANT должен дойти до твоего 23-шагового сценария со справочниками, вложенными меню, складом, закрытием задания и проверкой результата.
Второе — Luna должна иметь право отклонять готовность модулей. Astra руководит архитектурой и интеграцией, но не должна принимать всё только по отчётам разработчиков. Если независимая проверка обнаружила ложный PASS, неверную корреляцию объектов или недостаточные доказательства, соответствующий этап не принят.
Третье — не повторять старую проблему бесконечной разработки. После утверждения шести контрактов архитектура замораживается на время реализации первого ядра. Новые идеи проходят через отдельную процедуру изменений; они не должны постоянно пересобирать фундамент.
Какой результат я хочу увидеть первым
Не красивый Workbench и не граф из сотен узлов.
Первый серьёзный результат должен выглядеть так: пользователь передал исходное поручение, система обнаружила устаревший пункт 7, объяснила расхождение с ЦИЗ, предложила новую версию, получила её утверждение, выполнила безопасный тест и предоставила проверяемые доказательства без ложного PASS.
Далее та же система должна показать весь прогон на React Flow — от открытия справочника до независимого подтверждения результата в родительской задаче.
Именно это будет доказательством, что мы наконец построили тестировщик, а не ещё одну систему, которую придётся месяцами тестировать и чинить.
Это итоговая концепция, которую я рекомендую передать Astra без дальнейшего расширения архитектурного объёма до начала разработки.
