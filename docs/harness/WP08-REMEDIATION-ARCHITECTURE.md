# WP-08 REMEDIATION — архитектурное предложение и план

Основание: независимая приёмка WP-08, REJECT. Ветка аудита: `audit/wp-08-07c21c4`,
каталог `wp08-audit/`. Проверенная ревизия: `07c21c4`. Аудиторскую ветку не меняем.

## 1. Воспроизведение P0 (сделано Lead до любых правок)

| Дефект | Команда | Факт | Exit |
|---|---|---|---|
| AUD-P0-01 | `node wp08-audit/tests/wp08-r07-forge-candidate.mjs` | `SIGNER_RESULT {"ok":true,"verdict":"PASS"}`, `PUBLIC_OBSERVE_TRUSTED {"trusted":true,"passed":true,"verdict":"PASS","anchorStatus":"ANCHOR_OK"}` при отсутствии реальной мутации | 0 |
| AUD-P0-02 | `node wp08-audit/tests/wp0304-06-false-pass.mjs` | сценарий A: неполная запись + подмена стенда после POST → PASS; сценарий B: подмена в окне после T-C → POST уходит rogue, Bearer утёк, PASS | 0 (2/2) |

Оба дефекта подтверждены на 07c21c4 собственным прогоном, не по тексту отчёта.

## 2. Первопричины

**P0-01.** Анкер удостоверяет только связку файлов (approval, consumption, снапшоты, журнал, candidate), но не
происхождение candidate. Поэтому процесс, который может писать в runDir и обращаться к named pipe подписанта,
сам создаёт «правильную» цепочку и получает подпись. Происхождение не связано ни с процессом Verification,
который реально делал чтения, ни с его прочитанным набором.

**P0-02.** Существуют три разных, не связанных между собой канала: аттестация среды (Control, T-C),
отправка POST (Browser) и независимое чтение (Verification). Подмена стенда между ними никого не сбивает:
Verification не аттестует среду и верит публичным `/environment` и `/records`. Окно T-C→POST измерено аудитом
в 35 мс при детекции 1 мс — это не микроскопический остаток, а рабочий сценарий.

## 3. Изменение модели доверия (требует утверждения владельца)

Текущая формулировка WP-00 («код, умеющий править только каталог прогона, годный анкер не получает») и
05-KNOWN-RISKS («открытых P0 нет») опровергнуты. Предлагается явно заменить её на модель с цепочкой
происхождения и границей процесса:

**A1.** Control, Verification Worker и anchor-signer — доверенные компоненты, запускаемые harness/владельцем;
их код и память не под контролем противника.

**A2.** Противник в локальной 0.2 может: писать любые файлы в runDir и trust root (кроме приватных ключей),
поднимать свои процессы того же Windows SID, подключаться к публичным локальным каналам, делать HTTP-запросы.
Противник **не** имеет прав отладки/инъекции в доверенные процессы и не извлекает ключи через DPAPI.

**A3.** Происхождение устанавливается ключами, живущими только в памяти доверенных процессов, и каналами,
созданными доверенным родителем (fork IPC Control→Verification, приватный канал Control→signer). Подписант
принимает только то, что пришло по его приватному каналу, и дополнительно перепроверяет связку сам.

**Остаточный риск (фиксируется явно, P2/R-04):** код того же SID с правами инъекции/отладки, доступом к
DPAPI-ключам или запуском доверенных бинарников с выбираемыми входами находится вне модели. Для Dev/ЦИЗ
обязателен отдельный Windows SID (или отдельная учётная запись) для Verification и anchor-signer.

Утверждение этой замены — единственное архитектурное решение, которое требуется от владельца.
Направления исправления ниже уже предписаны аудитом и не меняют замороженные схемы 0.1.

## 4. AUD-P0-01 — достоверное происхождение Verification

Новый домен подписи `verification-attestation` (0.2.1, не затрагивает 0.1):

```
{ schemaVersion: '0.2.1', domain: 'verification-attestation', runId, manifestSha256,
  candidateSha256, readSetSha256, verificationKeyId, pid, startedAt, nonce,
  keyId, signature, signatureAlgorithm }
```

- **Verification Worker** генерирует эфемерную пару Ed25519 в памяти при старте (на диск не пишет),
  сам выполняет независимые чтения, сам считает `readSetSha256` по фактическим артефактам
  (evidenceId + artifact.sha256 + kind) и подписывает аттестацию вместе с кандидатом.
- Аттестация и кандидат передаются Control по **fork IPC** (канал создан Control). Control сверяет хеши с
  durable evidence и байтами candidate; при расхождении — INTEGRITY_ERROR, PASS не публикуется.
- **Anchor-signer** меняет топологию: запускается Control как дочерний процесс с приватным каналом
  (унаследованный IPC), а не публичным named pipe; путь к anchor.key передаётся только в его окружение.
  Подписант сам читает trust root/runDir и дополнительно требует: подпись аттестации ключом, зарегистрированным
  в этой сессии подписанта для данного runId, byte-identity candidate, head цепочки, approval/consumption,
  и **паритет 0.1**: `assertEvidenceRefs` + `assertTerminalEvidence` + `validateVerdictCoverage`.
- Подписант сохраняет аттестацию в `trustRoot/verification/<runId>.json` (подписант — единственный писатель).
- `AnchorStatement` расширяется полями `verificationAttestationSha256` и `verificationKeyId` (docs/changes/008).
- **observeTrustedVerdict** проверяет: анкер, аттестацию из trust root, byte-identity и **полный паритет с 0.1**
  (assertEvidenceRefs, assertTerminalEvidence, validateVerdictCoverage). Это закрывает AUD-P1-01.

Что это даёт: подделка файлов в runDir без работающего доверенного Verification и без его ключа больше не даёт
анкер, а подложный candidate не проходит проверку аттестации у подписанта и наблюдателя.

## 5. AUD-P0-02 — аутентифицированный канал и самопроверка Verification

- **Стенд подписывает ответы.** Ключ стенда (уже есть в WP-04) подписывает: аттестацию, ответ POST /records и
  каждый ответ GET /records для Verification, с уникальным nonce запроса и полем `standKeyId`.
- **Verification аттестует среду сам**: свежий challenge-response до первого чтения и после последнего,
  сверка environmentId/generation/origin/pid/standKeyId и владельца порта; каждое независимое чтение принимается
  только с валидной подписью стенда. Подмена сокета между POST и чтением даёт ENVIRONMENT_CHANGED/INCONCLUSIVE,
  а не PASS.
- **Browser и Verification требуют подпись стенда на ответе POST**: rogue без приватного ключа стенда не может
  подтвердить мутацию. Ответ без подписи — INCONCLUSIVE, PASS запрещён.
- **T-C** остаётся, но перестаёт быть единственной линией: даже если POST ушёл rogue, PASS из этого не следует.
- **Bearer**: токен становится одноразовым на прогон, привязан к runId и отзывается стендом после POST;
  повторное использование отвергается. Полностью исключить попадание заголовка в чужой сокет нельзя, пока
  отправка идёт из другого процесса; остаточный риск фиксируется, но без реального стенда токен бесполезен.
- Frozen `apps/verification/worker.mjs` 0.1 не меняется: для доверенного пути добавляется отдельный
  `apps/verification/trusted-worker.mjs` (или параметризованный доверенный режим в новом файле), чтобы не
  сломать Stable 0.1.

## 6. AUD-P1-02 — V-07 recovery

Гарантировать, что уже выданный анкер и durable candidate восстанавливаются: `reconcileTrusted` при наличии
candidate+анкера и отсутствии terminal-choice создаёт choice anchor и дописывает ровно выбранные байты без
нового раунда бюджета, без второго verdict и без повторной мутации. CANDIDATE_CONFLICT из-за повторного
свидетельства того же candidate — не повод для INCONCLUSIVE.

## 7. Обязательные P2

| ID | Требование |
|---|---|
| E-04 | `credentialRef` среды обязан участвовать в выдаче секрета: секрет другой среды не доставляется, отказ до мутации |
| R-02 | keygen отвергает не только сегмент `runs`, но и реальные пути (realpath) внутрь runDir/каталогов прогонов, включая junction/symlink |

| матрица/тесты | redteam входит в обязательный прогон; агрегатор без fallback-PASS; строко-специфичные проверки; строгие assertion вместо `<=1` |

## 9. Критерий готовности

1. Оба исходных теста аудита (`wp08-r07-forge-candidate.mjs`, `wp0304-06-false-pass.mjs`) на новой ревизии
   должны давать отказ доверенного PASS (тесты переиспользуются без правки их ожиданий — они воспроизводят атаку).
2. P0 закрыты воспроизводимыми регрессиями в основном наборе (`npm test`) и в независимом аудите.
3. P1-01 паритет наблюдателя и P1-02 recovery подтверждены тестами.
4. Обязательные P2 закрыты тестами.
5. Stable 0.1 не изменён: 59/59, схемы без диффа, замороженные пути пусты.
6. Отчёт относится к финальному SHA; внешняя приёмка — отдельно, свой ACCEPT не объявляю.
