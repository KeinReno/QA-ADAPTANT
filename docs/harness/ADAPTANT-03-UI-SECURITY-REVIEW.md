# ADAPTANT 0.3 — review безопасности локального UI

Дата: 2026-11-14  
Scope: HTTP UI и локальный API `apps/orchestrator/http.mjs`; проверка на локальной машине с тестовыми Task и Trust world.  
Статус: отрицательные проверки проходят; защита от произвольных процессов того же Windows пользователя не доказана.

## Изменения

- HTTP `Host` проверяется для каждого запроса: принимаются только `localhost`, `127.0.0.1` и `[::1]` с фактическим портом сервера. Некорректный Host и порт отклоняются до аутентификации и доступа к TaskService.
- Любой `POST` требует `Origin` с HTTP authority, точно совпадающей с `Host` по loopback hostname и фактическому порту. Даже другой loopback alias отвергается как cross-origin. Пропущенный, `null`, внешний или некорректный Origin отклоняется до host callback и TaskService.
- Любой `POST` требует `application/json`; простые типы содержимого, включая `text/plain`, получают 415. `OPTIONS` получает 405. CORS заголовки не выдаются.
- Создание HTTP сервера требует `authenticate` и `issuePlanApproval` host callbacks. Отсутствие любого callback не позволяет запустить сервер. Подтверждение проходит только через host callback, после чего `TaskService.approvePlan` повторно проверяет владельца, текущую версию плана и approval verifier.
- API скрывает Task другого владельца ответом 404. `start` делегируется `TaskService`, который требует `READY`; до этого состояния HTTP не создаёт dispatch intent и не запускает adapter. `cancel` проверяется сервисом по владельцу Task.
- UI печатает данные через `textContent`; CSP ограничивает источники `self`, не подключает внешние скрипты и стили, запрещает встраивание (`frame-ancestors 'none'`); также выставляется `X-Frame-Options: DENY`. Ответы имеют `no-store` и `nosniff`.

## Негативные проверки

`tests/adaptant03-ui.test.mjs`: 4/4 прошли на локальном процессе. Проверено:

- неизвестный Host, неправильный порт, внешний Origin, отсутствующий Origin, `text/plain` и `OPTIONS` отклоняются; для этих запросов число вызовов TaskService остаётся нулевым;
- loopback authority `localhost`, IPv4 и IPv6 принимаются при правильном порте;
- unauthenticated callback получает 401 без доступа к TaskService;
- Task другого владельца скрыта ответом 404;
- без `issuePlanApproval` сервер не создаётся; callback, не выдавший grant, не подтверждает план;
- прямой POST `start` для Task в `AWAITING_APPROVAL` возвращает `TASK_NOT_READY`, не добавляет runId/dispatch intent;
- разрешённый browser UI проходит локальный lifecycle до trusted результата; фактический MOCK виден в плане.

Проверка выполнена командой `node --test tests/adaptant03-ui.test.mjs` с Windows PowerShell 5.1 совместимым `PSModulePath`, применённым также для полного baseline gate. Полный regression после этих изменений будет зафиксирован отдельным evidence пакетом.

## Граница доверия и ограничения

Loopback, `Host`, `Origin` и JSON-only POST защищают от удалённого сетевого доступа, DNS rebinding через чужой Host и браузерного cross-origin запроса из обычного внешнего сайта. Они не являются аутентификацией процесса: локальная программа может самостоятельно открыть loopback socket, подделать `Host`/`Origin` и отправить JSON.

`authenticate(request)` обязан быть реальной host-side аутентификацией текущего Windows пользователя и возвращать стабильный `actorRef`, связанный с `Task.ownerRef`; callback, возвращающий константу или только проверяющий наличие заголовка, небезопасен. Даже Windows SID не отличает браузер от другого процесса, запущенного тем же пользователем. Поэтому исключение произвольного процесса того же SID и защита от локального вредоносного клиента в этой версии не доказаны.

`issuePlanApproval` обязан показать владельцу конкретную версию плана и её digest в доверенном host UI и выдавать approval только после явного действия владельца. Callback, который автоматически подписывает план при любом HTTP POST, устраняет пользовательское подтверждение и небезопасен. Данный репозиторий проверяет наличие callback и verifier, но не содержит production host identity broker или доказательства его интерактивного поведения.

Пока отдельный host broker не обеспечивает эти свойства, локальный HTTP UI пригоден для изолированного локального стенда, но не должен считаться границей защиты от вредоносных процессов того же пользователя. Для такого уровня угроз требуется OS-bound IPC/session capability или иной host-механизм, недоступный обычному HTTP-клиенту; это отдельная архитектурная задача. Никакие Dev credentials или Trust Foundation изменения в этой работе не использовались.
