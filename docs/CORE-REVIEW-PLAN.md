# План независимого black-box review ядра

Статус: план приёмки; реализация и тесты не выполнены. Проверки будут написаны после готовности публичного интерфейса WP-01/02 и запускаются через Control API, реальные дочерние процессы и `adapters/local`. Не импортировать private модули, не подменять процессные сбои unit-моками, не использовать настоящие данные/Dev. Каждый кейс — отдельный временный run directory и уникальный fixtureId. Для кейсов с мутацией проверять число фактических HTTP POST на стороне локального fixture server.

Основание: `ARCHITECTURE.md`, `MODULE-BOUNDARIES.md`, `CIZ-ADAPTER.md`, `EVIDENCE-SCHEMA.md`, `FIXTURE-CONTRACT.md`, `OPERATION-CONTRACT.md`, `SCENARIO-SCHEMA.md`, `VERDICT-POLICY.md`, `docs/FAULT-MATRIX.md`. Вердикты и границы доказательств ниже — требования контрактов, не результат тестового прогона.

## Attack cases

| ID | Атака и setup | Проверяемое ожидаемое поведение |
|---|---|---|
| CR-01 Потерян ответ после фактического commit | Локальный сервер принимает единственный разрешённый POST, создаёт запись с fixtureId, но рвёт соединение до ответа. Control завершается/перезапускается; reconciliation читает запись независимым GET. | Итог `INCONCLUSIVE`, mutationCount=1. Объект можно обнаружить, но нельзя выдумать отсутствующее response evidence, превращать unknown outcome в PASS или повторно отправлять POST. Повторный START после restart не меняет mutationCount. |
| CR-02 INTENT/ACK потеря на границе click | Задержать/сбросить ACK после durable INTENT; отдельно оборвать Browser процесс до и после dispatch. Перезапустить новый Control и передать тот же intent/START. | Сохранённый intent трактуется как possibly dispatched. Повторный INTENT получает прежний ACK без новой мутации; новый browser не нажимает. Один reconciliation GET допустим; POST остаётся максимум один. Если нет полного request/response/read доказательства — `INCONCLUSIVE`, не PASS/авторетрай. |
| CR-03 Поддельное browser evidence и неверный entity ID | Browser worker сообщает success, status 200 и ID существующей записи другого fixture; независимый endpoint возвращает другой ID/fixture/тип. Попытаться приложить browser observation как independent-read. | Verifier сам выполняет GET отдельным клиентом и сравнивает intent → реальный request/response → GET. Browser не может выпускать authoritative read/verdict. Чужая запись не PASS; без авторитетного полного доказательства итог `INCONCLUSIVE`, без ложного FAIL по чужой сущности. |
| CR-04 Валидный по имени, но чужой/двойной fixture | В локальном store подготовить запись с тем же display name, но чужим fixture marker; затем вариант с двумя записями для одного marker. В ответе POST ID тоже развести с записью fixture. | Ownership подтверждается marker + entity kind/ID + response/request identity, а не именем или `lookupBy=fixtureId` отдельно. Неоднозначность/расхождение запрещает PASS; verifier требует единственную сущность. Если чтение полностью доказывает нарушение утверждённого эффекта для собственной сущности — `FAIL`; если принадлежность не установлена — `INCONCLUSIVE`. |
| CR-05 Подмена, пропуск или перенос evidence | После завершения подготовить tamper сценарии: изменить байты артефакта, удалить его, дать symlink/path traversal, подмешать evidence другого runId/manifestSha256, сломать previousSha256/parentEvidenceIds; вызвать обычный public verify. | Verifier перечитывает файлы с диска, проверяет bytes/hash/цепь/run/manifest/fixture и не доверяет уже загруженным объектам. Итог не PASS (`INCONCLUSIVE/EVIDENCE_MISSING`, `INTEGRITY_ERROR` или контрактный отказ). Не импортировать данные другого run для доказательства или FAIL. |
| CR-06 Переписывание approved scenario между start и restart | Создать и утвердить scenario version V1, начать run, затем заменить реестр на V2 с другими equals/input/effects/locator. Перезапустить Control из persisted run. | Старый run использует неизменённый V1 snapshot/hash; либо обнаруживает нарушение связи approval/snapshot и блокирует как `CONTRACT_INVALID`. V2 не становится новым ожиданием старого прогона. Ни один click/POST не происходит из-за одного лишь изменения реестра. |
| CR-07 Ложный FAIL из-за временной недоступности/задержки GET | Server сохраняет запись; первые GET дают 503/timeout или валидный stale read без объекта, позднее до конца verify budget возвращают matching authoritative entity. Контрольная ветка: источник остаётся недоступен до deadline. | До исчерпания bounded deadline ошибка/задержка = `UNKNOWN`, не `VIOLATED`; после доступного matching read возможен PASS при полной цепочке и checks. Если read недоступен до deadline — `INCONCLUSIVE`, не FAIL. GET ограничены budget; POST не повторяется. |
| CR-08 Ложный PASS при неполном/дублированном coverage | Утвердить operation с несколькими required effects, затем через публичный bundle/contract boundary попытаться передать verifier evidence с пропущенным, неизвестным или дублированным checkId; отдельно сделать обязательное поле отсутствующим и сделать conditional input неизвестным/отсутствующим. | Неполная/дублированная coverage отвергается; каждый effect покрывается ровно один раз. Отсутствующее поле/неизвестное условие становится `UNKNOWN`, не `SATISFIED` и не `NOT_APPLICABLE`. PASS недоступен; итог `INCONCLUSIVE` если нарушение не доказано. |
| CR-09 Body drift, ложное `mutation=false`, redirect/origin | Подменить разрешённое fill/input или фактический HTTP body так, чтобы отличался утверждённый input hash/fixtureId; заявить в browser step `mutation=false` перед submit. В отдельной ветке ответить redirect на неподдерживаемый origin. | Adapter независимо классифицирует submit как мутацию; browser декларация не даёт обхода allowlist. До отправки body сравнивается с frozen inputs+fixtureId, несоответствие aborts request; недопустимый origin/redirect блокируется. mutationCount=0, результат блокированный (`CONTRACT_INVALID`/unsupported-target), не PASS и не подтверждённый FAIL. |
| CR-10 Неполный journal / lock / cancel около мутации | Оборвать процесс при записи хвоста журнала; запустить второй run на том же fixture/env; отменить сначала до dispatch, затем после начала dispatch. | Повреждённый/неполный tail не превращается в достоверное доказательство. Lock конфликт блокирует второй run. Cancel до dispatch закрывает браузер без POST; после dispatch не обещает rollback, прекращает дальнейшие мутации и запускает только reconciliation. Неизвестный результат — `INCONCLUSIVE`; POST по-прежнему максимум один. |

## Приёмочные ворота

- Все кейсы выполняются через опубликованные интерфейсы и настоящие IPC-процессы; restart-кейсы создают новый Control процесс и читают persisted run. Никакие внутренние helper assertions сами по себе не считаются black-box приёмкой.
- До запуска проверить документированные status/reason codes и способы fault injection. Если интерфейс пока не позволяет безопасно и воспроизводимо создать условие, отметить кейс `NOT RUN / interface gap`, не обходить его импортом private кода.
- Для каждого прогона сохранить runId, fixtureId, scenario/operation/manifest hashes, POST count, перечень созданных артефактов и ожидаемый/фактический verdict. Артефакты содержат только allowlisted поля, без headers/cookies/секретов.
- Принимать вердикт только по `VERDICT-POLICY.md`; HTTP 200, browser assertion, состояние процесса и близость timestamp не считаются доказательствами PASS/FAIL. В один кейс включать собственный временный store и fixture namespace.
- Ни этот план, ни успешное прохождение локальных атак не разрешают Dev-мутации, не подтверждают CIZ adapter и не принимают версию ядра автоматически.

Отложено до готовности исполнителя: тестовый код и аудит фактической реализации. Основной агент запросил отдельный code review после уведомления о готовом пакете.
