# Диагностика исходного поручения — инженерный анализ, не результат готового Intelligence

F-001, шаг7, REQUIREMENT_MISMATCH, состояние SOURCE_DISCOVERED.

Исходное требование: выбрать «категория» → «общие» в форме создания справочной работы. В локальной ревизии frontend d4fe0ca1 форма ReferenceBook/TypeActionsPage.jsx не содержит этот выбор. История commit 3ed7969c показывает удаление dropdown и category API parameter; backend migration p6e1a3c5d7f9 удаляет type_action.category_id. Сохранены флаг складской привязки и создание связанной работы. Источники подробно приведены в CIZ-SOURCE-AUDIT.md.

Предлагаемая правка: исключить только выбор категории из пункта7. Новый текст сохранён как scenario-proposed.DRAFT.ru.txt; он **не утверждён и не исполняем**. Оригинал сохранён отдельно без языковых исправлений. Runtime Dev ещё не обследован. Если Dev расходится с локальными исходниками, finding требует пересмотра; нельзя автоматически считать локальную историю установленной версией Dev.

F-002, шаги9/10/17, FIXTURE_UNAVAILABLE, состояние требования безопасного исполнения. «Любая задача/любой исполнитель/первый роутер» не определяют допустимые данные. Нужны конкретные разрешённые IDs в fixture, выбор до мутаций и доказанная принадлежность. Это не исправление бизнес-ожиданий и не разрешение выбрать произвольный объект.

F-003, шаг22, RESULT_UNCONFIRMED, не дефект ЦИЗ. Появление manager action/comment и причинная связь пока не проверены. Требование сохраняется; отсутствие исследования не позволяет удалить его или заменить проверкой текста на экране.

Эта диагностика выполнена инженерами основной агент + Luna по исходникам. Она не доказывает, что будущий программный Intelligence умеет самостоятельно находить расхождение. WP-04 обязан проверить тот же результат на исходном/переставленном/контрольном тексте и runtime evidence.
