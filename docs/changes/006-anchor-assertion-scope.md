# 006 — что именно удостоверяет анкер

Причина: внутреннее ревью WP-05 (docs/harness/WP-05-INTERNAL-REVIEW.md, D-02) показало, что формулировка
WP-00 «процесс, который меняет только каталог прогона, годный анкер для подложного PASS не получает»
сильнее, чем позволяет модель. Подписант проверяет связку approval/consumption/снапшоты/журнал/candidate,
но не пересчитывает бизнес-проверки candidate: это работа Verification Worker.

## Решение

- `AnchorStatement` удостоверяет: (1) конкретный `candidateSha256`, (2) голову цепочки evidence до verdict,
  (3) связку с approval и полным consumption того же runId, (4) неизменность байт candidate на момент подписи.
- Анкер **не** подтверждает бизнес-истину: `checks` candidate считает Verification, а Control публикует только
  результат, прошедший `validateVerdictCoverage` по фактическим `independent-read` из durable storage.
- Подложный candidate, собранный процессом под тем же Windows SID, может получить подпись, если он совпал по
  цепочке и снапшотам. Это граница R-04: DPAPI/ACL одного пользователя не отделяют Verification от другого кода
  той же учётной записи. Для локальной 0.2 принимается; для Dev/ЦИЗ граница должна быть вынесена отдельно.
- Требование к WP-06: candidate строится только из результата Verification в `verifyAndPersist`; внешнего API,
  принимающего candidate, нет. `publishTerminalVerdict` обязан проверять анкер для исхода `anchor`
  (D-01) и не является источником доверенного PASS: единственный источник — `observeTrustedVerdict`
  с `trusted===true` и `passed===true`.

## Что меняем и что нет

Меняется: WP-05 (проверка анкера при публикации, формулировки отчёта), docs/changes.
Не меняется: схема `VerdictPolicy` 0.1, формат evidence-коммитов, модель ключей WP-01, контракт WP-00 по смыслу
(уточняется только область утверждения анкера).
