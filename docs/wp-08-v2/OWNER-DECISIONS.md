# РЕШЕНИЯ, ТРЕБУЮЩИЕ УТВЕРЖДЕНИЯ ВЛАДЕЛЬЦА

До ARCHITECTURE ACCEPT должны быть зафиксированы решения D1–D7. Без них пакет не считается
полным, а реализация не начинается.

## D1 (M09) — конфигурация развёртывания и граница доверия

**Рекомендуемый вариант (предпочтение владельца уже заявлено):**
- Рабочая учётная запись ADAPTANT — обычная **не-административная**.
- TAS и admin-CLI — **отдельная административная граница** (выделенная учётная запись
  администратора, secure desktop UAC, отдельная сессия).
- Обычный SID не имеет записи в Registry, ключам и конфигурации службы.
- Пользовательский код не инициирует операции доверия без подтверждения администратора.

**Альтернативы:** (b) TPM/HSM для ключа анкера/реестра; (c) письменное принятие остаточного
риска владельцем для конкретной среды.

**Деградация owner=local administrator (обязательный анализ):**
- Атакующий того же SID = админ → запись ACL Admins, изменение службы (подмена бинаря),
  чтение DPAPI LM, отладка TAS. Граница TAS **полностью деградирует**; UAC не защищает
  от уже-администратора. TPM/HSM хранит ключ, но не мешает подменить код службы или решения.
- Приёмка v2 для такой среды не выдаётся без варианта (b)/(c) и явного решения владельца.

## D2 — перенос ключа анкера в TAS

Согласовать изменение эксплуатации: anchor-key больше не в пользовательском secretsDir;
файл с ACL только SID службы. Альтернатива (если владелец против) — TAS подписывает через
отдельный защищённый провайдер, но пользовательский процесс не должен иметь доступа к ключу.

## D3 — политика исторических доказательств (M08)

Согласовать: legacy-прогоны/анкеры получают `LEGACY_UNVERIFIED`, автоматического trusted PASS
нет; переаттестация — отдельным решением владельца с офлайн-подтверждением fingerprint
исторических ключей. Никакого «задним числом доказано».

## D4 — DoS через перехват approval

Принять политику: перехват approval даёт DoS легитимному прогону, но не ложный PASS.
Варианты смягчения: bind-журнал, revoke/rebind владельцем, ограничение TTL, уведомление.
Требуется решение, считается ли DoS допустимым или нужен дополнительный owner-шаг.

## D5 — TPM/HSM

Зафиксировать, что TPM/HSM не заменяет административную границу: защищённый ключ не мешает
скомпрометированной системе подменить код службы/решения. Рассматривать как дополнение.

## D6 — Registry: backup и хранение версий

Согласовать срок хранения исторических версий, процедуру backup/restore (подпись владельца,
версия ≥ HWM), ответственного администратора.

## D7 — закрепление ключа TAS в установочном каталоге

Согласовать формат: публичный ключ TAS + его хеш в коде клиента, каталог установки
(ACL: admins/service, read-only для пользователей), подпись артефактов сборки.
