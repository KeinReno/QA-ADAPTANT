# TRUST FOUNDATION V2 — МОДЕЛЬ ДОВЕРЕННЫХ ГРАНИЦ

## 1. Модель угроз A1–A3 (без сужения)

- **A1.** Control, Verification Worker, anchor-signer (в v2 — TAS) — доверенные компоненты,
  запускаемые harness/владельцем.
- **A2.** Противник в локальной 0.2 может: писать любые файлы в runDir и trust root
  (кроме приватных ключей), **поднимать свои процессы того же Windows SID**, подключаться
  к публичным локальным каналам, делать HTTP-запросы. Не имеет прав отладки/инъекции
  в доверенные процессы и не извлекает приватные ключи через DPAPI.
- **A3.** Происхождение устанавливается ключами, живущими только в памяти доверенных
  процессов, и приватными каналами.

Дизайн `41043ad` сужал A2 («не исполняет код от пользователя») — в v2 это **не повторяется**.
Процессы того же SID считаются враждебными.

## 2. Граница доверия v2

Внутри TCB: ядро ОС и её ACL/UAC, служба TAS (выделенный SID), Canonical Trust Registry,
ключ анкера в TAS, подписанный владельцем реестр версий.

Снаружи: пользовательские процессы (A2), сеть, локальный стенд, файлы runDir/trust root.

Правило: **ни одно значение из пользовательского процесса не становится доверенной
истиной о ключах или идентичности корня**. Пользовательский процесс может лишь запросить
проверку/подпись; TAS принимает решение по своему реестру.

## 3. Новые предпосылки (явно)

1. Windows корректно применяет ACL к каталогам ProgramData для SID службы и пользователей.
2. UAC/elevated-токен нельзя получить без согласия администратора; владелец — отдельная
   роль, подтверждающая enrollment/rotation.
3. Атакующий A2 не является администратором и не может отлаживать/инъецировать в TAS.
4. Служба запускается с наименьшими привилегиями; её приватный ключ анкера защищён
   DPAPI LocalMachine + правами службы, а не DPAPI CurrentUser.
5. Реестр версий доступен только на чтение пользователям (через IPC), запись — TAS.

Если предпосылки 1–5 не выполняются на целевой среде (например, пользователь = локальный
администратор), граница доверия деградирует: это фиксируется как остаточный риск и решение
владельца, а не замалчивается.

## 4. Что новая граница НЕ закрывает

- Администратора, ядро, отладку службы.
- Компрометацию owner-ключа (A2 исключает извлечение; при компрометации ключа владельца
  подпись approval перестаёт быть барьером — ротация обязательна).
- Атаки на пользовательский runDir, влияющие только на собственный прогон атакующего
  (не на доверие хранилища).
- Supply-chain зависимостей сборки.

## 5. Границы компонентов

| Компонент | Доверенный? | Права |
|---|---|---|
| TAS | да | владеет реестром, ключом анкера, выпускает grant |
| Enrollment CLI | да (только elevated) | меняет реестр через TAS |
| Control | частично (A1), но не источник ключей | вызывает TAS |
| Verification/Browser Worker | да (A1), но ключи не держит | получает grant |
| Пользовательский CLI/тесты | нет | read-only проверки |
| Файлы runDir/trust root | нет | данные, не доверие |
