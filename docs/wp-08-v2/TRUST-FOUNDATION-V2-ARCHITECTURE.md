# TRUST FOUNDATION V2 — АРХИТЕКТУРА (архитектурное предложение, без реализации)

Статус: DRAFT для архитектурной проверки Qwen.
Основание: REJECT ре-приёмки `41043ad` (аудит `4e96cdc`), подтверждённые R5, R7, R8 (+R6).
Модель A1–A3 сохраняется целиком, без сужения.

## 1. Почему текущий подход не может быть исправлен точечно

Все три обхода имеют одну первопричину: **источник доверия находится в зоне записи
атакующего A2**. DPAPI CurrentUser защищает от чтения чужих ключей, но не разделяет
процессы одного SID: любой процесс пользователя может изготовить новый DPAPI-конверт,
создать новый корень и вызвать публичный API с указателем на него. Самозакрепление
(«корень подтверждает сам себя») не является границей доверия.

Вывод: закрепление должно принадлежать **другой стороне**, чем вызывающий пользовательский
процесс, и идентичность разрешённого Trust Root должна быть зафиксирована вне каталогов,
куда пишет A2.

## 2. Целевая схема

```
┌──────────────────────────── Пользовательский SID (A2) ─────────────────────────────┐
│  Control / Verification Worker / Browser Worker / CLI / тесты                      │
│         │  IPC (named pipe, только read/verify и request-anchor)                   │
│         ▼                                                                          │
└─────────┼──────────────────────────────────────────────────────────────────────────┘
          │
┌─────────▼──────────────── Windows SID службы KAIDEN-TAS (доверенная граница) ──────┐
│  Trust Authority Service (TAS)                                                     │
│   • Canonical Trust Registry  (ProgramData, ACL: SYSTEM+Admins+TAS)               │
│   • Owner-enrolled root identity: trustRootId, ownerKeyId, anchorKeyId,           │
│     registryVersion, история версий (append-only, подписанные записи)             │
│   • Verification: load pinned root → verify approval/anchor/receipt               │
│   • Anchor signing: ключ анкера хранится у TAS (DPAPI LocalMachine + service SID) │
│   • Отказ при любом расхождении; кэша, основанного на метаданных, нет             │
└─────────┬──────────────────────────────────────────────────────────────────────────┘
          │  только при elevated-токене администратора + явное подтверждение владельца
          ▼
┌───────────────────────── Enrollment / Rotation (UAC) ─────────────────────────────┐
│  kaiden-trust-admin enroll|rotate|status|revoke   (запуск elevated)               │
└───────────────────────────────────────────────────────────────────────────────────┘
```

### 2.1. Компоненты

1. **TAS (Windows-служба, выделенный SID).** Единственный владелец доверенной конфигурации.
   Не принимает от клиента ни путь trust root, ни secretsDir, ни ожидаемые keyId.
2. **Canonical Trust Registry** — версионированный журнал: запись = {trustRootId, ownerKeyId,
   anchorKeyId, пути, статус active/revoked/retired, createdAt, registryVersion, подпись
   владельца, подпись администратора}. Хранится вне user-writable каталогов, ACL закрыт.
3. **Enrollment/Rotation CLI** — единственная точка изменения доверия; требует elevated-токен
   (UAC) и подтверждение владельца; выполняет TAS, а не пользовательский процесс.
4. **IPC-контракт** — именованный канал с явным протоколом: `verify-* `, `anchor-*`,
   `observe-*` (read-only), и запрет любых «доверие-меняющих» глаголов для обычного клиента.
5. **Ключи.** Owner-ключ подписи approval остаётся у пользователя (A2 запрещает извлечение
   ключей); TAS хранит **только публичные** ownerKeyId/ключ и сверяет подписи. Ключ анкера
   переносится в TAS: пользовательский процесс больше не держит и не подставляет anchor-ключ.

### 2.2. Ключевые потоки

**startTrusted.**
1. Control передаёт TAS запрос `verify-approval` (approval, runId, manifestSha256, environment).
2. TAS сам читает enrolled root по фиксированному `trustRootId` из реестра (клиент root не
   указывает), проверяет подпись approval против enrolled ownerKeyId, проверяет environment
   record и pinned-канал.
3. TAS выдаёт краткоживущий `verificationGrant` (не ключи), привязанный к runId/approvalId.
4. Anchor signing: Worker просит TAS подписать statement; TAS проверяет grant + evidence head
   и подписывает своим anchor-ключом. Пользовательский процесс не может попросить подпись
   для чужого/произвольного корня.

**observeTrusted / recovery.**
TAS сам читает evidence, terminal-choice, receipt и анкер, сверяет с enrolled root и
историей версий реестра; PASS выдаётся только если все проверки прошли в TAS. Кэш по
mtime/size отсутствует; возможен кэш по хэшу содержимого внутри TAS, но он не является
источником доверия (инвалидация по content-hash + registryVersion).

**Enrollment (однократно, elevated).**
Владелец запускает `kaiden-trust-admin enroll --root <путь>`: TAS фиксирует trustRootId,
ownerKeyId, anchorKeyId, ACL, записывает подписанную запись версии 1. После этого публичный
API не может принять другой корень — только enrolled.

**Rotation.**
`rotate`: elevated + подтверждение владельца + сверка с **внешним ожидаемым keyId**
(владелец вводит/подтверждает fingerprint офлайн) → новая версия реестра, старые версии
остаются для проверки исторических доказательств. Никакого `reseal` из пользовательского API.

## 3. Почему это закрывает R5/R7/R8 и не сужает A2

- **R5 (изготовление DPAPI-конверта тем же SID):** конверт пользователя больше не является
  доказательством. Доверие = запись реестра TAS, а TAS не принимает данные от пользовательского
  процесса как источник истины. Записать в реестр может только elevated enrollment.
- **R7 (выбор нового корня через публичный API):** параметр `trustRoot` удаляется из
  публичных контрактов; TAS обслуживает только enrolled root; новый корень не имеет записи
  в реестре → отказ.
- **R8 (reseal с чужими ключами):** `resealTrustRootPin` удаляется; ротация — только через
  elevated CLI и TAS, со сверкой против внешнего ожидаемого keyId, а не против `owner.pub`
  из подменяемого корня.
- **R6 (кэш по mtime/size):** кэш метаданных удаляется; в TAS — инвалидация по content-hash
  и версии реестра; пользовательского кэша доверия нет.
- **A2 не сужается:** атакующий по-прежнему может писать любые файлы в runDir/trust root,
  поднимать процессы своего SID, подключаться к публичным каналам. Он не может изменить
  реестр TAS (ACL службы), не может получить elevated-токен и не может заставить TAS
  изменить доверие. Остаточные риски (админ/ядро/отладка службы) явно вне A2 и фиксируются
  отдельно.

## 4. Защита от поддельных запросов с пользовательского SID

- IPC-канал разрешает подключение пользователям, но **авторизация не по SID**: read-only
  глаголы возвращают только результат проверки (не ключи, не доверенную конфигурацию).
- Доверие-меняющие операции (enroll/rotate/revoke) недоступны через обычный IPC: только
  elevated CLI, проверка целостности вызывающего (подпись администратора), журналирование.
- Anchor signing принимается только с `verificationGrant`, выданным TAS для конкретного
  runId/approvalId; grant одноразовый, с TTL, привязан к evidence head.
- Replay/подмена запросов: nonce + одноразовые grant + pinning по PID/creationTime клиента
  в пределах сессии (как дополнительный сигнал, не как граница доверия).

## 5. Что остаётся вне гарантий (честно)

- Компрометация администратора/ядра/самой службы TAS.
- Пользователь с правом отладки/инъекции в TAS (A2 это исключает).
- Потеря/удаление реестра TAS: fail-closed, восстановление — санкционированная процедура
  из резервной копии, подписанной владельцем.
