# TRUST FOUNDATION V2 — ПОСЛЕДСТВИЯ ДЛЯ СУЩЕСТВУЮЩИХ УСТАНОВОК

## 1. Поведение без миграции

V2 без enrolled-записи в реестре TAS: любые доверенные операции отказывают
(`TRUST_ROOT_NOT_ENROLLED`). Это fail-closed, а не тихое принятие старого корня.

## 2. Миграция (однократно, elevated)

1. Резервная копия текущего trust root (чтение, без приватных ключей).
2. `kaiden-trust-admin enroll --root <путь> --owner <карточка владельца>`:
   - TAS фиксирует trustRootId, ownerKeyId, anchorKeyId, ACL, создаёт registry v1;
   - владелец подтверждает fingerprint ключей (внешняя сверка, не из подменяемого каталога).
3. Проверка: `kaiden-trust-admin status --json`, затем позитивный P01.
4. Старый `trust-pin.json` переводится в разряд legacy и игнорируется; он не является
   источником доверия.

## 3. Что меняется для пользователей/CI

- В публичных вызовах исчезают `trustRoot`/`secretsDir`/`anchorKeyPath`; скрипты CI
  должны передавать только `trustRootId` (или ничего — единственный enrolled).
- Тестам нужен harness-провайдер TAS (in-memory fake за тем же контрактом) для unit/CI
  без установки службы; fake не должен использоваться в приёмочных прогонах.
- Существующие артефакты evidence/anchor читаются; исторические PASS проверяются по
  registryVersion, действовавшей на момент выпуска.

## 4. Совместимость

- Stable 0.1 не затрагивается (отдельная ветка/тег, решения по F-06 отдельно).
- ADAPTANT 0.3: feature-ветка не меняется; интеграция через публичные контракты и
  аддитивные поля (`trustRegistryVersion`), без переписывания схем.
- Откат: остановка TAS переводит доверенные операции в fail-closed; возврат на 41043ad
  возможен только с явным понижением гарантий и отдельным решением владельца.

## 5. Открытые вопросы владельцу (до реализации)

1. Кто является администратором TAS на целевой среде (локальный админ пользователя?),
   и не деградирует ли этим граница доверия (см. TRUST-BOUNDARIES-V2 §3).
2. Допустим ли перенос ключа анкера в службу (меняет процесс эксплуатации)?
3. Нужен ли TPM/HSM-вариант для сред без доверенного admin-разделения?
4. Формат внешней сверки fingerprint владельцем (офлайн-карточка/рукописный код).
5. Политика хранения исторических версий реестра (срок, бэкапы, восстановление).

## 6. Уточнения v2.1

- Миграция выполняется admin-CLI под отдельной административной границей (M09/D1);
  пользовательский SID миграцию инициировать не может.
- Старый `trust-pin.json` (41043ad) не переносится и не считается защитой; корень,
  созданный прежним `createTrustRoot`, не доверенный до enrollment.
- Legacy-прогоны получают `LEGACY_UNVERIFIED`; автоматического PASS нет (M08/D3).
- Fake TAS-провайдер в миграции/приёмке не используется; приёмка — против реальной службы (M11).
- Откат на 1a510a5/41043ad возможен как понижение гарантий только отдельным решением
  владельца и не считается принятой защитой.
