# 05 — дорожная карта реализации

Реализация начинается только после утверждения WP-00. Каждый пакет ниже — отдельная сдача. Исполнитель пакета не принимает его сам. Следующий пакет, который пишет в `apps/control/run.mjs`, не начинается, пока контракты предыдущих пакетов не зафиксированы отдельным `docs/changes`.

Общие регрессии на каждом пакете, который уже имеет код: `npm test`, `npm run test:races`, `npm run schemas`. До появления кода эти команды для проверки документов не требуются. `npm run test:parallel` по-прежнему не является критерием приёмки.

## Зависимости

```text
WP-00 утверждение
    │
    ▼
WP-01 Identity и формат trust root
    │
    ├── WP-02 Approval и consumption
    ├── WP-04 Environment registry
    └── WP-05 Anchor
            │
            ▼
         WP-03 Policy PDP  (после типов WP-02 и WP-04)
            │
            ▼
         WP-06 Врезка в Control  (один владелец файлов apps/control)
            │
            ▼
         WP-07 Негативные испытания
            │
            ▼
         WP-08 Независимая приёмка
```

WP-02, WP-04 и WP-05 можно вести параллельно после WP-01, потому что у них разные файлы. WP-03 зависит от уже утверждённых структур approval и среды, но не от сетевого кода. WP-06 один: два агента не правят `run.mjs` одновременно. WP-07 пишет тесты и фикстуры отказов, не меняя смысл PEP. WP-08 не пишет продуктивный код.

## Пакеты

### WP-01 — Identity и корень доверия

Цель: создавать и проверять Principal и публичный ключ без сети и без Control.

Объём: `packages/trust/identity.mjs`, загрузка `owner.pub`, проверка роли и статуса. Генерация ключа — утилита, которая пишет файлы только в путь, переданный аргументом, и печатает `keyId`, не сам ключ.

Зависимости: утверждённый WP-00, `packages/core/canonical.mjs`.

Интерфейс: `loadTrustRoot`, `assertPrincipal`.

Тесты: верная подпись карточки, чужой ключ, отозванный Principal, отсутствие файла, отказ писать ключ в каталог репозитория.

Готовность: unit-тесты зелёные, схемы 0.1 без diff, Control не импортирует пакет.

Риск: случайно прочитать приватный ключ в тест и оставить его в артефакте. Запрещено фиксировать PEM в репозитории.

Приёмка: независимый читатель проверяет, что приватный ключ не требуется для `assertPrincipal` и что `runner` не проходит как издатель.

Параллельность: этот пакет первый, его контракт блокирует остальные.

### WP-02 — Approval

Цель: подписывать разрешение на точные входы и один раз связать его с `runId`.

Объём: `packages/trust/approval.mjs`. Эксклюзивное создание consumption. Вычисление состояния `issued/consumed/revoked/expired`.

Зависимости: WP-01.

Интерфейс: `verifyApproval`, `consumeDispatch`, `revokeApproval`.

Тесты: смена одного поля входов меняет хеш и ломает сверку; второй `runId` не создаёт второй файл; тот же `runId` идемпотентен; отзыв; просрочка; чужой issuer.

Готовность: ни один тест не вызывает Playwright и не открывает сокет.

Риск: сделать статус частью подписанного тела. Это запрещено контрактом WP-00.

Приёмка: аудитор отдельно проверяет, что расход не нужен для функции просмотра состояния и что функция расхода не выполняет HTTP.

Параллельность: да, вместе с WP-04 и WP-05.

### WP-03 — Policy

Цель: чистый PDP.

Объём: `packages/trust/policy.mjs`, коды причин, проекция в reason 0.1 как чистая таблица, без записи verdict.

Зависимости: типы WP-02 и WP-04. Можно начать от заглушек структур сразу после утверждения контрактов, не дожидаясь файлового ввода-вывода.

Интерфейс: `decide(facts) -> TrustDecision`.

Тесты: таблица решений из матрицы приёмки на заранее собранных фактах. PDP не получает путь к диску.

Готовность: для каждой строки матрицы есть ожидаемый `effect` и `reasonCode`.

Риск: зашить в PDP чтение trust root и сделать его непроверяемым без файлов. Запрещено.

Приёмка: аудитор вызывает `decide` без окружения стенда.

Параллельность: после стабилизации структур. Не вместе с правкой Control.

### WP-04 — Идентичность среды

Цель: подписанный реестр и сверка локального стенда.

Объём: `packages/trust/environment.mjs`. Опрос `/environment` аргументом URL из реестра, не из произвольного поля вызывающего. Сравнение поколения и хеша nonce. Запрет вида `dev` и `production`.

Зависимости: WP-01. Локальный стенд 0.1 для интеграционного теста. В тестовом стенде допускается отдать `generation` и nonce только под флагом теста, не ломая текущий ответ для старых тестов: старый клиент игнорирует лишние поля JSON, если сервер добавляет их только когда стенд запущен в доверенном режиме. Это единственное будущее изменение `adapters/local`, и оно не входит в WP-00. Пока флаг выключен, ответ `/environment` остаётся прежним.

Интерфейс: `attestEnvironment`.

Тесты: чужой порт, неверный nonce, поколение меньше и больше, `kind=dev`, обрыв сокета, редирект.

Готовность: при любой ошибке результат не `active`.

Риск: принять fingerprint константы `qa-adaptant-local-fixture-v1` как успех. Тест обязан это запретить.

Приёмка: аудитор поднимает посторонний сервер на `127.0.0.1`, который повторяет `environmentId` вызывающего, и видит отказ.

Параллельность: да, до WP-06.

### WP-05 — Анкер

Цель: подписать терминальный коммит в каталог вне прогона и обнаружить конфликт.

Объём: `packages/trust/anchor.mjs`.

Зависимости: WP-01 и существующий формат `evidence-commits`.

Интерфейс: `publishAnchor`, `verifyAnchor`.

Тесты: идемпотентная повторная публикация, второй другой verdict, подмена `envelopeSha256`, отсутствие каталога, таймаут интерфейса не публикует PASS сам по себе — функция только возвращает отказ, решение о verdict принимает будущий PEP.

Готовность: функция не пишет в `evidence.jsonl` и не создаёт `evidence-anchor.json` внутри прогона.

Риск: «починить» отсутствующий анкер локальной копией в каталоге данных. Запрещено.

Приёмка: аудитор переписывает каталог прогона и сохраняет старый анкер; `verifyAnchor` расходится.

Параллельность: да, до WP-06.

### WP-06 — Врезка в Control

Цель: включить T-A, T-B, T-D и T-E, не меняя `start()`.

Объём: `apps/control/trust-entry.mjs` с `startTrusted`, `observeTrusted`, `cancelTrusted`, `reconcileTrusted`. Точечный вызов из `run.mjs` только если передан уже проверенный контекст доверия. Владелец файлов — один исполнитель.

Зависимости: WP-02, WP-03, WP-04, WP-05 и зелёные регрессии 0.1 на нетронутом `start()`.

Интерфейс: четыре функции. `DispatchPermit` не экспортируется за пределы Control.

Тесты: успешный локальный доверенный прогон с одним POST; старый `start()` без trust root по-прежнему проходит текущий runtime; отказ до ACK не создаёт `mutation-intent`; секрет не попадает в окружение Browser до ALLOW.

Готовность: `npm test` и `npm run test:races` зелёные. Схемы 0.1 без diff.

Риск: изменить общий `run()` так, что старый путь начнёт требовать ключ. Критерий отказа пакета — любой старый тест, которому внезапно нужен trust root.

Приёмка: независимый прогон обоих входов. Исполнитель WP-06 не проводит WP-08.

Параллельность: нет.

### WP-07 — Негативная матрица и отказы

Цель: автоматизировать матрицу `06-ACCEPTANCE-MATRIX.md` на временных каталогах.

Объём: `tests/trust-*.test.mjs`. Инъекции: недоступный trust root, задержка анкера, второй процесс на тот же approval, обрыв после consumption.

Зависимости: WP-06.

Готовность: каждая строка матрицы либо автоматический тест с фактическим числом POST, либо явная пометка, почему она проверяется только чтением кода. Пометка не прячет обязательную строку категории.

Риск: тест, который ловит исключение и называет это PASS, не проверив счётчик мутаций стенда.

Приёмка: аудитор запускает тесты сам и сверяет счётчики стенда, не лог агента.

Параллельность: тесты можно писать по контрактам заранее как падающие, но сдаются после WP-06.

### WP-08 — Независимая приёмка

Цель: решение ACCEPT / CONDITIONAL ACCEPT / REJECT по инвариантам доверия.

Объём: отчёт в `docs/`, без правки продуктивного кода проверяющим. Если нужен фикс, его делает исполнитель отдельным циклом, затем новый проход.

Зависимости: WP-07 и неизменность тега `v0.1.0-stable`.

Критерий: регрессия 0.1, доверенный позитивный прогон, выборка негативных строк всех пяти категорий, отсутствие секретов в каталоге прогона, отсутствие нового evidence kind в схеме 0.1.

Параллельность: нет. Проверяющий не является автором WP-06.

## Кому можно отдать работу

| Пакет | Можно отдать другому агенту | Конфликт файлов |
|---|---|---|
| WP-01 | Да, после утверждения | Только `packages/trust/identity.mjs` |
| WP-02 | Да | `packages/trust/approval.mjs` |
| WP-04 | Да | `packages/trust/environment.mjs` |
| WP-05 | Да | `packages/trust/anchor.mjs` |
| WP-03 | Да, один автор PDP | `packages/trust/policy.mjs` |
| WP-06 | Только один исполнитель, не автор независимой приёмки | `apps/control/**` |
| WP-07 | Можно разделить файлы тестов по категориям | Не трогать `run.mjs` |
| WP-08 | Только тот, кто не писал проверяемый пакет | Отчёт, не код |

Общий запрет: не редактировать `packages/contracts/index.mjs`, `schemas/`, `approved-registry.mjs` и тег `v0.1.0-stable` в этих пакетах.

## Порядок, который нельзя переставить

Сначала подпись и расход approval, затем PDP, затем врезка в ACK, затем испытания на повторную мутацию, затем независимая приёмка. Анкер можно писать параллельно, но включать в публикацию PASS только в WP-06 и принимать в WP-08. Среда `dev` не включается ни в одном из этих пакетов.
