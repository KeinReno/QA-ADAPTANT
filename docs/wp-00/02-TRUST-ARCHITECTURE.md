# 02 — архитектура Trust Foundation 0.2

Цель 0.2: перед любой мутацией вне принятого локального пути Control Plane проверяет подписанное разрешение на точные входы, операцию, fixture и подтверждённую среду, а терминальный PASS опирается на подпись вне каталога прогона.

Ядро 0.1 остаётся исполнителем жизненного цикла. Trust Layer не заводит второй журнал мутаций и не выдаёт второй вид approval с другим смыслом.

## Два входа

| Вход | Кто | Поведение |
|---|---|---|
| `start` / `observe` / `cancel` / `reconcile` | Принятые тесты 0.1 | Код и результат как в Stable. Реестр `local-create-record`. Анкер 0.2 не требуется |
| `startTrusted` и парные `observeTrusted`, `cancelTrusted`, `reconcileTrusted` | Новые тесты и будущий адаптер | Тот же `run()` после прохождения PEP. Без доверенного решения мутация не получает ACK |

Отдельные функции нужны, чтобы не менять форму результата `start()` и не заставлять 59 принятых тестов знать про анкер. Внутри оба входа сходятся в одном Control. Второго исполнителя мутаций нет.

Пока `startTrusted` не реализован, продуктивного пути 0.2 нет. WP-00 его только задаёт.

## Участники

Понятия не смешиваются.

| Понятие | Смысл в 0.2 |
|---|---|
| Identity | Запись Principal: идентификатор, роль, публичный ключ, состояние ключа |
| Authentication | Проверка подписи Ed25519 этим публичным ключом. Пароля и сессии нет |
| Authorization | Решение Policy: можно ли этому Principal выполнить это действие в этой среде |
| Approval | Подписанный снимок конкретных входов и границ одной мутации |

Роли 0.2, и только они:

| Роль | Может | Не может |
|---|---|---|
| `owner` | Подписывать approval, отзыв, реестр сред и реестр principal. Держит приватный ключ | Исполнять мутацию в обход Policy |
| `operator` | Собрать запрос на прогон и вызвать `startTrusted` от имени субъекта, указанного в approval | Подписать approval |
| `runner` | Идентичность процесса Control: записать факт расхода approval | Иметь приватный ключ владельца |
| `verifier` | Читать снимки, журнал и анкер | Запускать мутацию и подписывать approval |
| `agent` | В будущем готовить DRAFT | Подписывать, запускать и выбирать среду |

Для одного человека на локальном стенде достаточно ключа `owner`. Он подписывает approval отдельным действием и только потом запускает прогон. Это два разных акта, даже если их выполняет один человек. Роль `operator` может совпадать с человеком-владельцем, но её ключ не подписывает approval. Роль `agent` в 0.2 не получает ключа подписи.

Локальный актор `local-test-harness` остаётся строкой реестра 0.1. Он не является Principal 0.2 и не может подписать внешнюю или доверенную мутацию.

Владелец QA-системы — держатель приватного ключа `owner`. Создавать описание задачи может `operator` или `owner`. Утверждает бизнес-операцию только `owner`. Запускает выполнение `operator` или `owner` через Control. Сам агент в 0.2 действий не исполняет: `maxModelCalls` остаётся 0.

## Корень доверия

Корень — публичный ключ `owner`. Приватный ключ лежит в файле вне репозитория и вне каталога данных прогонов. Путь задаётся окружением `QA_ADAPTANT_TRUST_KEY` и в документы, снимки, журнал и ответы не копируется.

Каталог `QA_ADAPTANT_TRUST_ROOT` тоже вне каталога прогонов. В нём только публичные и подписанные записи:

- `owner.pub` — публичный ключ, `keyId` = SHA-256 сырого ключа
- `principals/` — подписанные карточки
- `environments/` — подписанный реестр сред
- `approvals/` — подписанные разрешения
- `revocations/` — подписанные отзывы
- `consumption/` — факт расхода права мутации, создаётся через эксклюзивную запись
- `anchors/` — подписанные анкеры терминальных прогонов

Каталог данных прогона по-прежнему хранит снимки и `evidence-commits`. Он не хранит приватный ключ и не считается источником истины для PASS доверенного режима.

Проверка подписи использует `node:crypto`, алгоритм Ed25519. Своей схемы подписи нет. Подписывается UTF-8 каноническая форма из `packages/core/canonical.mjs`, без полей `signature` и `signatureAlgorithm`.

## Поток доверенной мутации

```text
owner подписывает Approval
        │
        ▼
startTrusted
        │  снимок 0.1, как сейчас
        ▼
PEP preflight (T-A)
        │  DENY / INDETERMINATE → BLOCKED, approval не израсходован, секрет не выдан
        ▼
аттестация среды по реестру, не по строке вызывающего
        │
        ▼
Browser без секрета мутации
        │
        ▼
INTENT
        │
        ▼
PEP dispatch (T-B)
        │  сверка входов, операции, среды, поколения, fixture, эффектов, срока, отзыва
        │  эксклюзивная запись consumption: approvalId → runId
        │  только затем mutation-intent и ACK
        ▼
существующий затвор тела POST (T-C)
        │
        ▼
Verification Worker считает бизнес-вердикт
        │
        ▼
PEP anchor (T-D)
        │  PASS записывается только после подписи анкера
        │  анкер недоступен → INCONCLUSIVE, запись терминальная
        ▼
observeTrusted показывает PASS только если локальный коммит и анкер совпали
```

`DispatchPermit` — короткоживущая запись в памяти Control после ALLOW на T-B. Её поля: `decisionId`, `approvalId`, `runId`, `inputsHash`, `environmentId`, `environmentGeneration`, `method`, `path`. Browser её не подписывает и не принимает извне. Будущий адаптер может получить её только аргументом вызова из Control. Импорт адаптера из Browser, Verification и будущего Intelligence запрещён границей модулей.

## Три права внутри одного approval

Один документ approval. Три разных права. Второго типа approval нет.

| Право | Расход | Что разрешает |
|---|---|---|
| `dispatch` | Один раз, в момент успешного T-B | Запись intent и последующий единственный POST |
| `observe` | Не расходуется | Чтение уже связанного `runId` |
| `reconcile` | Не расходуется | Повторное чтение после сбоя, без нового POST |

Связывание `runId` происходит в файле `consumption/<approvalId>.json` флагом создания «только если нет». Содержимое: `approvalId`, `runId`, `decisionId`, `consumedAt`. Второй `runId` для того же `approvalId` получает отказ. Повтор того же `runId` — обычная идемпотентность 0.1.

Расход записывается до ACK. Если процесс падает после расхода и до POST, право уже потрачено. Новый POST требует нового approval. Это то же правило, что «intent без ответа не переотправляется». OBSERVE и RECONCILE этого прогона остаются разрешены и мутацию не повторяют.

Отзыв до расхода запрещает T-B. Отзыв после расхода не отменяет уже возможный POST и не разрешает второй. Дальше работает обычный reconcile.

Просрочка до расхода запрещает мутацию. Просрочка после расхода не запрещает чтение результата.

## Среда

Реестр сред подписывает `owner`. Запись содержит стабильный `environmentId`, целое `generation`, вид, статус, точный origin и способ аттестации.

Вызывающая сторона не назначает сервер разрешённым. Control ищет `environmentId` в реестре. Для `local-stand` дополнительно:

- origin буквально `http://127.0.0.1:<порт>`, порт записан в реестре в момент создания стенда владельцем ключа;
- DNS не используется;
- редиректы запрещены, как уже сделано у Verification;
- `/environment` возвращает `environmentId`, `generation` и одноразовый `attestationNonce`, который создал держатель ключа и положил в реестр до доверия;
- совпадение одной только строки fingerprint не принимается.

Поколение увеличивается при смене порта, nonce или статуса. Расхождение поколения между реестром и живым ответом — отказ, для verdict 0.1 проецируется в `ENVIRONMENT_CHANGED`.

В 0.2 Policy разрешает мутацию только при `kind=local-stand` и `status=active`. Записи `dev` и `production` можно хранить как `disabled`, решение для них всегда DENY. Это оставляет место под ЦИЗ и не открывает Dev.

Секрет среды привязан к `environmentId` в реестре. Control передаёт его Browser только после ALLOW на T-A для preflight-чтения, если чтение вообще требует секрет, и заголовок мутации — только после T-B. Для нынешнего локального стенда GET `/environment` секрет не требует. Bearer на POST по-прежнему не пишется в evidence.

Недоступность реестра, обрыв ответа `/environment`, несовпадение nonce или смена origin между T-A и T-B дают INDETERMINATE. PEP трактует это как отказ мутации. Если intent уже записан, повторная отправка не выполняется, итог чтения — `INCONCLUSIVE`.

## Анкер

Подписывается не весь каталог, а заявление о терминальном коммите:

- `runId`, `manifestSha256`
- номер и `envelopeSha256` последнего непрерывного коммита evidence
- значение verdict и код причины 0.1
- `approvalId`, `inputsHash`, `environmentId`, `environmentGeneration`

Файл анкера создаётся в `trust-root/anchors/`, подписью `owner`. Повтор той же канонической записи идемпотентен. Другое заявление на тот же `runId` — конфликт, `INTEGRITY_ERROR`, PASS не выдаётся.

Срок ожидания записи локального анкера — 5 секунд после готового локального результата. Этого достаточно для файла на том же компьютере. Если подпись не легла, Control записывает терминальный `INCONCLUSIVE` с проекцией `EVIDENCE_MISSING` и больше не меняет его на PASS. Так сохраняется неизменяемость терминального verdict 0.1 и не появляется ложный PASS.

OBSERVE доверенного прогона перечитывает коммит и анкер. Совпадение — можно показать сохранённый PASS. Нет анкера или подпись не сходится — показывается удержание результата, локальный файл verdict не переписывается в обход правила одного терминального события. Для прогона без доверенного входа `observe()` 0.1 эту проверку не выполняет.

Авария между локальным коммитом evidence и анкером оставляет прогон без терминального PASS. RECONCILE читает бизнес-состояние существующим Verification Worker и снова проходит T-D. Новый POST не создаётся.

## Policy

PDP — чистая функция. На вход ей передают уже загруженные факты. Сеть и диск внутри PDP запрещены. Загрузка фактов — сборщик в Control.

Результат: `ALLOW`, `DENY` или `INDETERMINATE`.

| Эффект | До intent | После возможной отправки |
|---|---|---|
| ALLOW | Можно перейти к записи intent, если PEP зафиксировал расход | Чтение разрешено, второй dispatch запрещён |
| DENY | `BLOCKED`, POST нет | Не превращается в разрешение повтора |
| INDETERMINATE | Как DENY для новой мутации | `INCONCLUSIVE`, PASS запрещён |

PEP — только Control, точки T-A, T-B, T-D, T-E. Browser не вызывает PDP. Verification не выдаёт ALLOW. Будущий Intelligence не получает функции записи consumption и не импортирует хранилище ключа.

Обязательные входы PDP на dispatch: субъект, операция и её версия, канонический хеш входов, целевой ресурс, среда и поколение, approval и его подпись, состояние расхода и отзыва, состояние прогона, ограничения реестра эффектов.

Дополнительные поля решения: `decisionId`, `reasonCode` доверия, `approvalId`, `inputsHash`, `environmentId`, `environmentGeneration`, `obligations`. Для ALLOW обязательство одно: `consume-dispatch`. Для чтения: `do-not-dispatch`.

## Что будет позже и что не входит в 0.2

В 0.3 и позже, отдельным утверждением: аттестация Dev по отпечатку TLS-сертификата, включение вида `dev`, адаптер ЦИЗ как получатель `DispatchPermit`, отзыв среды без остановки уже начатого чтения, ротация ключа с хранением прежнего публичного ключа как `retired`.

Сознательно откладывается: корпоративный каталог пользователей, OAuth, брокер, отдельная СУБД, микросервисы, собственный формат подписи, UI Workbench, автономное составление сценария, мутации ЦИЗ, миграция QA-v2.

Подключение ЦИЗ позже не меняет модель: любой метод с побочным эффектом, включая GET, который подтверждает уведомления, классифицируется как мутация и проходит T-B. Адаптер не выбирает origin. Origin берётся из реестра сред того поколения, которое подписано в approval. Пока вид среды не `local-stand` и не включён отдельным решением владельца, Policy возвращает DENY.
