# 02 — архитектура Trust Foundation 0.2

Цель 0.2: перед любой мутацией вне принятого локального пути Control Plane проверяет подписанное разрешение на точные входы, операцию, fixture и подтверждённую среду, а терминальный PASS опирается на подпись вне каталога прогона.

Ядро 0.1 остаётся исполнителем жизненного цикла. Trust Layer не заводит второй журнал мутаций и не выдаёт второй вид approval с другим смыслом.

## Два входа

| Вход | Кто | Поведение |
|---|---|---|
| `start` / `observe` / `cancel` / `reconcile` | Принятые тесты 0.1 | Код и результат как в Stable. Реестр `local-create-record`. Анкер 0.2 не требуется. Аргументы approval, trust root и адаптера отвергаются. Этот вход не загружает будущий адаптер |
| `startTrusted` и парные `observeTrusted`, `cancelTrusted`, `reconcileTrusted` | Аутентифицированный локальный оператор | Тот же обработчик ACK после PEP. Без доверенного решения мутация не получает ACK. Адаптер, когда он появится, вызывается только здесь и только с `DispatchPermit` |

Отдельные функции нужны, чтобы не менять форму результата `start()` и не заставлять 59 принятых тестов знать про анкер. Внутри оба входа сходятся в одном Control. Второго исполнителя мутаций нет.

Пока `startTrusted` не реализован, продуктивного пути 0.2 нет. WP-00 его только задаёт.

## Участники

Понятия не смешиваются.

| Понятие | Смысл в 0.2 |
|---|---|
| Identity | Запись Principal: идентификатор, роль, состояние и, для оператора, SID Windows |
| Authentication | Для подписи документов — проверка Ed25519. Для вызова `startTrusted` — SID Windows вызывающего процесса, а не строка в approval |
| Authorization | Решение Policy: можно ли этому уже аутентифицированному Principal выполнить это действие в этой среде |
| Approval | Подписанный снимок конкретных входов и границ одной мутации |

Роли 0.2, и только они:

| Роль | Может | Не может |
|---|---|---|
| `owner` | Подписывать approval, отзыв, реестр сред и реестр principal ключом owner | Подписывать анкер, исполнять мутацию, держать ключ внутри Control |
| `operator` | После проверки SID вызвать `startTrusted` | Подписать approval. Строка `subjectPrincipalId` без SID не является вызовом |
| `runner` | Процесс Control: списать approval и запросить анкер у подписанта | Видеть приватные ключи owner и анкера |
| `anchor-signer` | Отдельный процесс: подписывать только заявление анкера своим ключом | Подписывать approval, отзыв, реестр и аттестацию стенда |
| `verifier` | Читать снимки, журнал и анкер | Запускать мутацию и подписывать |
| `agent` | В будущем готовить DRAFT | Подписывать, запускать и выбирать среду |

Для локальной 0.2 один человек может быть и owner, и operator. Подпись approval и вызов `startTrusted` остаются двумя действиями. Совмещение не даёт процессу Control ни одного приватного ключа. Роль `agent` в 0.2 ключа не получает.

Локальный актор `local-test-harness` остаётся строкой реестра 0.1. Он не является Principal 0.2 и не может подписать доверенную мутацию.

Владелец QA-системы — держатель ключа owner. Утверждает бизнес-операцию только он, отдельной командой подписи. Запускает выполнение аутентифицированный operator через Control. Сам агент в 0.2 действий не исполняет: `maxModelCalls` остаётся 0.

## Ключи и каталоги

Три разных места. Редакция 2 не создаёт их на диске и не считает уже существующими.

| Место | Содержимое | Кто читает приватный материал |
|---|---|---|
| `%LOCALAPPDATA%\KAIDEN\QA-ADAPTANT\secrets\owner.key` | Ключ подписи approval и реестров | Только утилита подписи, запущенная интерактивным пользователем |
| `%LOCALAPPDATA%\KAIDEN\QA-ADAPTANT\secrets\anchor.key` | Ключ анкера | Только процесс anchor-signer |
| `%LOCALAPPDATA%\KAIDEN\QA-ADAPTANT\trust-root\` | Публичные ключи, карточки, реестр, approval, отзывы, consumption, анкеры | Control и проверяющий. Приватных ключей здесь нет |
| Каталог прогона | Снимки и `evidence-commits` | Control. Это не корень доверия |

ACL обоих файлов ключей и каталога `secrets` — только текущий пользователь Windows. На диске байты ключа дополнительно закрыты DPAPI в области этого пользователя: копия файла под другой учётной записью не раскрывает ключ. Утилита подписи расшифровывает ключ в память на время одной подписи. Control не получает переменных с путями к этим файлам.

Резервная копия — отдельное действие владельца. Автоматически ключ не копируется в репозиторий, `runDir`, trust root и журнал. Публичные ключи можно хранить вместе с trust root: ими подпись не восстановить.

Подпись — Ed25519, `node:crypto`, канонический JSON из `packages/core/canonical.mjs`. У каждого подписанного объекта есть поле `domain`. Проверяющий принимает подпись только если `domain` и `keyId` совпали с назначением:

| `domain` | Чей `keyId` |
|---|---|
| `approval`, `revocation`, `principal`, `environment-record` | Публичный ключ owner |
| `anchor-statement` | Публичный ключ anchor-signer |
| `environment-attest` | Публичный ключ стенда, записанный в реестре сред |

Утилита owner отказывается подписывать `anchor-statement`. Процесс anchor-signer отказывается подписывать всё, кроме `anchor-statement`. Поэтому ключ, попавший в Control, в этой схеме не предусмотрен: Control ключа не имеет. Даже ошибочная передача ключа анкера в утилиту owner не создаёт годный approval, потому что проверяющий approval сверяет `keyId` owner.

Процесс anchor-signer слушает локальный канал с ACL текущего пользователя. Эта ACL не отличает Control от любого другого процесса с тем же SID. Для локального 0.2 так и зафиксировано: DPAPI и ACL одного пользователя не изолируют подписанта от произвольного кода этой учётной записи. Перед Dev и ЦИЗ этой границы недостаточно, и она там не применяется.

Внутри этой границы подписант не доверяет хешу, который прислал вызывающий. Запрос содержит `approvalId` и путь прогона. Подписант сам читает trust root и каталог прогона и подписывает заявление только если одновременно верно всё ниже. Иначе ответ `ANCHOR_BINDING_REJECTED`, файла анкера нет.

- Подпись owner на approval верна, домен `approval`, срок и отзыв позволяют публикацию результата уже связанного прогона.
- Файл `consumption/<approvalId>.json` полный, его `bodySha256` сходится, и `runId` в нём равен `runId` манифеста.
- Замороженные снимки прогона совпадают с хешами approval: входы, операция, сценарий, fixture, поколение среды.
- В evidence ещё нет записи verdict. Голова цепочки, посчитанная подписантом, совпадает с головой в candidate.
- `digest` байт candidate совпадает с тем, что войдёт в заявление. Candidate — это будущий артефакт verdict, без ссылки на анкер.
- Файл `terminal-choice.json` ещё не существует. Если он уже есть, новая подпись PASS не выпускается.

Код под тем же SID, который умеет править только каталог прогона, эту связку не собирает: approval и consumption лежат в trust root и подписаны или зафиксированы отдельно. Код под тем же SID, который умеет прочитать `owner.key` через DPAPI, находится за пределом модели и может создать настоящий approval. Это не обещание 0.2.

Trust root на том же компьютере, что и `runDir`, закрывает согласованную перезапись одного только каталога прогона. Это не внешнее хранилище. Перед ЦИЗ границу нужно выносить отдельно. Для локального 0.2 такая граница принята как ограниченная.

## Поток доверенной мутации

```text
утилита owner подписывает Approval ключом owner
        │
        ▼
startTrusted читает SID вызывающего
        │  SID не совпал с карточкой субъекта → DENY, approval не израсходован
        ▼
PEP preflight (T-A) и challenge-response стенда
        │  DENY / INDETERMINATE → BLOCKED, секрет не выдан
        ▼
Browser без секрета мутации
        │
        ▼
INTENT → PEP dispatch (T-B)
        │  новая аттестация, тот же живой процесс стенда
        │  durable consumption, затем mutation-intent, затем ACK
        ▼
непосредственно перед POST (T-C) ещё раз проверяется живой процесс
        │
        ▼
Verification считает candidate в память и в sidecar
        │  в evidence verdict ещё нет
        ▼
anchor-signer подписывает голову цепочки и хеш candidate
        │
        ├─ подпись в бюджет → один evidence verdict PASS или FAIL
        └─ бюджета не хватило для PASS → один evidence verdict INCONCLUSIVE
```

`DispatchPermit` — короткоживущая запись в памяти Control после ALLOW на T-B. Её поля: `decisionId`, `approvalId`, `runId`, `inputsHash`, `environmentId`, `environmentGeneration`, `method`, `path`. Browser её не подписывает и не принимает извне. Будущий адаптер может получить её только аргументом вызова из Control. Импорт адаптера из Browser, Verification и будущего Intelligence запрещён границей модулей.

## Три права внутри одного approval

Один документ approval. Три разных права. Второго типа approval нет.

| Право | Расход | Что разрешает |
|---|---|---|
| `dispatch` | Один раз, в момент успешного T-B | Запись intent и последующий единственный POST |
| `observe` | Не расходуется | Чтение уже связанного `runId` |
| `reconcile` | Не расходуется | Повторное чтение после сбоя, без нового POST |

Связывание `runId` — файл `consumption/<approvalId>.json`. Второй `runId` для того же `approvalId` получает отказ. Повтор того же `runId` — идемпотентность 0.1.

Публикация расхода на Windows не использует `fs.rename` поверх итогового имени. Обычный rename на этой ОС может заменить существующий файл, а проверка «имени ещё нет» перед rename проигрывает гонку. `fsync` каталога здесь не является шагом успеха: на Windows он может вернуть `EPERM` и ничего не доказывает.

Итоговое имя создаётся одним вызовом с диспозицией Win32 `CREATE_NEW`. В Node это флаг `wx`. Если имя занято, вызов возвращает `EEXIST` и не меняет байты файла.

1. Победитель открывает `consumption/<approvalId>.json` с `CREATE_NEW` и пишет полный JSON, включая `bodySha256` от канонического тела без этого поля.
2. Он вызывает `fsync` этого файлового дескриптора, затем закрывает его и читает файл заново. ACK возможен только если прочитанные байты разбираются, `bodySha256` сходится и `runId` равен текущему.
3. Только после этого пишется `mutation-intent`, и только после durable intent уходит ACK.
4. Проигравший получает `EEXIST`. Если файл уже полный и `runId` тот же, он присоединяется к существующему прогону и второй ACK не шлёт. Если `runId` другой, отказ `APPROVAL_REPLAY`. Если файл есть, но неполный, оба пути получают `CONSUMPTION_INCOMPLETE`: ACK нет, файл не удаляется и не перезаписывается.

Падение после `CREATE_NEW` и до полного `fsync` оставляет занятое имя без годного `bodySha256`. Мутации нет. Второго владельца нет. Новый POST требует нового approval. Повтор того же `runId` не дописывает этот файл поверх. `EPERM` от `fsync` каталога, если его всё же вызвали, не превращается ни в успех, ни в разрешение второго ACK.

Это обязательство WP-02. Документ его задаёт; испытание двух процессов и обрыва на Windows выполняется в том пакете, а не этим текстом. OBSERVE и RECONCILE уже связанного прогона остаются чтением.

Отзыв до расхода запрещает T-B. Отзыв после расхода не отменяет уже возможный POST и не разрешает второй. Дальше работает обычный reconcile.

Просрочка до расхода запрещает мутацию. Просрочка после расхода не запрещает чтение результата.

## Аутентификация вызывающего

`subjectPrincipalId` задаёт, кому выписано право. Он не доказывает, что текущий процесс — этот человек. Для однопользовательской 0.2 доказательством служит SID Windows.

Карточка operator, подписанная owner, хранит `windowsSid`. `startTrusted` читает токен вызывающего через API Windows, а не поле JSON. Совпадение SID с карточкой субъекта — факт `authenticatedSid` для PDP. Несовпадение даёт отказ до расхода approval. SID, присланный аргументом функции, игнорируется.

В 0.2 нет сетевого входа. Если вызов идёт не внутри процесса, а через локальный канал, канал разрешает только этот SID, и сервер читает SID клиента сам. Многопользовательская аутентификация в 0.2 не проектируется: другой пользователь Windows до канала не допускается. Процессы той же учётной записи считаются этим оператором. Это граница локальной 0.2, не корпоративный вход.

## Среда

Реестр сред подписывает owner. Запись содержит `environmentId`, поколение, вид, статус, origin и `standKeyId` — идентификатор публичного ключа стенда.

Приватный ключ стенда создаётся в памяти процесса стенда и на диск не пишется. Публичный ключ попадает в реестр в момент регистрации, подписью owner. Перезапуск стенда меняет ключ и требует нового поколения реестра.

Доверенный путь не считает ответом доказательство GET `/environment` и не принимает повтор строки fingerprint. Проверка такая:

1. Control посылает новый случайный challenge.
2. Стенд подписывает `domain=environment-attest`, идентификатор, поколение, origin, свой PID и этот challenge.
3. Control проверяет подпись ключом из реестра и открывает дескриптор этого процесса.
4. Тот же обмен повторяется на T-B, перед расходом approval.
5. Непосредственно перед `route.continue` Control ещё раз убеждается, что дескриптор процесса жив. Если процесс завершился, POST обрывается.
6. Слушающий сокет стенда занимает адрес монопольно. Пока процесс жив, второй слушатель на тот же порт не садится.

Чужой процесс может прочитать открытый ответ и повторить `environmentId`. Без ключа стенда он не подпишет свежий challenge. Если настоящий стенд уже завершился и чужой процесс занял порт, новая аттестация не проходит, а проверка дескриптора перед POST не даёт отправить мутацию на новый сокет.

Остаток гонки — гибель стенда в промежутке между последней проверкой дескриптора и отправкой уже разрешённого пакета. Проверка стоит в том же обработчике, который решает, вызывать ли `route.continue`. Отдельный сервер, который только повторяет публичные поля, этой гонкой не лечится: у него нет ключа и нет старого дескриптора.

Поколение меняется при смене порта, ключа стенда или статуса. Для verdict 0.1 отказ аттестации до мутации проецируется в `ENVIRONMENT_CHANGED`.

В 0.2 Policy разрешает мутацию только при `kind=local-stand` и `status=active`. Записи `dev` и `production` остаются `disabled` и дают DENY.

Секрет среды привязан к `environmentId`. На доверенном пути он попадает в Browser только после T-B. Bearer по-прежнему не пишется в evidence. Старый тестовый стенд без доверенного режима отвечает на `/environment` как сейчас, и `start()` эту новую аттестацию не требует.

Недоступность реестра, обрыв аттестации или смена процесса между T-A и POST дают отказ новой мутации. Если intent уже записан, повторная отправка не выполняется.

## Публикация verdict и анкер

Анкер не подписывается ключом owner и не подписывает сам файл verdict: этот файл ещё нельзя записать, пока неизвестно, появится ли подпись. Иначе отказ анкера потребовал бы второй терминальной записи, что запрещено правилом одного verdict в 0.1.

Candidate — это ровно тот объект, который позже станет артефактом evidence вида `verdict`. Его поля совпадают с `VerdictPolicy` 0.1 и ничем не дополняются: `schemaVersion`, `runId`, `manifestSha256`, `verdict`, `reasonCode`, `message`, `checks`, `ownershipVerified`, `integrityVerified`, `completedAt`. `completedAt` фиксируется в момент durable candidate. `candidateSha256` — `digest` этих байт. Поля `anchorId`, `approvalId` и голова цепочки в candidate не входят, иначе итоговое тело не сойдётся с уже подписанным хешем. Связь с анкером хранится в `AnchorStatement` и в `terminal-choice.json`.

Выбор исхода — отдельный файл `runDir/trust/terminal-choice.json`, тоже через `CREATE_NEW`. В нём `outcome`, `candidateSha256` того тела, которое будет записано в evidence, и при отказе от прежнего PASS-candidate ещё `discardedCandidateSha256`. Два писателя не затирают этот файл. Кто получил `EEXIST`, читает уже выбранный исход и следует ему.

| Состояние | Что уже на диске | Чего ещё нет |
|---|---|---|
| `collecting` | Бизнес-цепочка без verdict | Candidate и выбора исхода |
| `candidate-ready` | Durable candidate бизнеса | `terminal-choice.json` и записи verdict |
| `anchor-held` | `terminal-choice.json` с `outcome=anchor` и годный анкер на этот `candidateSha256` | Записи verdict |
| `terminal` | Ровно один коммит evidence вида `verdict`, его байты равны выбранному candidate | Другого verdict |

Переходы:

1. Verification записывает бизнес-candidate. Журнал evidence verdict не получает. Бюджет `anchorBudgetMs` подписан в профиле trust root: по умолчанию 5000 мс, диапазон от 1 до 60000. Вызывающий его не меняет.
2. Пока выбора нет, runner просит подпись у anchor-signer. Подписант сам проверяет связку approval, consumption, снимков и candidate.
3. Успешная подпись и `CREATE_NEW` выбора `outcome=anchor` переводят прогон в `anchor-held`. В evidence дописывается одно тело, байт в байт равное бизнес-candidate. Ссылка на анкер в это тело не добавляется.
4. Если бюджет истёк раньше, чем выбор создан, `CREATE_NEW` записывает `outcome=budget-inconclusive`. Для evidence собирается новый объект `VerdictPolicy` с `INCONCLUSIVE` и `EVIDENCE_MISSING`. Его `digest` и есть `candidateSha256` выбора. Прежний PASS-candidate остаётся на диске как отброшенный: его хеш пишется в `discardedCandidateSha256` и в журнал не копируется.
5. Анкер, который подписал отброшенный PASS-candidate в момент гонки с бюджетом, не связывается с выбором. Это `ANCHOR_UNLINKED`, не `ANCHOR_CONFLICT` и не повод писать второй verdict или менять INCONCLUSIVE на PASS. После появления `terminal-choice.json` подписант новые PASS-заявления не выпускает.
6. Для бизнес-FAIL без анкера выбор `fail-without-anchor` один раз записывает тот же FAIL-candidate. Нарушение эффекта не прячется. Наблюдение может показать `ANCHOR_MISSING`. Второй записи нет.

Аварии и гонка:

| Момент | Что делать |
|---|---|
| Candidate ещё не durable | Посчитать снова. POST не повторять |
| Выбора нет, анкера нет, бюджет жив | Снова просить подпись. Verdict не писать |
| Выбор `anchor` есть, verdict в evidence нет | Дописать ровно тело выбранного candidate. Бюджет заново не разыгрывать |
| Выбор `budget-inconclusive` есть, а анкер PASS пришёл следом | Анкер оставить непривязанным. Записать один INCONCLUSIVE, если его ещё нет |
| В evidence уже один verdict | Ничего не дописывать |
| Два процесса выбирают исход одновременно | Один `CREATE_NEW`. Второй читает первый файл |

`observeTrusted` показывает PASS только когда выбор равен `anchor`, единственный verdict равен PASS, байты verdict равны `candidateSha256` этого выбора и анкер с тем же хешем подписан ключом anchor-signer. Непривязанный анкер PASS при выборе INCONCLUSIVE не показывается как успех и не считается конфликтом. `observe()` старого входа эту проверку не выполняет.

## Policy

PDP — чистая функция. На вход ей передают уже загруженные факты. Сеть и диск внутри PDP запрещены. Загрузка фактов — сборщик в Control.

Результат: `ALLOW`, `DENY` или `INDETERMINATE`.

| Эффект | До intent | После возможной отправки |
|---|---|---|
| ALLOW | Можно перейти к записи intent, если PEP зафиксировал расход | Чтение разрешено, второй dispatch запрещён |
| DENY | `BLOCKED`, POST нет | Не превращается в разрешение повтора |
| INDETERMINATE | Как DENY для новой мутации | `INCONCLUSIVE`, PASS запрещён |

PEP — только Control, точки T-A, T-B, T-D, T-E. Browser не вызывает PDP. Verification не выдаёт ALLOW. Будущий Intelligence не получает функции записи consumption и не импортирует хранилище ключа.

Обязательные входы PDP на dispatch: аутентифицированный SID, субъект, операция и её версия, канонический хеш входов, целевой ресурс, среда и поколение, результат аттестации, approval и его подпись, состояние расхода и отзыва, состояние прогона, ограничения реестра эффектов. Строка `subjectPrincipalId` без SID в этот набор не подставляется как уже проверенная личность.

Дополнительные поля решения: `decisionId`, `reasonCode` доверия, `approvalId`, `inputsHash`, `environmentId`, `environmentGeneration`, `obligations`. Для ALLOW обязательство одно: `consume-dispatch`. Для чтения: `do-not-dispatch`.

## Что будет позже и что не входит в 0.2

В 0.3 и позже, отдельным утверждением: аттестация Dev по отпечатку TLS-сертификата, включение вида `dev`, адаптер ЦИЗ как получатель `DispatchPermit`, отзыв среды без остановки уже начатого чтения, ротация ключа с хранением прежнего публичного ключа как `retired`.

Сознательно откладывается: корпоративный каталог пользователей, OAuth, брокер, отдельная СУБД, микросервисы, собственный формат подписи, UI Workbench, автономное составление сценария, мутации ЦИЗ, миграция QA-v2.

Подключение ЦИЗ позже не меняет модель: любой метод с побочным эффектом, включая GET, который подтверждает уведомления, классифицируется как мутация и проходит T-B. Адаптер не выбирает origin. Origin берётся из реестра сред того поколения, которое подписано в approval. Пока вид среды не `local-stand` и не включён отдельным решением владельца, Policy возвращает DENY.
