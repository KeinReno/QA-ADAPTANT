# 06 — матрица приёмки

Статус строк: проект критериев. Они станут обязательными в WP-07. PASS строки означает фактический результат процесса и счётчик POST стенда, а не описание в отчёте агента.

Общие доказательства для каждой строки: каталог прогона, коммиты evidence, файл consumption если он должен появиться, анкер если он должен появиться, ответ стенда `mutationCount`. Секретов в этих файлах нет.

Проекция verdict — по таблице контрактов. В колонке «решение» указан эффект PDP и точный `reasonCode` доверия.

## Позитивные

| ID | Предусловие | Действие | Решение | POST | Доказательства | Критерий |
|---|---|---|---|---|---|---|
| P-01 | Старый bundle 0.1, trust root отсутствует | `start()` | путь 0.1, без TrustDecision | 1 при обычном сценарии | как в Stable | Регрессия `npm test` и `npm run test:races` |
| P-02 | Подписанный approval на точные входы локальной операции, среда `local-stand` поколения N | `startTrusted` | ALLOW `TRUST_OK`, затем бизнес-PASS | 1 | intent, request, response, independent-read, consumption на этот `runId`, анкер с тем же `envelopeSha256` | `observeTrusted` показывает PASS |
| P-03 | Прогон P-02 завершён | `observeTrusted` и `reconcileTrusted` | ALLOW фазы чтения, `do-not-dispatch` | 0 новых | тот же consumption | verdict не меняется, второго POST нет |
| P-04 | Approval подписан, старт ещё не вызывался | два одинаковых запроса consumption с одним `runId` | один файл, второй вызов идемпотентен | 0 до старта | один consumption | нет двух записей расхода |
| P-05 | Бизнес-эффект нарушен, анкер доступен | доверенный прогон | бизнес-FAIL, анкер публикуется | 1 | вердикт FAIL и анкер FAIL | отсутствие анкера не требуется, чтобы увидеть FAIL; при доступном корне анкер есть |

## Жизненный цикл

| ID | Предусловие | Действие | Решение | POST | Доказательства | Критерий |
|---|---|---|---|---|---|---|
| L-01 | Два процесса, один approval, разные `runId` | одновременный старт | один consumption, второй `APPROVAL_REPLAY` | не больше 1 | один объект стенда | второй POST — провал |
| L-02 | Approval есть, cancel записан до INTENT | старт | DENY `RUN_CANCELED` → BLOCKED `CANCELED` | 0 | approval остаётся `issued` | расход не создан |
| L-03 | Падение после consumption и до POST | reconcile | чтение, новый dispatch запрещён | 0 | consumption есть, intent может отсутствовать | новый approval обязателен для новой попытки; этот прогон сам не шлёт POST |
| L-04 | Падение после POST | reconcile | существующий путь 0.1, без второго POST | 1 | request evidence не дублируется | счётчик стенда не растёт |
| L-05 | Уже есть терминальный результат | повторный reconcile | чтение | 0 | тот же verdict | нет новой мутации |
| L-06 | Approval использован | новая попытка с тем же документом | `APPROVAL_REPLAY` или `APPROVAL_CONSUMED` | 0 новых | — | отказ |

Строка L-03 сознательно строже удобства: потерянный расход не возвращается. Это согласовано с правилом 0.1 «доказанное отсутствие отправки всё равно не повторяется автоматически».

## Что проверяет независимый аудитор

Минимум WP-08: P-01, P-02, P-03, A-04, A-07, A-09, E-01, E-06, V-01, V-03, L-01, L-03, B-02. Остальные строки обязан закрыть WP-07 автоматическим прогоном, а аудитор выборочно переигрывает любую из них на своей временной директории.

Ложный PASS, второй POST и потеря уже подтверждённого коммита по любой строке — REJECT пакета, даже если остальные строки зелёные.
