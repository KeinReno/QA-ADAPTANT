# 04 — модель угроз

Граница расчёта: один локальный компьютер, один Control Plane, каталог прогонов и отдельный trust root. Противник не является держателем приватного ключа `owner`, пока явно не назван сценарий компрометации ключа. Процессное разделение Browser и Verification защищает от случайной общей логики и не считается границей от того, кто управляет диском.

## Доверенные базы

| База | Доверяем | Не доверяем |
|---|---|---|
| Приватный ключ owner вне репозитория | Подпись approval, отзыва, реестра сред и карточек principal | Подпись анкера; копии в чатах, снимках и evidence |
| Приватный ключ anchor-signer вне репозитория | Подпись только `anchor-statement` | Подпись approval и любых доменов owner |
| Публичный ключ owner и публичный ключ anchor-signer | Проверка подписи своего `domain` | Файл, подменённый до загрузки ожидаемого keyId |
| Приватный ключ стенда в памяти его процесса | Подпись свежего challenge | Ответ `/environment` и повтор публичных полей |
| Код Control на ревизии, которую принял отдельный аудит | PEP не обходится процессом Browser | Запуск изменённого Control без приёмки |
| Каталог прогона | Рабочие снимки и локальная цепочка | Подлинность против полной перезаписи |
| Ответ `/environment` и повтор challenge | Ничего без подписи ключа стенда на новом challenge | Строку fingerprint и скопированный публичный nonce |
| Слова модели и HTTP 200 | Ничего | Уже зафиксировано в правилах проекта |

Ожидаемый `keyId` для доменов owner читается из `owner.pub`, для `anchor-statement` — из `anchor.pub`. Каждый ключ загружается один раз и дальше сравнивается с уже прочитанным значением. Подмена файла после старта не меняет загруженный ключ. Подмена до старта — компрометация корня: новые подписи этого ключа считаются ключом злоумышленника. Это принимаемый остаточный риск локальных ключей. Обнаружение такой подмены не обещается средствами 0.2. Защита — права на файл ключа и отсутствие ключа в репозитории.

## Секреты

| Секрет | Где живёт | Куда не попадает |
|---|---|---|
| Ключ owner | `%LOCALAPPDATA%\KAIDEN\QA-ADAPTANT\secrets\owner.key`, ACL текущего пользователя, байты закрыты DPAPI | Git, snapshot, evidence, trust root, процесс Control, процесс anchor-signer |
| Ключ анкера | `%LOCALAPPDATA%\KAIDEN\QA-ADAPTANT\secrets\anchor.key`, та же защита | Утилита подписи approval, Control, репозиторий, каталог прогона |
| Ключ стенда | Только память процесса стенда | Диск, evidence, реестр. В реестре лежит только `standKeyId` |
| Bearer стенда | Память стенда и окружение Browser после T-B | Snapshot, evidence, документы |
| Старые сессии ЦИЗ | Нигде в этом проекте | Не копируются |

Утрата приватного ключа останавливает новые approval и новые анкеры. Уже записанный терминальный verdict 0.1 без возможности проверить подпись в доверенном режиме не показывается как PASS.

## Участники и что им запрещено

| Участник | Допустимо | Обход, который закрываем |
|---|---|---|
| Владелец ключа owner | Подпись approval и реестров | Подпись анкера и запись intent |
| Процесс anchor-signer | Подпись `anchor-statement` по байтам, которые он сам прочитал | Подпись approval и хранение ключа owner |
| Оператор | Запрос старта после проверки SID | Подмена входов после подписи и вызов от чужого SID |
| Control (`runner`) | PEP, расход, просьба подписать анкер | Приватные ключи, второй POST, PASS без перехода в `terminal` |
| Browser | Щелчок после ACK, один POST на allowlist | Прямой POST до ACK, чужой origin, второй POST |
| Verification | GET и бизнес-вердикт | Публикация PASS доверенного режима, чтение чужого тела как независимого |
| Agent | Ничего в 0.2 | Вызов адаптера и выбор «разрешённого Dev» |
| Вызывающий `start()` | Старый локальный путь | Объявление произвольного loopback средой доверенного пути |

## Сценарии обхода

| Угроза | Что мешает |
|---|---|
| Подменить входы после подписи | `approvedInputsHash` и повторная сверка на T-B и на теле POST |
| Подменить операцию или версию | Оба поля в подписи, плюс реестр смыслов 0.1 |
| Повторить публичный ответ стенда | Свежий challenge и подпись ключа стенда. Копия fingerprint и `environmentId` не проходит |
| Занять порт после гибели стенда | Дескриптор прежнего процесса уже не жив, новый процесс не подписывает challenge старым ключом, POST обрывается до `route.continue` |
| Повторить approval на другом `runId` | Эксклюзивный consumption после fsync |
| Признать обрывок файла расходом и всё же послать ACK | Итоговое имя принимается только после полного чтения. Временный файл ACK не открывает |
| Вернуть расход после падения до ACK | Файл не удаляется. Новый POST требует нового approval |
| Вызвать `startTrusted` с чужим `subjectPrincipalId` | SID берётся из токена процесса, аргумент JSON игнорируется |
| Подписать анкер ключом owner или approval ключом анкера | Разные `domain` и разные `keyId`. Чужой ключ для домена недействителен |
| Дать Control любой из двух приватных ключей | В окружении runner этих путей нет. Подписант анкера — другой процесс |
| Обойти Policy через `start()` и будущий адаптер | `start()` отвергает approval, trust root и адаптер. Адаптер загружается только в `startTrusted` после ALLOW |
| Согласованно переписать только каталог прогона | Подпись анкера другим каталогом и другим ключом. Это не защита от того, кто управляет и диском, и процессом подписанта |
| Записать PASS в evidence, а анкер не получить | Verdict в evidence появляется один раз и только после решения. До этого состояние `candidate-ready` не является PASS |

Канал anchor-signer с ACL текущего пользователя принимает соединение от любого процесса этого SID. Подписант не считает такое соединение доказательством, что вызывающий — Control. Он подписывает только связку, которую сам прочитал: approval с подписью owner, полный consumption с тем же `runId`, снимки прогона и candidate без ссылки на анкер. Подложный PASS в одном только каталоге прогона этой связки не проходит.

DPAPI и ACL не отделяют Control от другого кода той же учётной записи. Такой код может снять защиту `owner.key` и создать настоящий approval. Для локального 0.2 эта граница принята явно. Для Dev и ЦИЗ она не принимается.

Полная перезапись каталога прогона вместе с управлением процессом anchor-signer одним противником, у которого есть права владельца машины, не отличается от действий настоящего владельца. Отдельный каталог trust root на том же компьютере эту границу не усиливает до внешнего хранилища. Компрометация ключа owner останавливает новые approval. Компрометация ключа анкера останавливает новые анкеры и не создаёт approval. Ротация ключей отложена.

## Отрицательные результаты, которые нельзя смягчать

- INDETERMINATE на новой мутации не превращается в ALLOW.
- Состояние `candidate-ready` не показывается как PASS.
- Уже записанный терминальный INCONCLUSIVE не заменяется на PASS.
- Расход approval не снимается, чтобы повторить POST.
- Повтор fingerprint или публичного ответа стенда не заменяет подпись challenge.
- Вердикт Verification Worker со значением PASS остаётся candidate, пока не выполнен переход в `terminal`.
- `start()` не выпускает доверенный PASS и не вызывает адаптер.
- Недоступность Dev или ЦИЗ в 0.2 нечем заменить: эти виды среды дают DENY.
