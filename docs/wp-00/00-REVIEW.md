## Что изменилось после PR #1

| Замечание | Как закрыто |
|---|---|
| A-01. Один ключ и на approval, и на анкер | Два ключа и два процесса. `owner` подписывает только разрешения и реестры. Анкер подписывает отдельный процесс, у которого нет права подписи approval |
| A-02. Публичный nonce можно повторить | Аттестация — challenge-response ключом стенда в памяти процесса. Перед POST Control проверяет, что тот же процесс ещё держит порт |
| A-03. PASS в журнале раньше анкера | Пока нет анкера, в evidence нет verdict. Ровно одна терминальная запись появляется после решения: PASS с анкером или INCONCLUSIVE |
| A-04. `subjectPrincipalId` не доказывает вызывающего | Доверенный вызов читает SID Windows у вызывающего. Поле в approval само по себе личность не подтверждает |
| Расход до ACK | Полный файл consumption появляется через запись во временный файл, fsync и rename на том же томе. ACK только после повторного чтения. Обрывок не считается расходом и не удаляется молча в пользу второго POST |
| Обход через `start()` | Старый вход не принимает approval, trust root и адаптер. Будущий адаптер вызывается только из `startTrusted` |

Ответы Q-01…Q-04 записаны в `08-OPEN-QUESTIONS.md` и больше не блокируют форму протокола. Они не разрешают писать код.

## Что ещё нужно от повторного рассмотрения

Подтвердить, что редакция 2 закрывает A-01…A-04. До этого подтверждения пакеты WP-01…WP-08 не начинаются.

Каталог `%LOCALAPPDATA%\KAIDEN\QA-ADAPTANT\` этой редакцией не создаётся. Документ задаёт путь и ACL, но не утверждает, что каталог уже есть или что права на него уже выставлены. Отдельный каталог trust root на том же компьютере защищает от правки только `runDir`. Перед ЦИЗ этой границы мало; для локального 0.2 она принята как ограниченная.
